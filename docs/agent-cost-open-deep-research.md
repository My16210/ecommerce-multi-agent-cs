# Agent 成本归因：外部样本 open_deep_research 接入报告

**一句话结论**：同一套采集层、不改对方一行业务代码，接住了 LangChain 官方的 open_deep_research；同样三道题，加不加搜索，成本结构从“最终报告占 48.2%”反转为“检索上下文占 69.1%”。

## 一、为什么接它

第一个样本 ecom_cs 是我自己写的。它能回答“哪一次调用花了多少钱”，但证明不了“换一个不是我写的系统，这套采集还能不能接住”。所以外部样本要满足三个条件：不是我的代码、有真实的 LangGraph 子图和多次模型调用、模型可以替换。

open_deep_research 满足这三条。这里的主语是成本工具，ODS 是被观测的样本；成本工具要回答的是“哪一次调用花了多少钱、这笔钱该不该花、改完是否更划算”，本次只验证第一问在外部系统上的可用性，后两问不在范围内。只做观测，不做优化，也不把它当成被优化的对象。

## 二、怎么接的：不改对方业务代码

采集点是 LangChain 的 `BaseCallbackHandler`。调用它的图时，把 recorder 放进 `config["callbacks"]`，三个钩子各管一段：

- `on_chat_model_start`：记开始时间、模型名、节点名（取自 `metadata["langgraph_node"]`）。
- `on_llm_end`：从 `response.generations[0][0].message.usage_metadata` 取 input/output；失败时退回 `llm_output.token_usage`。
- `on_llm_error`：记一条 `source="unknown"`、tokens 为 0 的失败调用，不伪造数字。

callback 会穿过 supervisor / researcher 子图，节点归因来自运行时，不需要猜。每条记录固定八个字段：节点、调用类型、模型、输入 token、输出 token、延迟、来源、provider 有没有真的返回 usage。这样一条记录既能单独看，也能按节点或按模型聚合；失败调用也不会被算成 0。

没有 monkeypatch `init_chat_model`；对方仓库 `git status` 无输出，adapter 只在本仓库。monkeypatch 会把采集绑到某个内部函数名上，对方一改 import 就静默失效；callback 是公开扩展点，代价是必须接受它的调用时机，换来的是长期可维护。采集层和被测系统之间只有一个 `callbacks` 参数，这是这次接入最重要的边界。

跑的时候必须用 ODS 自己的 venv。默认 `--timeout` 240 秒在真实检索下会超时，完整模式统一用 600 秒。搜索由环境变量决定：有 `TAVILY_API_KEY` 就走 Tavily，没有就显式落到 `SearchAPI.NONE`。NONE 是官方支持的取值，不是 mock 搜索。两套运行只改这一个开关；题目、模型、超时、迭代上限保持一致，所以结构差异才能归因到“有没有检索”。

## 三、数据一：降级模式（无搜索，3 题）

| 题 | 调用 | 成本 | 报告字数 |
|---|---|---|---|
| Q1 | 6 | $0.002462 | 6,439 |
| Q2 | 5 | $0.001991 | 4,903 |
| Q3 | 5 | $0.002005 | 5,870 |
| **合计** | **16** | **$0.006458** | — |

按节点（3 题合计）：

| 节点 | 调用 | 成本 | 占比 | 输入 token | 输出 token |
|---|---|---|---|---|---|
| final_report_generation | 3 | $0.003112 | **48.2%** | 5,505 | 9,000 |
| supervisor | 6 | $0.002019 | 31.3% | 10,990 | 2,873 |
| researcher | 4 | $0.000798 | 12.4% | 4,208 | 1,189 |
| write_research_brief | 3 | $0.000529 | 8.2% | 1,277 | 1,394 |

没有检索时，钱集中在最后那一次大报告：48.2%。这不是“报告写得贵”，而是这一模式里几乎只有生成：brief、supervisor、researcher 都在小上下文里做规划，最后一步才把全部内容写成正文。它把“纯生成”的成本单独暴露了出来。

## 四、数据二：完整模式（Tavily 真实检索，同样 3 题）

| 题 | 调用 | 成本 | 报告字数 |
|---|---|---|---|
| Q1（LangGraph vs AutoGen 编排取舍） | 18 | $0.012596 | 6,237 |
| Q2（电商客服多 Agent 的失败模式） | 23 | $0.019739 | 16,482 |
| Q3（RAG Recall@5 78% 如何定位瓶颈） | 22 | $0.021821 | 5,881 |
| **合计** | **63** | **$0.054156** | — |

按节点（3 题合计）：

| 节点 | 调用 | 成本 | 占比 | 输入 token | 输出 token |
|---|---|---|---|---|---|
| researcher_tools | 39 | $0.037426 | **69.1%** | 297,504 | 15,744 |
| compress_research | 3 | $0.004443 | 8.2% | 25,397 | 5,837 |
| supervisor | 9 | $0.004315 | 8.0% | 26,724 | 4,845 |
| final_report_generation | 3 | $0.003812 | 7.0% | 11,809 | 9,000 |
| researcher | 6 | $0.003631 | 6.7% | 25,610 | 2,828 |
| write_research_brief | 3 | $0.000529 | 1.0% | 1,277 | 1,392 |

63 次调用全部 `unknown_calls=0`，三题均无报错。三题之间的差异也落在同一处：Q1 $0.012596，Q2 $0.019739，Q3 $0.021821；调用次数从 18 涨到 23、22，成本却涨得更多，说明多出来的轮次每一轮都在带着更长的上下文跑。Q2 的报告最长（16,482 字），成本却不是最高；Q3 报告最短（5,881 字），成本反而最高。报告长度不是成本的唯一驱动，真正同向的是检索轮次和上下文长度。这正是需要逐次记录、而不是只看请求总量的原因。

## 五、结构为什么反转

同一个系统、同样三道题，加不加搜索，最贵的一步换了人：降级模式是 `final_report_generation`（48.2%），完整模式是 `researcher_tools`（69.1%），最后报告掉到 7.0%。

完整模式下，钱不是花在“生成”上，是花在“反复读”上。`researcher_tools` 39 次调用累计输入 297,504 token、输出只有 15,744，输入输出比约 **18.9 : 1**。机制是每一轮都把之前检索到的网页内容连同已有笔记重新塞进上下文，再决定下一步搜什么，上下文持续膨胀；同一份网页会被后续多轮反复计费。输出 token 只占很小一部分，说明模型不是在“写”，而是在“读完再判断下一步”。

调用次数与成本也不同比例放大：16 → 63（3.9 倍），成本 $0.006458 → $0.054156（8.4 倍）。多出来的钱主要买的是上下文，不是步数。如果只看请求总数，会得到“搜索让成本涨了 8 倍”这种无法行动的结论；逐次记录才能看到涨的是 `researcher_tools` 的**输入**，而不是所有节点等比例变贵。

这也是对成本工具本身的要求：只记请求总量不够，必须保留每一次调用的 token 和节点，否则“结构反转”这个现象根本不可见。

同一个成本机制，在两个项目上量级不同。ecom_cs 的知识库 worker 也是“检索结果进 prompt”，但只放 rerank 后的 2–5 个 chunk；ODS 放的是完整网页，而且多轮累积。这说明工具抓的是同一类成本成因，不是某个框架的专属 bug。对成本工具来说，归因不能停在“哪个模型最贵”，要落到“哪个节点、哪一类 token”；否则换模型只是换一个数字，问题还在。

## 六、这条结论证明/没证明什么

**证明了**：采集层能接住一个不是我们写的 LangGraph 项目；两个模式下 16 次和 63 次调用都有完整的 model / in / out / latency / node 记录，`unknown_calls=0`；节点归因来自运行时，不用猜；同一系统在不同运行模式下的成本结构可以被放在一起比较。

**没证明**：这不是 open_deep_research 的成本基准；绝对值受单一模型和 token 上限影响，不能外推；本次没有做任何优化，不能得出任何降本幅度；降级模式的报告质量也没有被评价。

它也没有回答“哪种模式更好”。降级模式便宜，是因为它根本没做检索；完整模式贵，但贵在它真的读了资料。工具只负责把代价和构成摆出来，值不值是产品判断，不是成本表能替人做的决定。它能证明的是“看得见”，不是“更便宜”；看见之后要不要动、怎么动，是产品侧的判断，成本表只能提供依据。

真要优化，下一步该问的是“减少研究轮次、压缩网页内容、还是限制上下文”，而不是笼统地“换个便宜模型”。这三个方向对应的成本项不同，必须先有节点级和 token 级数据才谈得上验证；这也是本次只交付观测、不交付优化结论的原因。

## 七、限制

1. **只有 3 题、单一模型（qwen-plus）。** 不是 open_deep_research 的成本基准，只是采集层通用性的样本。
2. **final_report 三题都顶到 3000 token 上限**（该角色 `max_tokens` 设为 3000，官方默认 10000）。所以两套总成本都是**下界**，不是自然结束的真实花费。
3. **完整模式 `compress_research` 有两次顶到 2000 token 上限**，同样被截断。
4. **没有复现 ODS 默认的多模型分工**（按仓库配置：summarization 用 gpt-4.1-mini，research / compression / final_report 用 gpt-4.1），这里四个角色统一 qwen-plus，因此绝对成本不可直接外推。
5. **降级模式没有检索**，报告可能编造引用（实际文本里出现过“权威来源/严格实证证据”这类无检索支撑的措辞）。降级模式的数字只用于验证采集层，不用于评价 ODS 的研究质量。
