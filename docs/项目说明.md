## 一、它是什么

一个**能听懂自然语言、并真的去办事**的电商客服系统。用户问一句，系统自己判断该找谁办、
办完把结果合成一段话回答。

它和"套壳聊天机器人"的区别在于：**答案不是模型编的，是系统查出来的**。

| 用户问 | 谁来办 | 为什么是它 |
|---|---|---|
| "退货政策是什么""保修怎么算" | **知识库** | 答案在文档里，要检索 |
| "订单 52644 到哪了""我要退货" | **订单系统** | 答案在数据库里，要查、要写 |
| "哪个大区卖得最好""延迟交付风险最高的是哪种发货方式" | **数据分析** | 答案要算出来，得跑代码 |

第三个是关键：**要算的东西，模型算不对**。所以它不去"心算"，而是写一段 Python、
在沙箱里执行、看结果、不对就改——这是个循环，不是一次调用。

除了打字，客户界面还接受一张图片（商品截图、售后凭证、发票、运单）。图片**不进主链路**：
先用视觉模型提取成结构化字段（订单号 / 金额 / 商品 / 诉求），再拼成一段带标记的文本进图。
这样做的直接后果是安全边界清楚：**图片里认出来的订单号只能用来查，不能用来提交退货**——
写操作必须要求用户在当前这句话里亲手打出订单号。识别失败（没配 key、网络断、图太大、
模型吐了非 JSON）一律降级成"请手动输入"，不挡住后面的对话。

另外，同一批能力还开了一个 **MCP 工具出口**（查订单 / 查退货 / 检索知识库），给别的
Agent 按需调用，走 stdio、不监听端口。它**不经过 Supervisor**——调用方已经知道要查哪笔
订单，不该再花一次模型调用做意图识别。默认只读：按客户号查订单和提交退货默认不注册，
写操作即使打开也要显式 `confirm`。

### 它不做什么（同样重要）

- 不做多 agent 自由对话（一群 agent 互相聊、投票、辩论）。那种结构里一次错误会被下游放大，
  而且**没法定位是哪一环错了**。
- 不让模型拍板。退货申请只登记，最终决定权在后台的审核页（或同一个实现的命令行）。
- 不让匿名用户从话里认领客户身份。绑定客户号之后，订单层只认 principal 上的
  `customer_id`，查/写别人的订单会被拒绝；未绑定的本地演示仍退回 `_guess_customer`
  并在代码里标警告。**这说明的是"演示模式仍不猜"和"绑定后不猜"是两件事**。
  **这条同时决定了会话号是"凭证"而不是"账号"**：拿到它就能读到整段历史，所以界面不把它
  放进 URL、默认 30 天过期。
- 不执行退款。后台的"批准退货"只登记人的决定，没有支付网关可调——**假装退款比不做更坏**。

## 二、它长什么样

一个仓库、一个顶层包 `ecom/`、三个平级子系统：

```
ecom/
├── orchestrator/    编排层：Supervisor + 三个 Worker + 路由 + 汇总
│   ├── core/        supervisor（图的装配）/ router / aggregate / state
│   ├── workers/     knowledge / order / analytics
│   ├── tools/       订单工具（纯函数）—— **模型能调到的**
│   ├── admin/       退货审核—— **只有人能下的结论**（用目录而不是代码评审守这条边界）
│   ├── cli/         returns / session / memory，和界面共用同一份实现
│   ├── session.py   会话与记忆的存取层
│   ├── memory.py    蒸馏 / 召回（要联网，所以不塞进 session.py）
│   └── db/          订单库（SQLite / MySQL 双后端）
├── knowledge/       知识库子系统：混合检索 + 重排 + 生成 + 人审 + 评测
├── analytics/       数据分析子系统：写代码 → 沙箱执行 → 审查 → 纠错
└── mcp/             MCP 工具出口：tools.py（契约）+ server.py（stdio），默认只读
```

三个子系统**接入方式刻意不同**——这不是没统一，是按各自的性质选的：

| 子系统 | 接入 | 为什么 |
|---|---|---|
| 知识库 | **进程内 import** | 热路径（几乎每次提问都走）、无副作用的纯库 |
| 订单 | **本进程 + SQLite** | 毫秒级、纯函数、不调模型 |
| 数据分析 | **子进程** | 唯一执行**模型生成的代码**的，需要一个能被真杀死的边界 |

最后那条值得展开：Python 杀不掉正在跑的线程，"超时"只能做到"不再等它"，进程还在占资源。
而这里跑的是模型写的代码，可能死循环。所以它必须走子进程——`subprocess.run(timeout=)`
是真的杀。**连 Streamlit 界面也走这条边界**，不让界面成为例外。

几个入口，各管一件事：

| 入口 | 给谁用 | 为什么是它 |
|---|---|---|
| `main.py` | **排查问题** | 决策链摊在眼前；界面会把它藏起来 |
| `app.py` | 演示 | 主区域是对话，订单 / 看板 / 知识库是侧边栏的三个直连视图 |
| `admin.py` | **下结论** | 退货审核；三个页面里只有一个能写，口令不配就拒绝启动 |
| `api.py` | 被别的程序调 | 图里全是阻塞调用，所以是 `def` 不是 `async def` |
| `python -m ecom.analytics.cli.analyze` | **给编排层当子进程** | stdout 只吐一行 JSON，契约写在名字里 |
| `python -m ecom.mcp.server` | **别的 Agent**（MCP 客户端） | stdio、无端口；共用一个信封，默认只读 |
| `frontend/` → `/ui` | 浏览器里的第二界面 | React；构建后由 `api.py` 托管，只做流式对话 |

**人工审核这一环，形状是统一的**：模型能判定，不能拍板。知识库里模型判定"这个问题值得
沉淀"，人批准后才进向量库；退货里模型只能**登记**申请，结论由人在后台下。
**为什么中间必须隔一层**：模型生成的答案一旦直接进向量库，下一轮检索就会把它当"权威资料"
捞出来喂给模型——错误会被放大并固化成看起来不容置疑的知识（知识库自污染）。

两个鉴权开关的**方向是故意相反的**，这不是不一致：HTTP 接口不配 `API_KEY` 就放行
（以读为主，面向"clone 下来就能 curl 一下"），后台不配 `ADMIN_PASSWORD` 就**拒绝启动**。
一句话：**读可以默认开放，写必须默认关闭。**

### 数据从哪来

**不是造出来的。** 分析侧和订单侧都跑在一个公开数据集（DataCo 智能供应链）上，同一个源派生出两份：分析用的 20242 行抽样表、订单库用的 65752 笔订单种子。语料是 10 篇电商售后法规原文 + 7 篇客服示例文档。

换成真实数据之后暴露出来的三个问题，比数据本身更值得看——**它们原来被手写数据藏住了**：

1. **一行不等于一笔订单**（DataCo 一行是一个商品项，一笔订单平均 2.8 行）。直接数行数会把订单数多算近三倍，而且不报任何错。所以"口径"从提示词里搬出来，变成数据集目录下的 `NOTES.md`——**一份文件、一次读取、注入到三个 agent**，因为原来那两处各写了一遍，没有任何机制保证一致。
2. **公开数据里没有承运商、没有运单号，连发货地都没有**（只有目的地）。这三列就留空，回答里"有的才说"。合成一个假值会让下游"不许引用不存在的事实"那道检查一起失效。
3. **订单号是 1~5 位，不是 6 位以上**——这个假设在抽取和路由**两处**存在过。改一处才发现另一处：6 位以上的规则对真实订单号一笔都命中不了，却会把发票号路由成"查订单"。两处各自看都对，合起来就是"路由认得出、抽取认不出"。代价是 1~4 位的订单号在对话里认不出来（认错一个订单号比认不出更糟，所以不把门槛放宽）。

## 三、一次真实请求走一遍

下面这段是 2026-10-11 真跑出来的，不是示意（长句为排版折了行）：

```
$ uv run python main.py "订单 52644 到哪了，顺便问下你们的退货政策是什么" -v

路由上限 2 轮　worker 超时 {'knowledge': 90, 'order': 20, 'analytics': 180}
==========================================================
订单号 52644 的物流目的地是圣萨尔瓦多，当前状态为“延迟送达”，最近一次更新时间为
2017年2月12日11:11；但知识库中没有该订单的物流状态相关内容，无法查询具体进展，
建议您登录账户在“我的订单”中查看实时物流信息，或联系客服提供订单号进一步协助。

关于退货政策：自签收次日起7个自然日内，商品完好（含配件、吊牌齐全，无使用痕迹、
污渍、损坏）且不影响二次销售，可申请七天无理由退货；拆开外包装查验商品不视为影响
二次销售。不适用无理由退货的情形包括：定制商品、鲜活易腐品、已拆封的贴身衣物/化妆品/
隐形眼镜、数字化商品、报纸期刊等。退货流程时限为：商家须在48小时内审核退货申请；
同意后，您需在7日内寄回商品并回填快递单号；商家签收后3个工作日内完成验货并处理退款。
----------------------------------------------------------
来源：售后政策.md、促销活动规则.md、退换货流程.md、52644
----------------------------------------------------------
路由：order、knowledge　来源 llm　置信度 0.95
```

注意那句"知识库中没有该订单的物流状态相关内容"——它和前半句的物流信息**看起来冲突**，
其实是两个单元在各自的范畴里各说各话：知识库检索的是售后文档，里面不会有一笔具体订单
的物流；订单库才查得到。系统**没有**去做"冲突检测"把其中一个否掉——它没有能力判断哪边
在什么范畴里说话，挑错的概率比挑对的还高。正确做法是把来源标出来（上面 `来源：` 那行），
让人看得见分歧在哪。

这次运行里发生的事：

1. **router** 用 LLM 分类，置信度 0.95，决定同时找 `order` 和 `knowledge`。
2. 两个 worker 在**同一个超步里并行**：知识库 8.3 秒，订单 11 毫秒——差三个数量级。
   这就是为什么它们的超时是分开配的（90 / 20 / 180 秒）。
3. **aggregate** 手上拿到两个结果，调一次模型合成。
4. 合成的那句话里**主动报告了两个来源的冲突**——知识库说"资料里没有这笔订单的物流"，
   订单系统给了具体物流。系统没有掩盖它，也没有自行判断谁对。

同一天更早的一次运行 dashscope 不通，走的是另一条完整路径：**LLM 路由超时 8 秒 → 退回关键词
规则 → 知识库 worker 超时（标记为"坏了"）→ 订单那半照常答出来 → 明说"知识库这块暂时查不了"**，
总耗时 17.6 秒而不是 180 秒。两条路径都不是摆拍。

## 四、关键设计取舍

这一节是项目的重点。每条都给出"换了什么"。

### 1. 什么时候该用 Agent，什么时候该用 Tool？

判据只有一条：**有没有"看一眼结果再决定下一步"的循环？**

- 没循环 → 那就是个 Tool（函数调用），套上 Agent 的壳只是增加不确定性和 token。
- 有循环 → 才是 Agent。数据分析是典型：写代码 → 跑 → 看报错 → 改 → 再跑。

这个判据也解释了为什么"实时销售看板"没被做成 agent——那是查库，不是 agent。

### 2. Worker 之间不传自然语言，只传结构化结果

每个 worker 返回的是 `{ok, answer, sources, insufficient, ...}` 这样的结构，
不是"我查到了……"这种话。**自然语言在系统内部流转，等于把解析错误埋进管道**——
上一环的措辞变了，下一环就悄悄失效，而且不报错。

### 3. 路由有三层优先级，从聪明到兜底

```
① LLM 分类 → 失败则
② 关键词规则 → 一个都没命中则
③ 最小默认计划（交给知识库，它什么都能聊两句）
```

低置信度（<0.6）时会**往计划里补一个知识库**。这是故意的不对称：漏调一个 worker = 少答一半
（用户看得出来），多调一个 = 多花一次调用（用户看不出来）。

`router_source`（llm / rule / fallback）会记进 trace——**rule 和 fallback 的比例一涨，
就说明 LLM 那边在坏**。

### 4. `ok=False` 和 `insufficient=True` 是两件事

- `ok=False`：**坏了**（服务挂、超时、连不上）
- `insufficient=True`：**看过了，确实没有**

只有后者触发重路由。前者再试一次大概率还是坏——那叫"服务一抖动就换个 worker 再抖一次"。

### 5. 回环是有界的，而且由代码保证

`MAX_ROUNDS` 限轮数、`untried` 必须非空（没有新单元 = 原地打转）、全挂了就不再换人。
三个条件都写在汇总节点里，**不是靠提示词求模型别绕圈**。

### 6. 汇总不引入新事实

只有一个结论时**不调模型**，原样返回。没有东西可合并时调模型，只会把一段本来忠实的话
改写成可能不忠实的另一段话——多一次幻觉机会，零信息增益。

### 7. 换后端只改配置

向量库（Chroma / Milvus）、订单库（SQLite / MySQL）、联网搜索（开 / 关）都是配置切换，
代码不动。这是三个子系统共用的契约。

### 8. 多轮记忆：新建一张表，**不复用**知识库那套 checkpointer

知识库子系统里已经有一套跑通的落盘会话（LangGraph 的 `SqliteSaver`），看着应该直接搬过来
统一——**但不该搬**：

- **`chat_history` 在编排层是"节点输入"，不是"图状态"。** 它由 `make_initial_state` 塞进去，
  图**从不往回写**（没有 reducer、没有累积节点），每一轮都是调用方给一份新的。要让
  checkpointer 接管，就得往图里加"累积历史"的逻辑——那是改图的语义，不是加一个存储。
- **而那会撞上一个已知的坑**：给这个字段加 `operator.add` 之后，每次传入的初始值都会被
  append 而不是替换，历史里凭空多出重复轮次，**且不报错**。
- 两个图不是同一个图，共用一张表会让两种状态混在一个 `thread_id` 空间里。

对面的好处也说清楚，否则这个决定没有分量：**统一成一套的好处是"会话"这件事在整个项目里
只有一个答案**，新人只要学一次；代价是上面三条。**什么条件下该反过来选**：如果编排层以后
要在**图内部**做需要记忆的决策（比如记住"这个用户上一轮已经在等人工了"），那就是"历史作为
状态"，checkpointer 才是对的。

### 9. 三个旋钮看着像，其实是三件事

`HISTORY_TURNS=6` 管**成本**（喂给模型多少上下文），`SESSION_TTL_DAYS=30` 管**合规**
（留多久），`MEMORY_TOP_K=3` 管**成本**（带几条更早的摘要）。它们看起来都可以叫"留多少"，
但改动的动机完全不同——合并成一个开关，会在有人想省钱的时候顺手把合规期限也改掉。

第一个和第三个同属成本，但**是两条独立通道**：原文精确但贵，摘要便宜但有损。它们是两种
不同的东西，**所以不给它们一个共同的倍率**。

**会话过期只在两处触发**（进程启动时一次 + 显式命令），**不做**懒加载式的"读的时候顺手删"
——那会让读操作产生写副作用，出问题时极难定位。代价（长驻进程不会自我清理）如实写进
已知限制，并给了一行 cron。**这是换来的，不是漏掉的。**

**会话内的长期记忆也走同一条立场**：滑出 `HISTORY_TURNS` 那一段会被压成摘要存起来
（`memories` 表），需要时**按语义召回**几条拼在历史前面——**不是整段重灌**。蒸馏**只在
CLI 里做**（`cli.memory distill`），问答路径上一次模型调用都不多花。**代价说清：记忆不是
实时的**，要有人跑 `distill` 才更新，所以它也要外挂 cron。存的是**可执行的事实**（哪一笔
订单、诉求、结论），关键词只当索引——只存话题词的话，回答里继承不到任何结论。**这张表按
`session_id` 键，是会话内的，不是用户画像**；删会话会连摘要一起删。

## 五、做了什么工程保障

- **762 条测试，一条都不联网。** 不是图快——真调模型意味着测试结果随模型版本、网络、
  当天负载浮动，那样的测试没法规格回归，它昨天红今天绿，你只会学会忽略它。
  所有模型调用都用假实现顶掉（HTTP 接口测试也把 `answer` 整个顶掉了）。
- **身份层有契约测试。** token 只存 SHA-256、密码用 scrypt、角色有序、吊销/过期/轮换后
  立即失效、登录会话有 TTL、会话按 principal 归属、客户号绑定后订单归属校验、审计可读；
  API 层按"没 token 401 / 别人的会话 404 / trace 要 admin"钉住。
- **路由有可复跑的分数。** 50 题人工标注集 + `eval_router`：规则基线 `exact 82.0%`、
  `covered 84.0%`，错题分类写进报告；`--llm` 模式可以进一步量模型路由。
- **界面拆了模块。** `app.py` 从 927 行降到 620 行，三个直连视图和渲染件在 `ecom/ui/`；
  真假 Streamlit 两套测试都还在跑，行为没有变。
- **一个不 import 业务代码的 import 检查。** 合并时改了 270 处 import，其中约 55 处位于
  **本机装不上依赖、根本跑不了**的子系统里。这个检查只用 AST + 文件系统比对，把每条
  `from ecom.x.y import z` 解析回真实文件——那是它们唯一的保护。
- **界面测了四层，越往下越"真"。** 假 Streamlit（调用写得对不对）→ **真** Streamlit 运行时
  跑一遍（`AppTest`，函数签名和渲染对不对）→ API 用 `TestClient` 打（鉴权、错误体、会话
  有没有真的接上）→ 以及**一次性的人工验证**（真起 uvicorn、真发请求）。
  **但"没走的那一段"也写清楚了**：没有浏览器、没有 CSS、没有布局，交互路径（打字触发一次
  真实问答）正因为会调模型而**故意不测**。
- **不联网的规矩是"测试"的，不是"验证"的。** 全仓库只有一次真调模型：为了确认 HTTP 接口
  真起得来，真发了一次 `/chat`（257+29 token，1.2 秒）。它**如实标注**了走网络、花 token，
  没有被混进"测试"那一栏。Milvus 那条连外部服务的验证也默认 skip，要显式打开才跑。
- **流式和非流式共用一份收尾。** `answer_stream()` 只多了一个出口，token 汇总
  和 trace 仍然走同一个 `_finalize()`——两条路各写一份账，迟早会一条把重路由
  那轮算进去、另一条忘了，而症状是成本表安静地偏低。**只有汇总模型那一步是
  真逐 token 流**；只有一个结论时整段到达，不把完成的字符串切块假装在流。
- **可观测。** 决策链（用了哪些 worker、谁失败、各花多久、路由来源和置信度）是
  `main.py -v` 和 `GET /trace` 的共同内容。界面会把"哪一层慢 / 哪一层挂了"藏起来
  （超时变成转圈动画），所以排查时该用 CLI。

## 七、怎么跑起来

```bash
git clone <本仓库> ecom_cs && cd ecom_cs
cp .env.example .env      # 填一个模型 API Key
uv sync                   # 界面加 --extra ui
uv run python main.py --init-db                             # 灌演示订单库（65752 笔）
uv run python -m ecom.knowledge.cli.ingest                  # 建向量库
uv run python main.py "订单 52644 到哪了"
```

或者一条 compose 起服务（默认嵌入式向量库，零外部依赖）：

```bash
docker compose up -d      # → http://localhost:8501 客户界面
                          # → http://127.0.0.1:8502 后台（要 .env 里的 ADMIN_PASSWORD）
```

**不填 Key 也能跑**：路由会退回关键词规则，订单那一路完全不依赖模型。这是设计的一部分，
不是碰巧——三层路由里"规则兜底"存在的全部意义就是这个。
（这句话说的是**模型**的 Key，和 HTTP 接口那个 `API_KEY` 开关是两码事。）

后台那一条**不配口令就拒绝启动**——`st.error` + `st.stop`，宁可起不来也不裸奔。
第一次用就在 `.env` 里加一行 `ADMIN_PASSWORD=你自己的口令`。

要**挂到公网上给别人点开**，用另一套编排：

```bash
cp .env.prod.example .env.prod      # 填 DOMAIN / 邀请码 / 模型 Key
docker compose --env-file .env.prod -f docker-compose.prod.yml up -d --build
```

它同时打开三道闸：只读（退货在落库前被挡、数据分析停用、后台不部署）、
邀请码（没配就拒绝所有人）、成本上限（限流 + 每日 token 预算，账本重启也算数）。
能力边界见 [DEMO.md](DEMO.md)，部署与排障见 [RUNBOOK.md](RUNBOOK.md)。
**这一层仍是邀请码门禁；`AUTH_ENABLED` 的身份层是可选的另一层，且没有监控和多副本**，见 [上线清单.md](上线清单.md) 第一节。

## 八、这个项目原本是三个仓库

它是由三个独立开发的仓库合并成的（知识库、数据分析、编排层）。

合并不是为了整齐，是因为原来那个结构**被一次命名事故逼出来的**：两个仓库的顶层包都叫 `src`，
同一进程里必然有一个静默解析错。为了绕开它，知识库走进程内要挂 `sys.path` 加运行时闸门、
数据分析被迫走子进程、还多了四个配置项记录"别的仓库在哪"。

合并之后**这些绕道全部删掉了**。但数据分析那条子进程边界**保留了下来，理由换了一个**：
不再是被命名逼的，而是它执行模型生成的代码，需要一个能被真杀死的进程边界。

保留这个转变很重要——**同一条设计，理由变了，就该重新论证一次**，否则它会变成没人敢动的祖传代码。

合并前/后的完整对照表、以及合并过程中发现的四个"不报错但算错"的坑，
见 [README.md](../README.md#这个仓库是怎么来的)。
