# 多 Agent 电商智能客服系统 · 项目说明

> 这份文档写给**第一次接触这个项目的人**（面试官 / 技术评审），不假设你读过代码。
> 它是 [README.md](../README.md) 的导读：这里讲"这个项目是什么、为什么这么做、做到什么程度"，
> 具体代码位置、逐条实现细节、以及踩过的坑在 README 和 [FLOWCHART.md](../FLOWCHART.md) 里。

## 一、它是什么

一个**能听懂自然语言、并真的去办事**的电商客服系统。用户问一句，系统自己判断该找谁办、
办完把结果合成一段话回答。

它和"套壳聊天机器人"的区别在于：**答案不是模型编的，是系统查出来的**。

| 用户问 | 谁来办 | 为什么是它 |
|---|---|---|
| "退货政策是什么""保修怎么算" | **知识库** | 答案在文档里，要检索 |
| "订单 100002 到哪了""我要退货" | **订单系统** | 答案在数据库里，要查、要写 |
| "哪个地区卖得最好""这季度退货率多少" | **数据分析** | 答案要算出来，得跑代码 |

第三个是关键：**要算的东西，模型算不对**。所以它不去"心算"，而是写一段 Python、
在沙箱里执行、看结果、不对就改——这是个循环，不是一次调用。

### 它不做什么（同样重要）

- 不做多 agent 自由对话（一群 agent 互相聊、投票、辩论）。那种结构里一次错误会被下游放大，
  而且**没法定位是哪一环错了**。
- 不让模型拍板。退货申请只登记，最终决定权在人工审核队列。
- 不猜用户身份。演示里有个从自然语言猜客户号的函数，代码里标了警告——真实系统里
  客户身份必须来自登录态，从话里猜等于让任何人问出别人的订单。

## 二、它长什么样

一个仓库、一个顶层包 `ecom/`、三个平级子系统：

```
ecom/
├── orchestrator/    编排层：Supervisor + 三个 Worker + 路由 + 汇总
│   ├── core/        supervisor（图的装配）/ router / aggregate / state
│   ├── workers/     knowledge / order / analytics
│   ├── tools/       订单工具（纯函数）
│   └── db/          订单库（SQLite / MySQL 双后端）
├── knowledge/       知识库子系统：混合检索 + 重排 + 生成 + 人审 + 评测
└── analytics/       数据分析子系统：写代码 → 沙箱执行 → 审查 → 纠错
```

三个子系统**接入方式刻意不同**——这不是没统一，是按各自的性质选的：

| 子系统 | 接入 | 为什么 |
|---|---|---|
| 知识库 | **进程内 import** | 热路径（几乎每次提问都走）、无副作用的纯库 |
| 订单 | **本进程 + SQLite** | 毫秒级、纯函数、不调模型 |
| 数据分析 | **子进程** | 唯一执行**模型生成的代码**的，需要一个能被真杀死的边界 |

最后那条值得展开：Python 杀不掉正在跑的线程，"超时"只能做到"不再等它"，进程还在占资源。
而这里跑的是模型写的代码，可能死循环。所以它必须走子进程——`subprocess.run(timeout=)`
是真的杀。**连 Streamlit 界面也走这条边界**，不让界面成为例外。

四个入口，各管一件事：

| 入口 | 给谁用 | 为什么是它 |
|---|---|---|
| `main.py` | **排查问题** | 决策链摊在眼前；界面会把它藏起来 |
| `app.py` | 演示 | 四个 Tab = 四个面，共用一份进程 |
| `api.py` | 被别的程序调 | 图里全是阻塞调用，所以是 `def` 不是 `async def` |
| `python -m ecom.analytics.cli.analyze` | **给编排层当子进程** | stdout 只吐一行 JSON，契约写在名字里 |

## 三、一次真实请求走一遍

下面这段是 2026-10-10 真跑出来的，不是示意：

```
$ uv run python main.py "订单 100002 到哪了，顺便问下你们的退货政策是什么" -v

路由上限 2 轮　worker 超时 {'knowledge': 90, 'order': 20, 'analytics': 180}
==========================================================
订单号100002当前物流状态为「派送中」，承运商是中通，运单号ZT9988776655，
路线为郑州→上海，最近一次更新时间为2025-09-20 09:10。

关于退货政策：
- 七天无理由退货：自签收次日起7个自然日内，商品完好……即可申请；
- 质量问题退货（三包）：……

注意：「知识库」单元称提供的资料中没有订单号100002的物流状态相关内容，而「订单」
单元提供了该订单的详细物流信息，二者存在冲突。
----------------------------------------------------------
来源：售后政策.md、退换货流程.md、100002
----------------------------------------------------------
路由：order、knowledge　来源 llm　置信度 0.95
```

这次运行里发生的事：

1. **router** 用 LLM 分类，置信度 0.95，决定同时找 `order` 和 `knowledge`。
2. 两个 worker 在**同一个超步里并行**：知识库 8.3 秒，订单 11 毫秒——差三个数量级。
   这就是为什么它们的超时是分开配的（90 / 20 / 180 秒）。
3. **aggregate** 手上拿到两个结果，调一次模型合成。
4. 合成的那句话里**主动报告了两个来源的冲突**——知识库说"资料里没有这笔订单的物流"，
   订单系统给了具体物流。系统没有掩盖它，也没有自行判断谁对。

同一天更早的一次运行 dashscope 不通，走的是另一条完整路径：**LLM 路由超时 8 秒 → 退回关键词
规则 → 知识库 worker 超时（标记为"坏了"）→ 订单那半照常答出来 → 明说"知识库这块暂时查不了"**，
总耗时 17.6 秒而不是 180 秒。两条路径都不是摆拍。

## 四、关键设计取舍

这一节是项目的重点。每条都给出"换了什么"。

### 1. 什么时候该用 Agent，什么时候该用 Tool？

判据只有一条：**有没有"看一眼结果再决定下一步"的循环？**

- 没循环 → 那就是个 Tool（函数调用），套上 Agent 的壳只是增加不确定性和 token。
- 有循环 → 才是 Agent。数据分析是典型：写代码 → 跑 → 看报错 → 改 → 再跑。

这个判据也解释了为什么"实时销售看板"没被做成 agent——那是查库，不是 agent。

### 2. Worker 之间不传自然语言，只传结构化结果

每个 worker 返回的是 `{ok, answer, sources, insufficient, ...}` 这样的结构，
不是"我查到了……"这种话。**自然语言在系统内部流转，等于把解析错误埋进管道**——
上一环的措辞变了，下一环就悄悄失效，而且不报错。

### 3. 路由有三层优先级，从聪明到兜底

```
① LLM 分类 → 失败则
② 关键词规则 → 一个都没命中则
③ 最小默认计划（交给知识库，它什么都能聊两句）
```

低置信度（<0.6）时会**往计划里补一个知识库**。这是故意的不对称：漏调一个 worker = 少答一半
（用户看得出来），多调一个 = 多花一次调用（用户看不出来）。

`router_source`（llm / rule / fallback）会记进 trace——**rule 和 fallback 的比例一涨，
就说明 LLM 那边在坏**。

### 4. `ok=False` 和 `insufficient=True` 是两件事

- `ok=False`：**坏了**（服务挂、超时、连不上）
- `insufficient=True`：**看过了，确实没有**

只有后者触发重路由。前者再试一次大概率还是坏——那叫"服务一抖动就换个 worker 再抖一次"。

### 5. 回环是有界的，而且由代码保证

`MAX_ROUNDS` 限轮数、`untried` 必须非空（没有新单元 = 原地打转）、全挂了就不再换人。
三个条件都写在汇总节点里，**不是靠提示词求模型别绕圈**。

### 6. 汇总不引入新事实

只有一个结论时**不调模型**，原样返回。没有东西可合并时调模型，只会把一段本来忠实的话
改写成可能不忠实的另一段话——多一次幻觉机会，零信息增益。

### 7. 换后端只改配置

向量库（Chroma / Milvus）、订单库（SQLite / MySQL）、联网搜索（开 / 关）都是配置切换，
代码不动。这是三个子系统共用的契约。

## 五、做了什么工程保障

- **435 条测试，一条都不联网。** 不是图快——真调模型意味着测试结果随模型版本、网络、
  当天负载浮动，那样的测试没法规格回归，它昨天红今天绿，你只会学会忽略它。
  所有模型调用都用假实现顶掉。
- **一个不 import 业务代码的 import 检查。** 合并时改了 270 处 import，其中约 55 处位于
  **本机装不上依赖、根本跑不了**的子系统里。这个检查只用 AST + 文件系统比对，把每条
  `from ecom.x.y import z` 解析回真实文件——那是它们唯一的保护。
- **假 Streamlit 的冒烟测试。** 界面对应的模块连 import 都进不去（没装 `--extra ui`），
  所以往 `sys.modules` 里塞一个记录调用的假模块，把界面真跑一遍。
  它证明的是"调用写得对不对"，**不是"界面好不好看"**。
- **可观测。** 决策链（用了哪些 worker、谁失败、各花多久、路由来源和置信度）是
  `main.py -v` 和 `GET /trace` 的共同内容。界面会把"哪一层慢 / 哪一层挂了"藏起来
  （超时变成转圈动画），所以排查时该用 CLI。

## 六、验证到什么程度（如实说）

| 验过？ | 是什么 | 怎么验的 |
|---|---|---|
| ✅ | 知识库端到端 | 真跑：向量 20 + BM25 20 → RRF 融合取 5 → 重排取 3 → 带 `[1]` 引用的答复 |
| ✅ | 检索与答案质量（新语料） | 真跑：152 题 Recall@5 = 78.3%、MRR 0.533；40 条答案忠实性 83.0%（换语料前 75.3%） |
| ✅ | 编排层端到端 | 真跑：LLM 路由 0.95 → 两 worker 并行 → 汇总，17.6s / 881+370 token |
| ✅ | 订单子系统 | 真跑：本地 SQLite，毫秒级 |
| ✅ | 数据分析出图 | 真跑（容器内）：生成代码 → 沙箱执行 → 出图 7.8s，中文正常 |
| ✅ | 依赖表能装成 | 真构建：`uv sync` 解析出 **150 个包**，五个可选组全装成 |
| ✅ | 435 条测试 / 静态检查 | 431 passed / 3 failed / 1 skipped，3 条**合并前就在红** |
| ❌ | **界面真在浏览器里渲染** | 容器起着、健康检查通，但**没点过那四个 Tab** |
| ❌ | FastAPI 服务 | 装了依赖，没起过服务、没发过请求 |
| ❌ | Milvus 那一支 compose | 只验到配置能解析，没真起过（本机 19530 已被占用） |

**为什么留这些缺口**：本机直连 PyPI 不通，装不上包，所以很多验证是绕道 Docker 做的；
Milvus 那条支线本机 19530 上已经跑着一个不能动的实例。这些是环境限制，不是没做，
但结论就是上面这些**没被验证**，不粉饰成"已通过"。

已知的一个设计缺口：**没有锁文件**，所以每次构建重新解析依赖版本，两次构建的镜像
不保证依赖完全一致。

## 七、怎么跑起来

```bash
git clone <本仓库> ecom_cs && cd ecom_cs
cp .env.example .env      # 填一个模型 API Key
uv sync                   # 界面加 --extra ui
uv run python main.py --init-db                             # 造演示订单库
uv run python -m ecom.knowledge.cli.ingest                  # 建向量库
uv run python main.py "订单 100002 到哪了"
```

或者一条 compose 起服务（默认嵌入式向量库，零外部依赖）：

```bash
docker compose up -d      # → http://localhost:8501
```

**不填 Key 也能跑**：路由会退回关键词规则，订单那一路完全不依赖模型。这是设计的一部分，
不是碰巧——三层路由里"规则兜底"存在的全部意义就是这个。

## 八、这个项目原本是三个仓库

它是由三个独立开发的仓库合并成的（知识库、数据分析、编排层）。

合并不是为了整齐，是因为原来那个结构**被一次命名事故逼出来的**：两个仓库的顶层包都叫 `src`，
同一进程里必然有一个静默解析错。为了绕开它，知识库走进程内要挂 `sys.path` 加运行时闸门、
数据分析被迫走子进程、还多了四个配置项记录"别的仓库在哪"。

合并之后**这些绕道全部删掉了**。但数据分析那条子进程边界**保留了下来，理由换了一个**：
不再是被命名逼的，而是它执行模型生成的代码，需要一个能被真杀死的进程边界。

保留这个转变很重要——**同一条设计，理由变了，就该重新论证一次**，否则它会变成没人敢动的祖传代码。

合并前/后的完整对照表、以及合并过程中发现的四个"不报错但算错"的坑，
见 [README.md](../README.md#这个仓库是怎么来的)。
