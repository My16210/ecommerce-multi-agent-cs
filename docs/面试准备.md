## 零、先把项目讲清楚：30 秒 / 2 分钟 / 5 分钟

面试里「详细讲一下你的项目」从来不是让你背目录。它考的是**你能不能按听众的层次
组织信息**。准备三个版本，现场看对方要哪个。

### 30 秒版（电梯陈述）

> 这是一个基于 LangGraph 的多 Agent 电商客服系统。用户一句自然语言，系统先判断
> 该找谁办，再并行调用知识库、订单、数据分析三个 worker，最后把结果合成一句答复。
> 它解决的不是「让模型会聊天」，而是「让答案来自文档、数据库和真实计算，而不是模型编」。
> 三个 worker 的接入方式是刻意不同的：知识库进程内、订单查 SQLite、数据分析走子进程，
> 因为只有数据分析会执行模型生成的代码，需要一个能被真正杀死的进程边界。
> 入口有四个（CLI / Streamlit / FastAPI / React），另有一条只走 stdio 的 MCP 出口；
> 图片先提取成结构化意图再进主链路，答复通过 SSE 边生成边推；公网演示是只读的。

### 2 分钟版（STAR）

- **S（场景）**：电商客服的问题有三类来源——政策在文档里、订单在数据库里、
  统计要现算。真实用户不会按这个分类说话，「订单 52644 到哪了，顺便问下退货政策」
  一句话两个需求。
- **T（任务）**：做一个能听懂多意图、能真的去查/去算、并且在任何一个子系统挂掉时
  仍然能给出诚实答复的系统。
- **A（行动）**：
  1. **编排**：Supervisor + 3 Worker，router 三层路由（LLM → 关键词 → 默认知识库），
     aggregate 决定 answer / re_route / human；
  2. **契约**：worker 之间只传结构化结果，`ok=False`（坏了）和 `insufficient=True`
     （看过了没有）严格分开；
  3. **知识库**：向量 Top-20 + BM25 Top-20 → RRF 融合 → Top-5 → rerank → Top-3；
  4. **数据分析**：模型写 pandas → 子进程沙箱执行 → 报错自纠 → 审查 → 出报告；
  5. **边界**：模型能判定不能拍板，退货只登记、人工审核；知识库问答不直接回写向量库；
  6. **接入**：图片只做一次视觉提取（订单号 / 金额 / 商品 / 诉求），图片里的订单号
     只能查不能写；`answer_stream()` 只把汇总模型的增量真的吐出来；MCP 走 stdio、
     默认只读；React 前端和 Streamlit 共用同一套 `answer_stream()`。
- **R（结果）**：真实请求 16.3 秒，知识库 8.1 秒、订单 12 毫秒，两个数量级的差异
  正好说明了为什么要分开配超时；检索 152 题 Recall@5 = 78.3%、MRR = 0.533；
  答案忠实性 83.0%；订单库 65,752 笔；**717 条测试（715 passed / 2 skipped）不联网**。

### 5 分钟版（架构 + 取舍 + 边界）

在 2 分钟版上补三块，见下一节 Q1。**关键不是把功能讲全，而是每讲一个设计都带一句
「我为什么不选另一个」。**

### 表达原则

1. **先结论，再展开**：一句话说清这是什么，再讲细节。
2. **每个技术选择都配一个被放弃的选项**：没有对比的选型听起来像照抄教程。
3. **主动说边界**：哪没做、为什么不做、什么条件下会改。这比堆功能更加分。
4. **数字要能解释来源**：说 78.3% 时，要能说清是 152 题里的 119 题、Recall@5。

## 一、项目全局与架构

### Q1. 详细讲一下你的项目，重点讲架构和取舍。

**面试官在考什么**：你能不能把一堆功能组织成一条有主线的架构叙事，而不是报菜名。

**参考答案**：

这个系统的核心是一条单向数据流：

```
START → router → worker_knowledge ┐
              → worker_order     ┼→ aggregate → END（answer / human）
              → worker_analytics ┘         │
                    ↑                        │ decision == "re_route"
                    └────────────────────────┘
```

四个契约决定了整张图：

1. **`CSState`**：`plan`、`tried`、`round`、`results`、`decision` 等字段。
   `results` 是唯一带 reducer 的通道（`Annotated[list, operator.add]`），
   因为三个 worker 在同一超步并行写它。
2. **router**：三层优先级，LLM → 关键词规则 → 默认 knowledge。
   每层失败都有明确出口，模型整个挂掉系统仍然能路由。
3. **worker**：统一返回
   `{worker, ok, answer, data, sources, insufficient, error, elapsed_ms, tokens}`。
4. **aggregate**：短路决策树，顺序是
   「有结论 → 要不要重路由 → 有没有话可说 → 转人工」。

三个子系统接入方式不同，这是设计而不是不一致：

| 子系统 | 接入 | 理由 |
|---|---|---|
| 知识库 | 进程内 import | 热路径、无副作用的纯库；子进程要多付解释器启动 + chromadb 初始化 |
| 订单 | 本进程 + SQLite | 毫秒级、纯函数、不调模型 |
| 数据分析 | 子进程 | 唯一执行模型生成代码的，需要能被真正杀死的边界 |

入口是四个，不是四份实现：CLI（`main.py`）、Streamlit（`app.py`）、FastAPI（`api.py`）、
React（`frontend/`）都调同一个 `supervisor.answer()` / `answer_stream()`；MCP
（`ecom/mcp/`）是另一条**不经过 Supervisor** 的路，因为调用方已经知道要查什么。
这样划分的判据只有一句：**自然语言入口才需要路由，结构化调用不需要。**

**追问与陷阱**：

- 「为什么不是三个 agent 互相聊天？」——自由多 agent 对话会把一次错误在下游放大，
  而且没法定位是哪一环错了。这里用结构化契约 + 单向数据流，代价是不如自由对话灵活，
  换来每一步可查。
- 「这不就是 if-else 加几个函数？」——订单查询确实是工具，套 agent 壳是负收益；
  数据分析才是真 agent，因为它有「写代码 → 执行 → 看报错 → 改」的循环。
  判据只有一条：**有没有看一眼结果再决定下一步的循环。**

### Q2. 为什么要用 Supervisor + Worker，而不是单体 ReAct 或自由多智能体？

**面试官在考什么**：你是否理解多 agent 的适用边界，还是只是跟风。

**参考答案**：

单体 ReAct 的问题是**所有能力挤在一个上下文里**：政策文档、订单 SQL、pandas 代码、
报错信息全在一个 prompt 里，工具一多就会互相干扰，而且一次错误的工具选择会污染
后续所有推理。

自由多智能体（CrewAI / AutoGen 那种 agent 互相发消息）的问题是**错误会被放大且
难以归因**：A 说错一句，B 基于它继续推理，最后你只能看到一段错话，不知道是谁先错的。

Supervisor + Worker 买的是三件事：

1. **隔离**：每个 worker 只拿 `question` 和它需要的那点上下文，不拿完整对话历史。
2. **可归因**：每个单元有自己的 `ok / elapsed_ms / tokens / error`，trace 里一眼能看出
   是哪一环慢、哪一环挂。
3. **可降级**：知识库挂了，订单那半照常答，aggregate 明说「知识库这块暂时查不了」。

**代价**：不如自由对话灵活，worker 之间不能临时协商。这里认为不值得——客服场景的
三类答案是边界清晰的，不需要 agent 之间讨价还价。

**追问与陷阱**：

- 「那你的 supervisor 不也是单点？」——是。但它是**无状态的路由 + 汇总**，挂了可以
  重试；真正的业务能力在 worker 里，彼此独立。
- 「为什么不做成动态 DAG / 任意 worker 串联？」——当前场景没有「A 的输出是 B 的输入」
  这种依赖，三个 worker 都是拿同一个 question 独立干活。做 DAG 会引入调度复杂度，
  但换不来能力。

### Q3. 为什么选 LangGraph，不用 LangChain AgentExecutor、CrewAI、AutoGen？

**面试官在考什么**：框架选型是不是有依据，还是「教程用什么我用什么」。

**参考答案**：

选 LangGraph 的理由是**它把控制流显式化成图**：

- 节点、边、条件边都是代码，不是藏在 agent 循环里的隐式决策；
- 支持并行超步（三个 worker 同时进入）、状态 reducer、checkpoint；
- 递归上限 `recursion_limit` 是框架级兜底，但我们自己的 `MAX_ROUNDS` 才是主约束。

不选 AgentExecutor 的原因：它是「模型决定下一步调哪个工具」的循环，控制流在模型手里。
这个项目恰恰需要**控制流在代码手里**——路由失败要退规则、回环要有界、部分失败要
按固定优先级汇总。把这些交给模型，等于把可预测性交出去。

不选 CrewAI / AutoGen 的原因：它们的核心抽象是「角色 + 对话」，适合探索型任务；
这个项目需要的是「结构化契约 + 单向数据流」，不是角色扮演。

**代价**：LangGraph 的 API 比直接写函数多一层心智负担；状态 reducer 的语义（尤其
`operator.add` 跨轮只增不减）是真踩过坑的。

**追问与陷阱**：

- 「LangGraph 的 checkpoint 你为什么不用？」——见 Q58。`chat_history` 在这个图里是
  节点输入，不是图状态；让 checkpointer 接管要改图的语义，而且会撞上
  `operator.add` 重复累积的坑。
- 「换框架成本高吗？」——控制流、契约、worker 实现都是普通 Python，LangGraph 只包了
  一层图装配。真要换，改 `supervisor.py` 的 `build_graph` 和节点签名，业务代码不动。

### Q4. 三个 worker 是怎么划分的？为什么是三个，不是两个或五个？

**面试官在考什么**：你对「能力边界」的理解，而不是按技术分层拍脑袋。

**参考答案**：

划分依据不是「知识库 / 订单 / 分析」这三个部门，而是**答案在哪里**：

| 问题类型 | 答案在哪 | 需要什么 |
|---|---|---|
| 退货政策、保修 | 文档里 | 检索 + 生成 |
| 订单到哪了、我要退货 | 数据库里 | 查询 / 写入 |
| 哪个大区卖得最好 | 要算出来 | 生成代码 + 执行 + 纠错 |

这三个来源对应三种**完全不同的失败模式**：检索失败是 `insufficient`，查库失败是
`ok=False`，代码执行失败要重试。如果按「售前 / 售中 / 售后」这种业务分，三种失败模式
会混在一个 worker 里，监控上就分不清了。

为什么不是五个：多一个 worker 就多一条并行边、一套超时、一套失败语义，而当前场景
没有第四种答案来源。**能用一个工具函数解决的，不升级成 worker。**

**追问与陷阱**：

- 「订单查询为什么不是 agent？」——它没有循环，输入订单号输出状态，纯函数。
  套 agent 只会多一层提示词、多一次模型调用，换来更不确定的输出。
- 「数据分析为什么是 agent？」——它有完整的「生成 → 执行 → 看报错 → 改」循环，
  这个循环就是它的全部价值。

### Q5. 画一下你的项目流程图。

**面试官在考什么**：你能不能在白板上把系统讲清楚，而不是背文档。

**参考答案**（先画这 7 个框，再补箭头和标注）：

```
                         ┌─────────────────────────────┐
                         │      decision == re_route    │
                         ▼                             │
START ──► router ──┬──► worker_knowledge ──┐           │
                   ├──► worker_order     ──┼──► aggregate ──┬──► END（answer）
                   └──► worker_analytics ──┘                └──► END（human）
```

画的时候按这个顺序讲，面试官会跟着你的思路走：

1. **先画 router**：三层路由，LLM → 规则 → 默认 knowledge。强调「模型挂了也能路由」。
2. **画三条并行边**：三个 worker 在同一超步执行；不在 plan 里的那个节点直接
   `return {}`，所以 trace 里会出现两个「没参与」的节点——这是固定边换白板可读性的取舍。
3. **画 aggregate**：四步短路决策，顺序不能换。
4. **画回环**：只画一条虚线，标注 `MAX_ROUNDS=2` + `tried` 排除，说明环有界。
5. **补三个接入边界**：知识库进程内、订单 SQLite、数据分析子进程。
6. **补一句失败语义**：`ok=False` 不重路由，`insufficient=True` 才重路由。

**追问与陷阱**：

- 「为什么不用 LangGraph 的 `Send` 动态分发？」——`Send` 要在运行时决定连到谁，
  plan 在 router 里已经算好了；固定边 + 节点自己判空，换来的是一张能画在白板上的图。
  代价是 trace 里有两个空节点。
- 「回环会不会死循环？」——三个条件同时保证有界：`plan` 非空、`untried` 非空、
  `round < MAX_ROUNDS`、`alive`。再加上 `recursion_limit = MAX_ROUNDS * 4 + 6` 的
  框架兜底。

### Q6. 一次请求在状态里怎么流？哪些字段会跨轮累加？

**面试官在考什么**：你是否真的理解 LangGraph 的 state 和 reducer，而不是只会拼节点。

**参考答案**：

`CSState` 里只有 `results` 带 reducer：

```python
results: Annotated[list, operator.add]
```

因为三个 worker 在同一个超步并行写它，没有 reducer 的字段在并行写时 LangGraph 会
直接报错。reducer 的语义是「各自 append，合起来」，所以它**跨轮只增不减**。

这带来一个真踩过的坑：第二轮 aggregate 会把第一轮的结论再汇总一遍，症状是
「同一段话说两遍」，而且只在第二轮出现。往一个 `operator.add` 通道写 `[]` 等于没写，
清不掉。

修法是给每条结果盖 `round` 标记（`workers/base.py::stamp_round`），汇总前用
`round_results(results, n)` 挑出本轮的。

`tried` 也是「多个节点想写同一个键」的场合，但这里**没上 reducer**，改成由 router
一次性写入。计划本来就是 router 定的，它顺手记下来最自然；这样从构造上绕开了并发写。
**能用设计绕开的并发问题，就不该用锁或 reducer 去救。**

**追问与陷阱**：

- 「为什么不用一个 `current_results` 字段每轮覆盖？」——并行 worker 写同一个键，
  没有 reducer 就会冲突；用 reducer 是 LangGraph 的契约，不是可选项。
- 「`round` 是谁维护的？」——router 每轮自增，从 1 起。

### Q7. `chat_history` 为什么是节点输入，而不是图状态？

**面试官在考什么**：你能否区分「状态」和「输入」，这是多轮系统最容易混淆的地方。

**参考答案**：

`chat_history` 由调用方通过 `make_initial_state` 塞进去，图**从不往回写**：
没有 reducer、没有累积节点，每一轮都是调用方给一份新的。

读它的是三处：

- **router**：指代消解（「那能退吗」指哪一笔）；
- **order worker**：抽实体；
- **knowledge worker**：生成答案。

**aggregate 刻意不读它**。aggregate 只做「各说各的、不替谁判对错」，它手上已经有
三个 worker 的结构化结论；再给它历史，等于给它素材去改写和脑补，多一次幻觉机会、
零信息增益。

这个决定直接导致会话持久化不能复用 `SqliteSaver`（见 Q58）。

**追问与陷阱**：

- 「那多轮上下文怎么进模型？」——调用方每轮从 `session.history()` 取最近 6 轮，
  拼上记忆，作为 `chat_history` 传进去；图不负责存。
- 「为什么不把历史放进 state 让 checkpointer 管？」——那会变成「历史作为状态」，
  需要往图里加累积逻辑；而且给 `chat_history` 加 `operator.add` 会让每次传入的初始值
  被 append 而不是替换，历史里凭空多出重复轮次，且不报错。

### Q8. 你的回环是怎么保证有界的？

**面试官在考什么**：多 agent 最经典的 bug 就是「没答上来 → 重新路由 → 还是它」。

**参考答案**：

四道门，全在 aggregate 里：

```python
can_retry = (
    bool(plan)          # 这一轮本来就是空计划，重来一遍还是空
    and bool(untried)   # 没有没试过的单元，再路由就是原地打转
    and round_no < MAX_ROUNDS
    and alive           # 全挂了就别换人再挂一次
)
```

再加 router 里的 `plan = [n for n in plan if n not in tried]`，以及
`app.invoke(..., recursion_limit=MAX_ROUNDS * 4 + 6)` 的框架兜底。

关键点是：**这不能靠提示词写一句「不要重复路由」**。模型不会替你保证控制流，
只有代码能。

**追问与陷阱**：

- 「`MAX_ROUNDS=2` 够吗？」——首轮 + 一次重路由。客服场景里，第一轮没答上来通常是
  「这个问题不属于任何一个 worker」，换一个再试一次是合理上限；再多次的收益递减，
  成本线性涨。
- 「全挂了为什么还要回答？」——全挂时 `alive=False`，不重路由，直接把已有的澄清话术
  或故障说明转达，并追加转人工。系统性的坏，换人不解决。

---

### Q9. 如果流量涨 100 倍，这套架构哪里先坏？

**面试官在考什么**：你有没有生产意识，能不能从 demo 架构看出瓶颈。

**参考答案**（按出事顺序）：

1. **SQLite 单写者**：`orders.sqlite` 和 `sessions.db` 都是单文件。横向扩两个副本写
   同一个文件不是「慢一点」，是错。先换 MySQL / Postgres，会话换 Redis 或外部存储。
2. **阻塞调用 + 单进程 uvicorn**：图里全是同步调用，`api.py` 用 `def` 让 FastAPI 丢进
   线程池，并发度 = 线程池大小。一个 8 秒的知识库请求会占住一个线程；没有排队和背压，
   超过线程池就是雪崩。
3. **没有限流和预算**：一次突发重复请求能把三家 LLM 的额度一起打空，没有任何一处先喊停。
4. **没有指标**：只有本地 JSONL trace，没有 dashboard / 告警。你会在用户投诉之后才知道
   出事了。
5. **沙箱资源无上限**：pandas 读大表、死循环、fork 炸弹，容器会先撑不住。
6. **长连接 / 流式**：如果要做打字机效果，同步阻塞模型撑不住，需要改成异步或独立
   streaming 服务。

**追问与陷阱**：

- 「加机器不就行了？」——SQLite 和进程内状态让「加机器」不成立，先解决共享状态。
- 「先优化哪个？」——先限流 + 预算（让服务活下来），再换库，再谈水平扩展。
  优化一个没有上限的系统，等于把雪崩推迟几秒。

### Q10. 这个项目里你最满意的设计和最不满意的设计分别是什么？

**面试官在考什么**：反思能力。只会夸自己项目的人，通常没有真正做过取舍。

**参考答案**：

**最满意**：`ok=False` 和 `insufficient=True` 的区分。它同时解决了行为问题
（服务一抖动就换个 worker 再抖一次）和监控问题（业务规则拦了多少 vs 系统坏了几次）。
这是一个很小的类型区分，但它把「失败」拆成了两种有不同处理方式的东西。

**最不满意**：身份。`_guess_customer` 从自然语言里猜客户号，猜不出用 `C9995` 兜底，
而 `C9995` 是库里真实存在的演示账号。这不是「猜得不准」，是「把客户号当成了不需要
验证的声明」。它是上线清单里的第一条，也是唯一一个「做了就要改架构」的。

## 二、路由与决策

### Q11. 路由为什么做三层？直接让 LLM 分类不就行了？

**面试官在考什么**：你如何处理「模型不可用」这个必然事件。

**参考答案**：

三层是**从聪明到兜底**，顺序就是优先级：

1. **LLM 分类**：能理解改写、口语、多意图。这是主路径。
2. **关键词规则**：LLM 超时、没 key、输出解析不出来时接管。笨、不花钱、不联网、
   不会失败——它存在的全部意义就是「模型这条路整个不可用时还有得用」。
3. **默认最小计划**：规则也没命中，交给 knowledge。它是唯一「什么都能聊两句」的
   worker，答不出来会走 `insufficient`，比直接甩一句「我帮您转人工」体验好。

这不是「不信任 LLM」，是**承认 LLM 会坏**。客服系统不能在模型 API 抖动时整体不可用。

**追问与陷阱**：

- 「规则会不会太粗糙？」——会，而且是有意的。它不负责替代 LLM，只负责在 LLM 挂掉时
  兜住常见问法（订单号、物流、退货、销量、政策）。
- 「规则和 LLM 冲突怎么办？」——LLM 成功时以 LLM 为准，规则不参与；只有 LLM 失败
  才落到规则。不存在「两者投票」。

---

### Q12. 置信度阈值 0.6 是怎么定的？低置信度为什么补 knowledge？

**面试官在考什么**：你是不是拍脑袋调参，还是理解错误代价的不对称。

**参考答案**：

`CONFIDENCE_FLOOR = 0.6`。低于它时，往计划里补一个 knowledge（如果还没试过）。

理由是**路由错一次的代价不对称**：

- 漏调一个 worker = 少答一半，用户看得出来；
- 多调一个 = 多花一次调用，用户看不出来。

所以低置信时宁可多带一个安全的。这是故意的不对称，不是没调好阈值。

0.6 本身是经验值，不是从评测集里拟合出来的。真要严谨，应该用一批带标注的多意图
问题扫阈值，看「漏调率 / 多调率 / 成本」的曲线。当前项目的规模没做这一步，面试时
要如实说。

**追问与陷阱**：

- 「为什么不设 0.9？」——会频繁补 knowledge，成本上升，而且 knowledge 对订单问题
  只能答「资料里没有」，收益很低。
- 「0.6 在换模型后还成立吗？」——不一定。不同模型的置信度分布不同，换模型要重标。
  这是已知限制。

---

### Q13. 路由的超时和重试是怎么设计的？为什么要 `max_retries=0`？

**面试官在考什么**：你是否理解重试放大，以及「重试权应该放在哪一层」。

**参考答案**：

- 单次超时 `ROUTER_TIMEOUT = 8s`；
- 重试次数 `ROUTER_ATTEMPTS = 3`；
- **总预算** `ROUTER_BUDGET = 20s`；
- openai 客户端 `max_retries=0`。

真踩过的坑：客户端 SDK 默认自带 2 次重试，外面又有一层 3 次重试，**两层是乘法**：
单次 8 秒 × SDK 试 3 次 = 24 秒，外面那个「20 秒总预算」直接失效。实测一次请求的
路由环节从 8 秒拖成了 25 秒才开始走规则兜底。

改法是关掉 SDK 自带重试，把重试权收回我们的代码。理由是我们比 SDK 多知道两件事：

1. **这次调用值不值得重试**：路由是幂等分类，值得；写退货不是，绝不能重试。
2. **整件事的总预算是多少**。

**追问与陷阱**：

- 「只有次数没有总时长行不行？」——不行。次数 × 单次超时才是上界；单次超时可能被
  SDK 内部放大，必须有总时长这把锁。
- 「`temperature=0` 是不是就确定了？」——不是。MoE 路由、批处理都会让它抖，偶尔解析
  失败是常态，所以要有重试，不能假定「上次这样这次还这样」。

---

### Q14. 多轮里的「那能退吗」怎么路由？为什么不直接在关键词表里加代词？

**面试官在考什么**：指代消解的设计，以及「加词」这种捷径为什么危险。

**参考答案**：

两处配合：

- **LLM 层**：router 的提示词里带一段**有界**的上文——最近 2 轮、每轮截断 160 字，
  外加最多 3 条记忆。否则「那能退吗」在分类器眼里是一句没主语的话。
- **规则层**：`utils/entities.carried_order_id`。只有同时满足三条才携带上一轮的订单号：
  1. 只看用户发言（客服回答里 5 位以上的数字太多）；
  2. 只看最近 `HISTORY_TURNS` 条；
  3. 那条消息里有 ≥2 个订单号就放弃；
  4. 当轮必须有指代词（那 / 它 / 这笔…），否则不携带。

**为什么不能在关键词表里加「那」「它」**：加词是「看到某个字就路由到某个 worker」，
携带实体是「接着上一轮说」。少了指代词门槛，「退货政策是什么」会因为在订单问题后面
出现而顺带带上 order——一个纯政策问题被拉去查订单。这是「用加词做指代消解」的典型翻车。

**追问与陷阱**：

- 「为什么不携带金额、商品名？」——那要的是字段级消解，不是实体携带。当前只做订单号，
  因为它是唯一同时满足「形状明确、写操作必须精确」的实体。
- 「为什么只带 2 轮？」——成本。路由每轮都跑，整段历史每轮都要付一次 token；
  而且 assistant 的历史回答里 5 位以上数字最多，整段塞进去会把路由往 order 带。

---

### Q15. 携带的订单号为什么「读可以用，写不可以」？

**面试官在考什么**：你是否理解「猜出来的实体」在写操作里的风险。

**参考答案**：

`carried_order_id` 补进来的号是**猜的**。所以：

- **读**（查物流、查状态）：可以用。答错了用户当场看得出来。
- **写**（`create_return`）：**一律不用**，退回「请提供订单号」。
  拿猜的号去提交退货申请，是替用户对**错误订单**办事，而且已经落库了。
- **澄清问句**（`_ask_before_writing`）可以用：它只问不做，把号说出来用户才知道系统
  认成了哪一笔，猜错当场能纠正。

闸门卡在**真正落库前那一行**，不是卡在这条路径的入口。`intent["order_id_source"]`
∈ `{"question", "context", ""}` 就是为这道闸留的。

**代价**：「那我要退货」这种明确诉求也不使用携带的号，用户得再说一次订单号。
这是拿「少问一次」换「绝不对错误订单办事」。

**追问与陷阱**：

- 「这不是体验不好吗？」——是，但代价不对称。多问一次只是麻烦；对错误订单提交退货
  是真实事故。
- 「记忆里的订单号能用于写吗？」——不能。同一条底线：摘要里的订单号是模型写的，
  拿它去提交退货等于替用户对一笔可能错的订单办事。

### Q16. 路由效果怎么评估？线上怎么知道路由在变差？

**面试官在考什么**：你有没有把「模型质量」变成可观测指标。

**参考答案**：

两层：

1. **离线**：准备一批带标注的问题，看每个问题该路由到哪些 worker，算
   plan 的 precision / recall；多意图问题单独看「漏调率」。
2. **线上**：`router_source` 进 trace，取值 `llm / rule / fallback`。
   **rule / fallback 的比例一涨，说明 LLM 那层在坏**——这是整套系统里唯一一个能在
   用户投诉之前发现路由退化的信号。

配套字段还有 `plan_reason`、`plan_confidence`、每个 worker 的
`ok / insufficient / elapsed_ms`。

**追问与陷阱**：

- 「只有比例，没有告警怎么办？」——这正是上线清单里说的：把它接成一个计数器，
  比接十个 CPU 指标有用。当前项目只落到 JSONL，没有 dashboard。
- 「路由错了但答案对了，算错吗？」——算。答案对可能是 knowledge 兜底恰好答上了，
  但路由错了意味着成本和多意图覆盖有问题，迟早会在别的问题上暴露。

### Q17. 一句话里有三个意图怎么办？意图之间冲突怎么办？

**面试官在考什么**：多意图处理，以及汇总层的边界。

**参考答案**：

- **多意图**：router 的提示词明确要求「一句话里有多个不相关的需求就返回多个单元」，
  返回的是 `workers: ["order", "knowledge"]` 这样的列表。三个 worker 并行执行。
- **冲突**：**不做冲突检测**。真实案例：知识库说「资料里没有订单 52644 的物流」，
  订单系统说「目的地 San Salvador，Late delivery」。看起来冲突，其实两个单元在各自
  范畴里各说各话。系统没有能力判断「哪边在什么范畴里说话」，挑错的概率比挑对的还高。
  正确做法是把来源标清楚，让人自己看到分歧。

**追问与陷阱**：

- 「那用户不会困惑吗？」——会，但比系统擅自消解、把对的那半删掉要好。汇总提示词
  第 3 条明确要求「有冲突时如实指出，不要替用户挑一个」。
- 「为什么不让 LLM 判断冲突？」——它没有外部依据判断谁的范畴更权威，只会基于措辞
  自信程度瞎猜。

### Q18. 如果让你加一个新 worker（比如「物流轨迹预测」），要改哪些地方？

**面试官在考什么**：你是否理解架构的扩展点，而不是只会改一个文件。

**参考答案**：

1. **`WORKER_DESCRIPTIONS`**：加名字和职责说明——这份说明就是路由的「知识」，
   改它等于改路由行为。
2. **`workers/`**：实现 `run_xxx`，遵守统一返回契约，用 `stamp_round` 盖轮次。
3. **`supervisor.py`**：加一个节点和一条固定边到 aggregate。
4. **`settings.py`**：加超时。
5. **`aggregate.py`**：加用户可读的失败话术 `_FAIL_NOTE`。
6. **测试**：路由、契约、失败语义、边界（如果是子进程，要有进程边界测试）。

不需要改的：`CSState`（除非需要新字段）、aggregate 的决策树（它按 `ok/insufficient`
泛化处理）、会话层。

**追问与陷阱**：

- 「为什么不做一个插件注册表自动发现 worker？」——当前只有三个，显式注册比魔法发现
  更好调试；等 worker 数量到两位数再谈插件化。
- 「新 worker 要不要进 `tried`？」——要。router 统一排除，防止回环原地打转。

## 三、Worker 契约、可靠性与汇总

### Q19. Worker 之间为什么传结构化结果，不传自然语言？

**面试官在考什么**：你对「系统内部用自然语言流转」的代价有没有认识。

**参考答案**：

三个理由，第一个最要紧：

1. **自然语言要再解析一遍**，等于把「理解」做了两次，每次都可能出错，而且出错时分不清
   是「上游没说清」还是「下游理解错」。
2. **结构化结果能被程序直接消费**：汇总按字段合并、trace 按字段聚合，不用写一层
   「从散文里抠信息」的代码。
3. **上下文隔离的落点就在这**：每个 worker 拿到的是 question 和它自己需要的东西，
   不是完整对话历史。

返回契约：

```python
{"worker": "order", "ok": True, "answer": "...", "data": {...},
 "sources": [...], "insufficient": False, "error": "",
 "elapsed_ms": 7, "tokens": {"in": 0, "out": 0}}
```

**追问与陷阱**：

- 「那 answer 字段不还是自然语言？」——是，但它是**给用户看的最终产物**，
  不是 worker 之间协商的载体。`data` 才是结构化事实。
- 「为什么不让 worker 返回 JSON 再统一渲染？」——`answer` 是已经面向用户的文本，
  再包一层 JSON 只会增加转义和解析失败；`data` 保留结构化即可。

---

### Q20. `ok=False` 和 `insufficient=True` 有什么区别？为什么这个区分重要？

**面试官在考什么**：这是全项目最重要的一条区分，也是最能看出你有没有想过失败语义的。

**参考答案**：

| | 含义 | aggregate 怎么处理 |
|---|---|---|
| `ok=False` | **坏了**：embedding 服务挂、子进程超时、库连不上 | 告诉用户这块暂时不可用；**不重路由** |
| `insufficient=True` | **看过了，确实没有** | 换一个 worker 再试一轮 |

为什么重要：

- **行为上**：把两者混在一起，会变成「服务一抖动就换个 worker 再抖一次」，白烧一轮
  时间还把用户拖住。`ok=False` 多半是同一个网络 / 同一台机器的问题，再试一次大概率
  还是坏。
- **监控上**：看不出「业务规则拦下了多少」和「系统坏了几次」。
- **语义上**：`insufficient` 是**有信息量的失败**——它看过了，这个单元的知识范围里
  确实没有。这时换一个单元是有依据的赌注。

同理，「订单号查不到」「这个状态不能退货」是**业务结论**，以 `ok=True` 返回，
不是故障。

**追问与陷阱**：

- 「有没有例外？」——退货审核链路上有一个 `ok=False` 是刻意留的：用户确实没拿到东西。
  要能说清这个例外。
- 「全部 `ok=False` 怎么办？」——`alive=False`，不重路由，直接说明并转人工。

---

### Q21. Worker 的超时为什么是 90 / 20 / 180 秒？超时真的能杀掉任务吗？

**面试官在考什么**：你是否知道 Python 线程杀不掉，以及「超时」到底保护了什么。

**参考答案**：

三个 worker 的耗时差三个数量级，实测一次请求里知识库 8.1 秒、订单 12 毫秒。
所以超时分开配：

| worker | 超时 | 理由 |
|---|---|---|
| knowledge | 90s | 向量化 + BM25 + rerank + 生成，四步网络往返 |
| order | 20s | 本地 SQLite + 纯规则，正常毫秒级；给 20s 是防库锁 |
| analytics | 180s | 生成代码 + 执行 + 可能审查 + 可能纠错 |

**关键限制**：进程内 worker 的「超时」只是**不再等它**。Python 杀不掉正在跑的线程，
被放弃的线程会自己跑完再被回收。它保护的是响应时间，**不是资源占用**。

真正能强杀的是数据分析那条：`subprocess.run(timeout=...)` 到点是真杀。子进程超时
设成比 worker 超时短 5 秒（175s），让子进程自己的超时先触发，否则是父进程单方面放弃。

**追问与陷阱**：

- 「那知识库死循环怎么办？」——它没有死循环，最坏是网络调用挂起；线程会在底层超时后
  自己结束。真正的资源风险在 analytics。
- 「为什么不把所有 worker 都放子进程？」——知识库是热路径，子进程要多付解释器启动 +
  chromadb 初始化，收益抵不过成本。当前规模下不值得。

### Q22. 一个 worker 挂了，答案怎么组织？会不会让用户觉得系统坏了？

**面试官在考什么**：降级体验的设计。

**参考答案**：

aggregate 把结果分成三堆：

- `usable`：真答上来了；
- `thin`：通了，但明确说「查不到 / 需要更多信息」——它的 answer 是澄清话术，
  不能当正文拼进去，但用户仍需要看到；
- `failed`：这个单元没跑起来。

有 `usable` 时：合并 usable，failed 的补一句「这块暂时用不了」，thin 的澄清话术、
上一轮的 `pending_note` 都附在后面。

没有 usable 但有话可说时：把故障说明 / 澄清话术如实转达；如果全挂了，再追加
`HANDOFF`（转人工）。

什么都说不出才 `human`——这是唯一真正该转人工的情况。

**追问与陷阱**：

- 「为什么不把所有失败都转人工？」——转人工是成本最高、体验最差的兜底。能答一半
  就答一半，并明确说哪块没拿到，比一句「已转人工」有用。
- 「把异常原文给用户行不行？」——不行。`ModuleNotFoundError: No module named 'pymysql'`
  对用户没有意义，还泄露内部结构。错误进日志和 trace，用户只看到人话。

### Q23. 汇总为什么要「不引入新事实」？只有一个结论时为什么连模型都不调？

**面试官在考什么**：你对幻觉来源的理解，以及「少调一次模型」的工程判断。

**参考答案**：

汇总提示词的硬要求：

1. 只做整理：合并重复、调整顺序、统一人称和语气；
2. **一个字的新事实都不许加**：不许补常识、不许推测、不许把没说清的说圆；
3. 有冲突如实指出，不替用户挑一个；
4. 直接给正文，不要「根据以上信息」这类开头。

`len(usable) == 1` 时直接原样返回，不调模型。理由：没有东西可合并时调模型，只会把
一段本来忠实的话改写成一段可能不忠实的另一段话——**多一次幻觉机会，零信息增益**。

**追问与陷阱**：

- 「不调模型，语气不统一怎么办？」——单个 worker 的 answer 已经面向用户写好了；
  为了统一语气而引入幻觉风险，不划算。
- 「多段拼接会不会像两件事？」——`_concat` 在多段时带单元名分节（【知识库】【订单】），
  因为两段来自不同系统的话直接连排，读起来像同一件事的延续。

### Q24. 两个 worker 的结论看起来矛盾，你怎么处理？

**面试官在考什么**：你是否会忍不住「让模型判个对错」。

**参考答案**：

**不消解，只如实呈现**。真实案例：

- 知识库：「提供的资料中没有订单 52644 的物流状态相关内容」；
- 订单：「订单 52644 的物流：目的地 San Salvador，当前 Late delivery」。

同一句话里一个说没有、一个说有，而这**恰恰是对的**：知识库检索的是售后文档，
当然不会有一笔具体订单的物流；orders 表里才有。两个单元各说各的边界。

如果系统看到不一致就去挑一个，它挑掉的很可能正是对的那部分——它没有能力判断
「哪边在什么范畴里说话」。正确做法是把来源标清楚（`来源：售后政策.md、52644`），
让人自己看到分歧。

**追问与陷阱**：

- 「那用户问『到底有没有』呢？」——这属于新的一轮问题，需要 router 重新判断，
  而不是在汇总层猜。
- 「能不能让 worker 带上自己的范畴标签？」——`sources` 已经是这个作用；
  更细的范畴需要 worker 在 `data` 里声明，当前没做。

### Q25. 「退货政策是什么」被当成「我要退货」，真的插了一条申请——你怎么修的？

**面试官在考什么**：这是项目里最严重的一次真实事故，考的是你从事故里提炼规则的能力。

**参考答案**：

事故：一句「订单 52644 到哪了，顺便问下你们的退货政策是什么」，因为含「退货」两个字，
被规则判成 `create_return`，**系统替用户提交了退货申请**。

修法是三层闸门：

1. **第一人称诉求才触发**：`CREATE_RETURN_HINT` 匹配「我要退 / 帮我退 / 申请退 /
   不想要了…」。光出现「退货」两个字不算。
2. **政策问法排除**：句子里有「政策 / 规则 / 能不能退 / 怎么退 / 多久 / 流程…」
   且没有第一人称诉求，就**不认成要办退货**，交给知识库。
3. **worker 里再一道**：规则层只挡规则路径，模型也可能把「你们的退货政策是什么」
   听成「要退货」——写操作要两层都守。

代价是多问一句「您是要办还是问规则」；放过去的代价是替用户办了他没要求的事。
**代价不对称，所以宁可多问。**

回归测试：`test_asking_about_the_policy_does_not_file_a_return`。

**追问与陷阱**：

- 「为什么不用纯 LLM 判断意图？」——认操作类型 LLM 更强，但写操作不能只有一层；
  规则先挡明显问法，LLM 兜底，最后 worker 再校验。
- 「怎么证明修好了？」——那条回归测试 + 实际跑「退货政策」确认库里没有新增申请。

### Q26. 写操作怎么保证幂等？两个人同时审同一笔退货怎么办？

**面试官在考什么**：并发和幂等，尤其是「读后写」的竞态。

**参考答案**：

`review_return` 有两道闸：

```python
# 第一道：幂等。状态不是「待审核」就返回 already=True，一个字段都不动
if current["status"] != OPEN_RETURN_STATUS:
    return {"ok": True, "already": True, ...}

# 第二道：竞态。UPDATE 带上 AND status = ?
counts = db.transaction([
    ("UPDATE return_requests SET status = ? WHERE return_id = ? AND status = ?",
     (decision, current["return_id"], OPEN_RETURN_STATUS)),
    ("INSERT INTO return_reviews (...) VALUES (...)", (...)),
])
if counts[0] == 0:
    raise _LostRace   # 必须抛，不能 return
```

三个要点：

1. **幂等**：审过的再审一次返回 `already=True`，note / reviewer 一个字段都不动。
   人的结论是**证据**，不是可以被后一次点击改写的草稿。
2. **`AND status = ?`** 堵的是 check-then-act：`get_return` 读到「待审核」之后、
   UPDATE 执行之前，另一个审核人先把结论下了。少了它，后手会覆盖前手。
3. **必须 `raise` 而不是 `return`**：`return` 会正常提交，那条 review 痕迹就落下了，
   变成「有痕迹、但状态没被这次改动」——正是事务要防的东西。

**追问与陷阱**：

- 「MySQL 分支呢？」——`transaction` 里必须显式 `autocommit=False`，默认
  `autocommit=True` 会让「事务」变成假的，每条语句各自提交，中途失败留下半截，
  而且不报错。
- 「为什么不用数据库唯一约束？」——幂等键是 `(return_id)` + 状态，但业务上允许
  「已拒绝后重新申请」，所以不能简单加唯一约束；状态机 + 条件更新更准确。

### Q27. 哪些调用可以重试，哪些绝对不能？

**面试官在考什么**：重试的边界，尤其是写操作。

**参考答案**：

| 调用 | 能重试吗 | 理由 |
|---|---|---|
| 路由 LLM 分类 | 能 | 幂等分类，重试只多花钱 |
| 知识库检索 / 生成 | 能（有限） | 只读，重试无副作用 |
| 订单查询 | 能 | 只读 |
| 创建退货申请 | **不能盲目重试** | 写操作，重试可能产生重复申请 |
| 批准退货 | 能安全重试 | 幂等：已审过返回 already=True |

退货申请本身也有幂等设计：`BLOCKING_RETURN_STATUSES = {待审核, 已通过}`。
`已通过` 必须拦——漏了它，同一笔订单能再申请一次，结果是两笔退款；
`已拒绝` 必须放——拦了它，用户会撞上「你被拒绝过所以永远不能再申请」。

**追问与陷阱**：

- 「调用超时了，不知道写没写成功，怎么办？」——这是分布式系统的经典问题。当前项目
  没有幂等键；真上线要在请求里带 `idempotency_key`，服务端去重。这是上线清单里的
  一项。
- 「两个方向为什么各写一条测试？」——只写一条的话，另一种写法照样全绿。

### Q28. 为什么用 RAG，而不是微调，或者直接把文档塞进长上下文？

**面试官在考什么**：技术选型的判断力。

**参考答案**：

三个方案的取舍：

| 方案 | 适合 | 不适合这个项目的地方 |
|---|---|---|
| 长上下文 | 文档少、问题少、每次都要通读 | 184 个 chunk、17 篇文档，每轮都塞进去 token 成本高；而且「lost in the middle」，关键条文容易被淹没 |
| 微调 | 风格 / 格式 / 领域语感 | 知识会更新，政策一改就要重训；而且微调不能让模型「引用原文」，幻觉仍然存在 |
| RAG | 知识可更新、要引用、要拒答 | 检索质量是瓶颈，需要评测和调优 |

这个项目需要三件 RAG 才能给的东西：

1. **可引用**：答案带 `[1]` 引用，能溯源到具体 chunk；
2. **可拒答**：资料里没有就说没有，而不是编；
3. **可更新**：政策文档改了，重建索引即可，不用动模型。

**追问与陷阱**：

- 「长上下文模型越来越强，RAG 会不会被取代？」——会压缩 RAG 的适用场景，但
  「权限过滤、成本、引用溯源、知识更新」这几件事仍然需要检索层。长上下文不是
  免费午餐。
- 「为什么不微调一个客服模型？」——没有标注数据，而且政策会变；微调解决的是
  「怎么说」，不是「说什么」。

### Q29. 讲一下你的 RAG 全链路。

**面试官在考什么**：你能否把检索、融合、重排、生成、评测串成一条线。

**参考答案**：

```
用户问题
  │
  ├─ 问题向量化（BGE-M3，带精确重复缓存）
  │
  ├─ 向量检索 Top-20 ─┐
  │                    ├─ RRF 融合 → Top-5 → rerank → Top-3 → 生成（带 [1] 引用）
  └─ BM25 检索 Top-20 ─┘
```

具体参数：

- chunk 512 字、overlap 50；
- 两路各召回 20（约全库 184 个 chunk 的 11%）；
- RRF 融合，K=60，两路权重默认 1.0；
- 融合后截断到 TOP_K=5；
- rerank（BGE-Reranker-v2-m3）取 3；
- 生成时带引用，资料里没有就走「资料中没有相关内容」。

降级语义：

- **向量路失败必须抛**：评测要靠它暴露 embedding 故障；如果这里吞掉，评测会把
  每道题都印成「未命中」，把真正的故障盖住。
- **BM25 失败只降级**：退回纯向量。它是增强，不该拖垮检索。
- **rerank 三级降级**：硅基流动 API → 本地 CrossEncoder → 按向量分数截断。

**追问与陷阱**：

- 「为什么先融合再截断，不是先截断再融合？」——先融合才能让「BM25 命中、向量漏了」
  的那条挤进最终 Top-5；先截断会丢掉单路的名次信息。
- 「rerank 为什么放在融合之后？」——融合负责召回广度，rerank 负责精度；顺序反了
  会让 rerank 只看单路候选。

### Q30. Chunk 为什么是 512 / 50？

**面试官在考什么**：切分参数是不是有依据，还是抄的默认值。

**参考答案**：

512 字大约是中文法规条文 1~2 条的篇幅：

- 太小：一条完整的「第 X 条」被切成两半，检索到半句，生成时缺前提；
- 太大：一个 chunk 里混进多条不相关的规定，rerank 分数被稀释，引用也不精确；
- 50 的 overlap 是为了防止「跨界的定义」被切断——比如某条的适用条件在上一条末尾。

这个值是经验值，不是从评测里扫出来的。真要严谨，应该固定其他变量，扫
256 / 512 / 768 / 1024 × overlap 0 / 50 / 100，看 Recall@5 和忠实性。
当前项目的规模没做完整网格，面试时要如实说。

**追问与陷阱**：

- 「为什么不按语义切分？」——语义切分需要额外的模型调用和阈值，而且法规本身有
  天然的「第 X 条」边界；当前按结构切已经够用。语料换成网页/PDF 后才值得引入。
- 「overlap 会不会导致重复召回？」——会，RRF 里同一路的重复 chunk 会被挡掉
  （`seen` 集合），融合分不会翻倍。

### Q31. 为什么做混合检索？BM25 补了向量检索的什么？

**面试官在考什么**：你是否理解稀疏检索和稠密检索的互补性。

**参考答案**：

向量检索擅长语义相似，但对**精确术语、编号、专有名词**不敏感：
「七天无理由退货」和「7 日无理由退货」向量很近，但「第 25 条」「BGE-M3」
这种词，向量可能抓不住。

BM25 擅长精确词匹配和低频词，但不懂同义改写。

这个项目的语料是法规原文，用户会问「七天」「无理由」「第几条」这种精确表述，
所以两路互补：

- 向量路：改写型问题（「买错了能退吗」→ 退货政策）；
- BM25 路：术语型问题（「三包」「七日」「运费」）。

实测 152 题里，改写型 Recall@5 68.6%，术语型 98.0%——这也说明两路的强弱项不同。

**追问与陷阱**：

- 「BM25 为什么手写，不引 rank_bm25？」——公式只有几个符号，手写能让每一项可解释；
  引库会变成黑盒。代价是约 40 行代码和一份要维护的测试。
- 「中文分词怎么做的？」——jieba，转小写、丢掉纯标点/空白（避免它们被算进文档长度
  `dl`，把长度归一化带偏）。

### Q32. 为什么用 RRF，不用归一化后加权求和？

**面试官在考什么**：融合算法的原理，以及「分数不可比」这个坑。

**参考答案**：

两路分数**根本不是一个量纲**：

- 向量路是余弦相似度，通常挤在 0.3~0.7；
- BM25 路是没有上界的原始分，中文短块常见 0~20+。

想让它们相加，就得先归一化。min-max 归一化的问题是：**min 和 max 是本次查询的
候选集里算出来的**。某一题只召回一条时，那一条会被抬到 1.0；另一题召回二十条时
分布完全不同。两路的相对权重每一题都在漂移，还得再拍一个 α 去平衡。

RRF 绕开整件事：**只用名次，完全不管分数**。

```
RRF(d) = Σ_r w_r / (K + rank_r(d))     rank 从 1 开始
```

名次天然是同一个尺度，两路可以直接相加。K=60 是原论文（Cormack et al. 2009）的
经典值。

**追问与陷阱**：

- 「K 起什么作用？」——K 越大，靠前几条之间的差距被压得越平。但它**动不了两路的
  话语权**：任一路第 1 名恒为 `w/(K+1)`，和 K 无关。想改相对强弱只能调权重。
- 「为什么权重默认 1.0？」——在留出集上 `tune_rrf.py` 没调出稳定收益，更像拟合了
  调参那一半的噪声。保留参数是为了让「不加权」这个结论可复现。

### Q33. 两路各召回 20 条，为什么是 20？

**面试官在考什么**：召回宽度和融合效果的关系。

**参考答案**：

20 约等于全库 184 个 chunk 的 11%，给融合足够的候选。

混合检索的价值就在于把「BM25 命中、向量漏了」的那条挤进最终 Top-5。如果只召回
5 条，单路漏掉的那条根本没机会进入融合；召回太宽（比如 100）则融合和 rerank 的
成本上升，而且大量低相关候选会稀释名次信号。

这是经验值。严谨做法是扫 `VECTOR_RECALL_K` / `BM25_RECALL_K`，看 Recall@5 和
最终答案忠实性的曲线。

**追问与陷阱**：

- 「召回宽度和 TOP_K 的关系？」——召回是「进入融合的候选」，TOP_K 是「融合后交给
  rerank 的条数」，rerank 再取 3。三者不是一回事。
- 「为什么 rerank 只取 3？」——上下文预算。3 条 512 字的 chunk 已经约 1500 字，
  再多会挤占生成空间，而且边际收益递减。

### Q34. 为什么要 rerank？bi-encoder 和 cross-encoder 有什么区别？

**面试官在考什么**：检索链路里「召回」和「精排」的分工。

**参考答案**：

- **bi-encoder**（向量检索用的 BGE-M3）：问题 and 文档分别编码成向量，再算余弦。
  优点是快，可以离线建索引；缺点是两个文本在编码时**互相看不见**，细粒度的相关性
  判断弱。
- **cross-encoder**（BGE-Reranker-v2-m3）：把 `(query, document)` 拼在一起过模型，
  直接输出相关性分。优点是准；缺点是不能预计算，只能对少量候选在线打分。

所以典型分工是：**召回用 bi-encoder 求广，rerank 用 cross-encoder 求精**。
这里先融合取 5，再 rerank 取 3。

**追问与陷阱**：

- 「rerank 会不会很慢？」——会，但对 5 条候选打分是可控的；它比把 20 条都塞进
  生成上下文便宜。
- 「rerank 挂了怎么办？」——三级降级：API → 本地 CrossEncoder → 按向量分数截断。
  最后一级等于不做重排，但链路不断。
- 「为什么不用 LLM 做 rerank？」——可以，但成本和延迟高得多；cross-encoder 是
  专门的轻量模型，性价比更高。

---

### Q35. 混合检索为什么放在应用层，不让向量库做？

**面试官在考什么**：你对「后端契约」和「能力对称」的理解。

**参考答案**：

两个后端的原生能力不对等：

- Milvus 2.5+ 有内置 BM25 Function；
- Chroma 1.5 本地版完全没有（`SparseVectorIndexConfig(bm25=True)` 在本地直接报
  "Sparse vector indexing is not enabled in local"）。

如果图省事只在 Milvus 上用原生 BM25，两个后端的检索能力就不对称了——而项目承诺
「换后端只改配置，检索 / rerank / 评测的代码一行不动」。

所以在应用层实现 BM25，只依赖契约里的 `store.all_chunks()`，底下是 Chroma 还是
Milvus 它不知道也不关心。

**追问与陷阱**：

- 「应用层 BM25 的性能怎么办？」——全库 184 个 chunk，进程内索引 + 缓存完全够用；
  语料上百万时才需要真正的稀疏索引。
- 「缓存怎么失效？」——懒加载 + 进程内缓存，key 是 `store.count()`。已知盲区：
  同一个 source 被等量改写时 count 不变、缓存不刷新；UI 留了「重建索引」按钮。

### Q36. 你的 RAG 效果怎么证明？78.3% 的 Recall@5 算好吗？

**面试官在考什么**：评测方法论，以及你能否诚实面对指标。

**参考答案**：

三层评测：

1. **检索层**：152 题，Recall@5 = 119/152 = 78.3%，MRR = 0.533。
   拆分看：改写型 68.6%，术语型 98.0%。
2. **生成层**：40 条答案快照，忠实性 117/141 = 83.0%（逐条 85.8%）。
3. **拒答层**：10 条不可答题，弃答 9/10。

78.3% 不算高。要能说清它意味着什么：**大约每 5 个问题有 1 个，正确答案没进 Top-5**。
对这个语料（10 篇法规 + 7 篇示例，184 个 chunk）来说，主要短板是改写型问题
（68.6%），术语型已经 98%。

**追问与陷阱**：

- 「为什么不把指标刷高？」——评测集是基准，不能因为分数不好看就删题、改题。
  唯一允许重建评测集的情况是语料整体换掉。
- 「合成评测集和人工金标准有什么区别？」——合成集的「标准答案」是模型自己出题
  自己给的；金标准只有人点过头的条目才算数。前者覆盖广，后者可信度高。
- 「83% 忠实性怎么算的？」——qwen-plus 逐条判定答案是否被检索到的资料支持；
  它不是绝对真理，但能抓明显的编造。

### Q37. 资料里没有答案时，系统怎么处理？`KB_MIN_SCORE` 为什么失效了？

**面试官在考什么**：拒答机制，以及你是否敢暴露自己系统的弱点。

**参考答案**：

两层：

1. **检索层阈值** `KB_MIN_SCORE = 0.5`：低于它认为没有相关内容；
2. **生成层**：提示词要求「资料里没有就说没有」，并配了 10 条不可答题评测。

**但换语料后这个阈值基本失效了**。实测：

- 可答问题余弦 0.523~0.781；
- 不可答问题 0.431~0.707；
- 30 条可答题里 15 条落在 0.66 以下，10 条不可答题里 2 条在 0.66 以上。

两段基本糊在一起，**没有任何阈值能把它们分开**。原因是语料同质化了：十篇都是法律
中文，问任何法律问题都能捞到一段「看着挺像」的条文。

但这不构成把阈值调高的理由——调高会一次性误伤那 15 条可答题。取 0.5 依旧是
「宁可漏报」：它现在只挡得住 0.431 那一条，等于这道闸门在新语料上基本常开。

**追问与陷阱**：

- 「那怎么办？」——靠生成层的拒答提示词 + 评测兜底，而不是靠一个不可靠的阈值。
  更好的做法是训练/引入一个「可答性分类器」，或者用 rerank 分数而不是向量余弦。
- 「为什么不直接调高阈值？」——会误伤大量可答题；指标上「拒答率」好看，但实际
  可用性下降。这是典型的「指标优化错方向」。

### Q38. 知识库为什么要有「人审队列」？模型生成的答案为什么不能直接回写？

**面试官在考什么**：知识库自污染的机制，以及 human-in-the-loop 的设计。

**参考答案**：

模型判定「这个问题值得沉淀」后，**不直接写入向量库**，而是进待审核队列；
人批准后才渲染成 md、才进向量库。

原因：模型生成的答案一旦直接进向量库，下一轮检索就会把它当「权威资料」捞出来喂给
模型——错误会被放大并固化成看起来不容置疑的知识。这叫**知识库自污染**。

这和退货审核是同一个形状：**模型能判定，不能拍板**。
`ecom/orchestrator/tools/` 是模型能调到的，`ecom/orchestrator/admin/` 是只有人
能下结论的——用目录结构守边界，而不是靠代码评审。

**追问与陷阱**：

- 「人审会不会太慢？」——会，但知识库写入是低频操作，不是热路径。
- 「怎么防止审核的人也犯错？」——审核痕迹留痕（谁、什么时候、什么决定），
  可以回溯；当前没有双人复核。

### Q39. 增量索引、孤儿 chunk、同名文件——你踩过哪些坑？

**面试官在考什么**：真实工程细节，尤其是「不报错但结果错」的问题。

**参考答案**：

1. **孤儿 chunk**：`add_chunks` 的幂等只在文件还在盘上时成立。文件被删后，它的
   chunk 谁也动不了，却照样被召回——实测清掉 253 个。修法是 ingest 时对比文件集合，
   删除不在盘上的 source 的 chunk。
2. **同名文件**：chunk 的 `source` 取的是 basename，两个子目录下的同名文件会共用
   一个 source、互相覆盖而不报错。修法是加一道同名检测。
3. **缓存盲区**：BM25 索引按 `store.count()` 失效；同一个 source 被等量改写时
   count 不变，缓存不刷新。当前规模接受，UI 留了重建按钮。

这三个的共同点：**都不会抛异常，只会让检索结果悄悄变错**。

**追问与陷阱**：

- 「怎么发现孤儿 chunk 的？」——统计「库里的 chunk 数」和「磁盘上文件的 chunk 数」
  对不上，然后逐条比对 source。
- 「为什么不每次 ingest 都全量重建？」——全量重建需要重新调 embedding，成本和
  时间都高；增量 + 清理是更实际的做法。

### Q40. Chroma 和 Milvus 怎么选？「换后端只改配置」这个契约怎么保证？

**面试官在考什么**：抽象层设计，以及契约测试。

**参考答案**：

- **Chroma**：默认，嵌入式，零外部依赖，适合「clone 下来就能跑」；
- **Milvus**：需要 Docker，适合更大规模 / 生产。

两个后端实现同一套 `VectorStore` 契约：`add_chunks / search / count / all_chunks /
delete / drop`。切换只改 `VECTOR_BACKEND` 环境变量。

保证契约的方式：

- 契约测试对两个后端跑同一组用例；
- 检索、rerank、评测的代码只依赖 `Hit` 契约，不依赖后端细节；
- 混合检索放在应用层（Q35），避免后端能力不对称。

**追问与陷阱**：

- 「Milvus 版本错位怎么办？」——本机服务端 v2.5.5，客户端 pin 在 `>=2.6,<3`，
  实测这几个接口能用，但没有保证。真要长期用，服务端该换到 2.6.x 对齐。
- 「为什么不直接用 Milvus 的 BM25？」——会让 Chroma 和 Milvus 的检索能力不对称，
  违背「换后端只改配置」的契约。

## 五、数据分析 Agent 与沙箱

### Q41. 数据分析为什么做成 Agent，而订单查询不是？

**面试官在考什么**：Agent 和 Tool 的判据。

**参考答案**：

判据只有一条：**有没有「看一眼结果再决定下一步」的循环。**

- **订单查询**：输入订单号，输出状态。中间没有「看看结果再改改」。给它套 agent
  壳子，只会多一层提示词、多一次模型调用，换来一个更不确定的输出。所以它是
  `tools/order_tools.py` 里的纯函数。
- **数据分析**：生成代码 → 执行 → 看报错 → 改代码 → 再执行。这个循环就是它的
  全部价值。所以它是 `ecom/analytics/` 里的图。

**把工具包装成 agent 是负收益。**

**追问与陷阱**：

- 「实时销售看板为什么不是 agent？」——那是查库，不是 agent。
- 「数据分析的循环会不会无限跑？」——有上限：执行报错最多重写 3 次
  （`MAX_EXEC_RETRY`），审查最多 2 轮（`MAX_REVIEW_ROUNDS`）。

---

### Q42. 数据分析的图长什么样？纠错循环怎么设计？

**面试官在考什么**：你是否理解多节点图的控制流，而不是「一个大 prompt」。

**参考答案**：

```
load_data → classify → analyst → execute ─┬─ 有错 → self_correct → execute
                                          ├─ 成功且需审查 → reviewer ─┬─ 通过 → report
                                          │                            └─ 不通过 → self_correct
                                          └─ 成功且不需审查 → report
```

两个纠错来源（执行报错 / 审查不通过）都走同一条边回到 `execute`，回到 execute 后
再由 `after_execute` 依据当前状态重新决策，所以不需要记住来源。

参数：

- `MAX_EXEC_RETRY = 3`；
- `MAX_REVIEW_ROUNDS = 2`（首审 + 复审）；
- 简单问题不审查，省一次模型调用。

**追问与陷阱**：

- 「为什么审查用另一个模型？」——生成用 DeepSeek，审查用 Qwen，避免同一个模型
  自己审自己。这是「用不同视角降低盲区」的朴素做法。
- 「审查不通过但额度用尽怎么办？」——带风险出报告，而不是无限重试。

---

### Q43. 为什么数据分析要走子进程，而不是进程内调用？

**面试官在考什么**：进程边界的作用，尤其是「超时」的真实语义。

**参考答案**：

三个理由，第一个最要紧：

1. **它执行模型生成的代码。** 沙箱（AST 白名单 + 受限 builtins）不做超时、也不做
   进程隔离，`while True: pass` 拦不住。`subprocess.run(timeout=...)` 到点是**真杀**；
   进程内那个「超时」只是不再等它。
2. **它可能跑几分钟。** 生成 → 执行 → 报错 → 改 → 再执行，循环几轮。进程内跑意味着
   这几分钟里 supervisor 那条线程被占着、还占着内存。
3. **崩了炸不到 supervisor。**

界面（`app.py`）也走这条边界，不让界面成为例外。

**追问与陷阱**：

- 「子进程启动不慢吗？」——慢，但数据分析本来就不是热路径；订单和知识库才是。
- 「为什么不把所有 worker 都放子进程？」——知识库是热路径，多付一次解释器启动 +
  chromadb 初始化不划算。
- 「子进程超时和 worker 超时的关系？」——子进程超时设成比 worker 超时短 5 秒
  （175s vs 180s），让子进程自己的超时先触发，否则是父进程单方面放弃。

---

### Q44. 你的沙箱到底做了什么？没做什么？

**面试官在考什么**：安全边界是否诚实，尤其是「AST 白名单不是强隔离」。

**参考答案**：

**做了三件事**：

1. **AST 白名单**：只允许 import `pandas / numpy / math / matplotlib / datetime /
   statistics / json / re`；显式禁掉 `open / eval / exec / compile / __import__ /
   getattr / setattr ...`；禁止 dunder 属性（挡 `__class__` 逃逸链）；禁止
   `to_csv / to_excel / to_sql` 等落盘方法。
2. **受限 builtins**：exec 时只注入白名单 builtins，不注入完整的那一份。
3. **非 root 用户**：镜像里是 `USER app`。

**没做**：

- 没有 rlimits（CPU、内存、文件大小、进程数都无限）；
- 没有独立低权用户、没有网络隔离、没有文件系统隔离；
- `run_code()` 自己不设超时，真正的超时在父进程的 `subprocess.run(timeout=...)`。

所以准确说法是：**它挡得住模型写错，挡不住有人故意攻击。** 不要把它说成「安全沙箱」。

**追问与陷阱**：

- 「为什么不加 `resource.setrlimit`？」——可以加，但和容器层面的
  `mem_limit / cpus / pids_limit` 有重叠；当前优先级是先别暴露出去。
- 「AST 白名单能绕过吗？」——能。它是在同一个进程地址空间里做的检查，逃逸一次就
  到底。真正的隔离要独立容器 / gVisor / 只读挂载 / 无网络。

---

### Q45. 提示词注入导致代码执行，这条链路怎么防？

**面试官在考什么**：你是否理解「用户输入 → 模型生成代码 → 执行」的完整风险。

**参考答案**：

完整链路：

```
用户问题（不可信）
  → app.py 数据分析视图（无鉴权）
  → workers/analytics.py 子进程
  → analyst.py 的提示词里原样拼入用户问题
  → 模型生成 pandas 代码
  → sandbox.py 执行
```

**准确地说**：用户的提问原文会进到「请写一段 pandas 代码」的提示词里，生成的代码
会被执行。一句精心构造的提问，可以改变模型写出什么样的代码。

三层防御，按性价比排：

1. **别暴露出去**：app 绑 `127.0.0.1`，不绑 `0.0.0.0`。投入最小、收益最大。
2. **界面要登录**：这是身份体系的直接推论。
3. **执行前的静态校验要面对「提示词注入」这个前提**：现在的 AST 白名单是按
   「模型可能写错」设计的，不是按「有人故意让模型写出攻击代码」设计的。

**追问与陷阱**：

- 「把用户问题做转义行不行？」——不够。提示词注入不是 HTML 转义能解决的；
  真正的边界是沙箱和权限。
- 「为什么不干脆不让模型生成代码？」——那就失去了数据分析能力；正确做法是
  隔离执行，而不是因噎废食。

### Q46. 数据集口径怎么保证一致？为什么要 `NOTES.md` 一份文件、三处注入？

**面试官在考什么**：单一真相源，以及「文档也是代码」的意识。

**参考答案**：

DataCo 数据暴露了一个关键问题：**一行不等于一笔订单**。一行是一个商品项，
一笔订单平均 2.8 行。直接 `len(df)` 当订单数会多算近三倍，而且**不报任何错**。

口径写在 `data/analytics/datasets/dataco/NOTES.md`：

- 订单数按 `Order Id` 去重；
- `Sale` 和 `Order Item Total` 差约 10%（未打折 vs 折后），默认取前者，不许混用。

**一次读取、三处注入**：analyst / self_corrector / reviewer 读的是同一个字符串。
原来是两处各写一遍，没有任何机制保证一致——换数据集时只改一处，审查员会拿旧口径
去否掉正确的代码。

这和 `utils/ids.py`、`utils/entities.py` 是同一条原则：**能靠「只有一份」消掉的分叉，
就不该指望靠注释去对齐。**

**追问与陷阱**：

- 「为什么把口径放在文件里，不放在提示词里？」——提示词是代码的一部分，改口径要
  改代码；文件是数据集的属性，换数据集时跟着目录走。
- 「怎么防止 NOTES.md 写错？」——评测真值用标准库 `csv` 独立算，不用 pandas；
  `tests/analytics/test_eval_truth.py` 用 AST 守白名单，防止「拿被考察的实现考察自己」。

### Q47. 中文图表在容器里全是豆腐块——你怎么发现的？

**面试官在考什么**：真实排障能力，尤其是「所有检查都绿但结果是错的」。

**参考答案**：

症状：子进程 exit 0、`chart_generated: true`、报告文字完全正常、日志里两行信息都在
——**每一项检查都是绿的，只有把 PNG 打开看才知道五个地区名全是方框**。

原因：`python:3.11-slim` 里没有 CJK 字体；`sandbox.py` 写死了
`["Microsoft YaHei"]`，matplotlib 找不到就**打一行 warning，然后悄悄退回 DejaVu Sans**。

修法必须两边一起改：

1. `sandbox.py` 给出跨平台候选顺序（Windows 雅黑优先，Linux 落到 Noto）；
2. `Dockerfile` 安装 `fonts-noto-cjk`（约 90MB）。

只改一边等于没改：列表里写着但系统上没有，等于没写。

验证方式也只能是把图画出来看：容器内五个地区名、标题、轴标签全部正常，stderr 的
`findfont` warning 消失。

**追问与陷阱**：

- 「为什么不装字体，改用英文标签？」——业务要中文，而且英文标签会丢信息。
- 「这个坑教了什么？」——「跑起来了」和「跑对了」之间的距离，靠日志和退出码发现不了。

## 六、会话与记忆

### Q48. 多轮会话怎么存的？

**面试官在考什么**：会话模型的选型，以及「为什么不用现成的」。

**参考答案**：

`data/orchestrator/sessions.db`，自己开 SQLite，三张表：

```sql
sessions(session_id PK, created_at, updated_at)
messages(id PK, session_id, role, content, created_at)
memories(id PK, session_id, summary, keywords, embedding BLOB,
         through_message_id, created_at,
         UNIQUE(session_id, through_message_id))
```

为什么和订单库分开：

- `orders.sqlite` 是「灌一次就不动」的派生数据，删了能重灌；
- `sessions.db` 是「每天都在长」的运行数据，里面是用户说过的话。
- 两者的备份 / 清理策略不该共用。

并发：WAL + `busy_timeout=5000` + 进程内 `threading.Lock` 保护写。

**追问与陷阱**：

- 「为什么不用 Redis？」——当前是单机演示；多副本部署时 SQLite 直接堵死横向扩展，
  那时必须换。
- 「为什么不用 ORM？」——SQL 很简单，薄适配器足够；ORM 会引入一层不必要的抽象。

### Q49. 为什么不复用知识库那边的 `SqliteSaver`？

**面试官在考什么**：你是否理解 checkpointer 的语义，而不是「有现成的就用」。

**参考答案**：

三条理由：

1. **`chat_history` 在 supervisor 里是「节点输入」，不是「图状态」。** 它由
   `make_initial_state` 塞进去，图从不往回写（没有 reducer、没有累积节点）。
   要让 checkpointer 接管，就得往图里加「累积历史」的逻辑——那是改图的语义，
   不是加一个存储。
2. **会撞上 `operator.add` 的坑**：给 `chat_history` 加 reducer 之后，每次传入的
   初始值都会被 append 而不是替换，历史里凭空多出重复轮次，且不报错。
3. **两个图不是同一个图。** `ask.py` 存的是知识库图的状态，supervisor 图是另一个
   对象；共用一张 `checkpoints` 表会让两种状态混在一个 `thread_id` 空间里。

对面的好处也说清：统一成一套的好处是「会话」在整个项目里只有一个答案，新人只学
一次。代价是上面三条。

**什么条件下该反过来选**：如果 supervisor 以后要在图内部做需要记忆的决策
（比如「这个用户上一轮已经在等人工了」），那就是「历史作为状态」，checkpointer
才是对的。

**追问与陷阱**：

- 「那为什么不干脆把历史放进 state？」——当前不需要图内决策；放进去会引入同步问题，
  多一条要与 `chat_history` 长期保持一致的平行管道。
- 「两个图的 `thread_id` 空间混了会怎样？」——同一个 id 下两种状态互相覆盖，
  症状是会话错乱，且不报错。

### Q50. `HISTORY_TURNS`、`SESSION_TTL_DAYS`、`MEMORY_TOP_K` 为什么不能合并成一个「留多少」？

**面试官在考什么**：配置项背后的动机是否清晰。

**参考答案**：

| 旋钮 | 管什么 | 性质 |
|---|---|---|
| `HISTORY_TURNS = 6` | 喂给模型多少原文 | **成本** |
| `SESSION_TTL_DAYS = 30` | 留多久 | **合规** |
| `MEMORY_TOP_K = 3` | 带几条记忆进 prompt | **成本（另一条通道）** |

它们看起来都可以叫「留多少」，但改动的动机完全不同。合并成一个开关，会在有人想
省钱的时候顺手把合规期限也改掉。

`HISTORY_TURNS` 和 `MEMORY_TOP_K` 同属成本，但是两条独立通道：

- 前者是「最近几轮的原文」，精确但贵；
- 后者是「更早那一段的摘要」，便宜但有损。

两者不是同一种东西的多少，所以不给它们一个共同的倍率。

**追问与陷阱**：

- 「`history()` 取的是最近还是最早？」——`ORDER BY id DESC LIMIT n` 再 `reversed`，
  取最近 N 轮。截错方向不会报错，只会让模型拿到很旧的上文，有专门测试钉着。
- 「为什么 TTL 是 30 天？」——无主数据不该无限期留着；30 天是演示级的合规默认值。

### Q51. 会话内长期记忆怎么做的？为什么蒸馏放在离线 CLI？

**面试官在考什么**：记忆系统的设计，尤其是「不在请求路径上做重活」。

**参考答案**：

`history()` 只带最近 6 轮，聊到第 20 轮时，第 3 轮说过的订单号、诉求、结论都已经
滑出窗口。这一层把**滑出窗口的那一段**压成一条摘要存进 `memories` 表，需要时
按语义召回，拼在真实历史前面。

关键设计：

1. **存「可执行的事实」，不是关键词**：摘要写「用户要为订单 52644 退货，但还没确认」，
   而不是「退货、订单」。关键词只能告诉你聊过什么话题，不能告诉你结论是什么。
2. **按需召回，不是每轮全灌**：先按语义挑最相关的 `MEMORY_TOP_K` 条；池子为空时
   **一次 embedding 都不调**。
3. **蒸馏只在 CLI**：`python -m ecom.orchestrator.cli.memory distill`。放在问答路径上
   意味着用户每问一句都可能多一次模型调用，而且不可控（第一次问就触发全量蒸馏）。
4. **代价说清：记忆不是实时的**，要有人跑 `distill` 才更新，所以外挂 cron。

**追问与陷阱**：

- 「为什么不设相似度阈值？」——池子是这个会话自己的、条数天然少，加一个没实测过的
  阈值只会静默丢掉记忆。
- 「换 embedding 模型怎么办？」——已存向量会失效，`_cosine` 遇到长度对不上返回 0.0
  （排到最后），但没有版本号落点，也就没有自动重算。这是已知限制。
- 「记忆能用于写操作吗？」——不能。摘要里的订单号是模型写的，拿它去提交退货等于
  替用户对一笔可能错的订单办事。

### Q52. 蒸馏的幂等和水位线怎么做的？

**面试官在考什么**：独立进程并发下的幂等，以及「锁不是万能的」。

**参考答案**：

`session.py` 的 `_lock` 是**进程内**的，而蒸馏是独立进程的 CLI。cron 撞上手动执行时，
两边会读到同一个水位线、蒸馏同一批消息、各插一条。

解法不是加跨进程锁，而是**让数据库保证幂等**：

```sql
UNIQUE(session_id, through_message_id)
```

配合 `INSERT OR IGNORE`，第二次成为 no-op。

`through_message_id` 是水位线：记住「已经蒸馏到哪条消息」，而不是「是哪条消息」。

两个边界方向相反，缺一条就出错：

- **下界** `id > 已蒸馏到的最大 id`：蒸馏过的不再重复喂给模型；
- **上界** `id <= 会话最大 id - 窗口宽度`：还在窗口里的不蒸馏（下一轮会由
  `history()` 原样喂给模型，再压一遍是重复付费）。

**追问与陷阱**：

- 「模型没给出可用摘要怎么办？」——不写、水位线不推进；写一条空记忆会永远占着
  水位线，把这段对话彻底吞掉。
- 「embedding 失败怎么办？」——抛出去。绝不写一条没有向量的记忆，那条约等于
  「存在但永远选不上」，`list` 里看得到它，用户会以为它在起作用。

### Q53. `session_id` 为什么是凭证而不是账号？由此推出哪些设计？

**面试官在考什么**：身份边界，以及「没做的能力」怎么用测试钉住。

**参考答案**：

`_guess_customer` 意味着「客户」是从话里猜出来的、未认证的。所以拿到 `session_id`
就能读到这个会话的全部历史。**它不是账号。**

三个推论，全是有意的：

1. **默认 30 天过期**：无主数据不该无限期留着。
2. **界面不把会话号放进 URL**：它是 bearer token，进了 URL 就会进浏览器历史、
   代理日志、Referer 头。代价是新开一个标签页 = 新的一段对话。
3. **侧边栏只显示前 12 位**：侧边栏是最容易被截图发出去的地方。

**没做的能力写成测试钉住**：`test_a_new_browser_session_starts_a_new_conversation`。
因为最容易被下一个人当成 bug 顺手补上，而补法（`st.query_params`）正好是不该做的。

**追问与陷阱**：

- 「为什么不直接做个登录？」——那是另一个项目的量级，而且会毁掉「clone 下来点开
  就能用」的定位。正确说法是「我知道这里没有身份，也知道补它要动什么」。
- 「删除会话时记忆怎么办？」——级联删除。删了会话却留着摘要，是隐私上的假动作。

### Q54. 为什么不做用户画像？

**面试官在考什么**：你能否区分「会话内记忆」和「用户级画像」。

**参考答案**：

跨会话的用户级记忆需要「这个人是谁」稳定可信，而这里客户身份是从话里猜的
（`_guess_customer`），没有登录态。做出来的画像会挂在错误的身份上——**先有身份，
才谈得上画像**。这是顺序问题，不是工作量问题。

`memories` 表按 `session_id` 键，跨会话一条都召不回来。它不是「开始做画像」的先例。

**追问与陷阱**：

- 「那如果加了登录呢？」——可以谈画像，但还要解决：谁有权读写、保留多久、
  用户能不能删除、跨设备怎么合并。这些是产品/合规问题，不是技术问题。
- 「为什么删会话要连记忆一起删？」——否则用户以为删干净了，摘要还躺在库里。

### Q55. 会话为什么不自动清理，要外挂 cron？

**面试官在考什么**：你是否理解「读操作产生写副作用」的代价。

**参考答案**：

过期只在两处触发：

1. 进程启动时调一次 `purge()`；
2. CLI 显式调用。

**不做**懒加载式的「读的时候顺手删」——那会让读操作产生写副作用，出问题时极难定位。

代价：长驻进程不会自我清理，需要外挂：

```bash
17 4 * * * cd /path/to/ecom_cs && uv run python -m ecom.orchestrator.cli.session purge
```

**追问与陷阱**：

- 「为什么不放在请求路径上顺手删？」——请求路径应该只做业务；清理失败不该影响问答，
  清理成功也不该让延迟抖动。
- 「多个副本怎么办？」——各自清各自的；当前是单机。

## 七、数据、一致性与事务

### Q56. 为什么默认 SQLite，不直接上 MySQL？

**面试官在考什么**：默认路径的取舍，而不是「哪个数据库更高级」。

**参考答案**：

默认 SQLite 的理由不是「SQLite 更好」，而是**默认路径必须零外部依赖**，否则
「别人拿到能跑」就是空话。

但代码不能被 SQLite 惯坏：

- SQL 全部用 `?` 占位符写，MySQL 分支在 `_translate` 里统一换成 `%s`；
- DDL 用两边都吃的写法（`VARCHAR` 做主键而不是 `TEXT`，不用 `AUTOINCREMENT`）。

MySQL 路径已经写好了（`ORDER_DB_DSN`），只是本仓库没拿真库跑过。

**追问与陷阱**：

- 「SQLite 能撑多少并发？」——同一时刻只有一个写者。对这个体量够用，但它把
  「横向扩到两个副本」这条路直接堵死了。
- 「什么时候换？」——有真实并发写入 / 多副本需求时。换库和改 schema 不要同时做，
  否则出问题分不清是哪一步。

### Q57. 退货审核为什么用新表，不给 `return_requests` 加列？

**面试官在考什么**：你是否会为了「看起来规范」而引入不必要的机制。

**参考答案**：

`Database.init_schema()` 只做 `CREATE TABLE IF NOT EXISTS`，已经存在的库不会自动
多出新列。给 `return_requests` 加三个列就得写迁移（SQLite `PRAGMA table_info` +
MySQL `information_schema`），那会是这个仓库的第一个 schema 演进机制。

选新表 `return_reviews` 的理由：

1. **能不引入机制就不引入机制**。这个项目里「删库重灌」一直是免费的（全是派生数据），
   为了加三列而引入第一个迁移机制，收益和分量不匹配。
2. **这个理由今天不成立，但下个月就成立**。一旦这套被演示过，`return_requests` 里
   就会有人下的结论；到那时再想加列，重灌库就等于抹掉人的决定。

**追问与陷阱**：

- 「那什么时候必须引入迁移？」——当 `return_reviews` 里出现第一个「人下的结论」时。
  这是一个明确的判据，不是「以后再说」。
- 「新表会不会让查询变复杂？」——会多一个 LEFT JOIN，但列表页和详情页共用同一条
  SQL，不会出现两条代码路径读同一件事。

### Q58. 「批准退货」到底做了什么？为什么不做退款？

**面试官在考什么**：业务边界和「不假装」的工程伦理。

**参考答案**：

只做两件事，在同一个事务里：

1. `return_requests.status` 从「待审核」改成「已通过 / 已拒绝」；
2. 往 `return_reviews` 插一行：谁、什么时候、什么决定、什么备注。

**不做**：

- **不执行退款**。没有支付网关可调，假装退款比不做更坏。
- **不改 `orders.status`**。退货通过 ≠ 订单状态变化；而且那个字段是 DataCo 的原值，
  改它就是在编造数据。

**追问与陷阱**：

- 「用户以为退款了怎么办？」——答复里明确说「只登记决定，不执行退款」；界面也要
  写清楚。当前 `message` 里就带这句话。
- 「为什么不接支付网关？」——那是另一个系统的集成，且涉及真实资金；这个项目的
  定位是架构演示，不是支付产品。

### Q59. 换成真实数据后暴露了哪三个问题？

**面试官在考什么**：真实数据和手写数据的差距，以及「不报错但算错」。

**参考答案**：

1. **一行不等于一笔订单**：DataCo 一行是一个商品项，一笔订单平均 2.8 行。
   `len(df)` 当订单数会多算近三倍，且不报任何错。口径写进 `NOTES.md`。
2. **公开数据里没有承运商、没有运单号、连发货地都没有**：`Order City` 是目的地，
   不是发货地。这三列一律留空，回答里「有的才说」。**不合成假值**——补一个假值会让
   下游「不许引用不存在的事实」那道检查一起失效。
3. **订单号是 1~5 位，不是 6 位以上**：`\b\d{6,}\b` 对真实订单号一笔都命中不了，
   却会把 6 位以上的发票号路由成「查订单」。两处各写一份，改一处才发现另一处。

第三个问题的修法不是「写进注释互相点名」，而是**让它只剩一份**：`utils/ids.py`。

**追问与陷阱**：

- 「为什么不把订单号门槛放宽到 4 位？」——「2025 年买的」里的 2025 会被认成订单号。
  认错一个订单号比认不出更糟。
- 「为什么不补承运商假值？」——演示效果确实吃亏，但数据里没有的东西一旦被补上，
  下游的事实检查就失效了。

### Q60. 你的测试策略是什么？为什么一条测试都不联网？

**面试官在考什么**：测试的可靠性，以及「不联网」这条规矩的代价。

**参考答案**：

**717 条 / 715 passed / 2 skipped**（宿主 `.venv`，2026-10-30 实测）。所有模型调用都用

### Q62. CI 里踩过什么坑？

**面试官在考什么**：你是否真的让 CI 跑起来过，而不是只写了个 YAML。

**参考答案**：

两个「本地永远看不出来」的坑：

1. **`python-version-file` 这个输入名不存在**。官方 action.yml 里只有
   `python-version` 和 `version-file`（管 uv 自己的版本）。名字写错的后果特别隐蔽：
   action 只打一条 warning 就**忽略它**，workflow 照样绿——看着像钉住了版本，
   实际什么都没做。
2. **`astral-sh/setup-uv` 没有 `v10` 这个大版本 tag**。它的大版本 tag 只发到 v7，
   之后只发 `v10.0.1` / `v10.3.0` 这种精确版本。钉 `@v10` 会让 job 在
   "Set up job" 阶段就红，报 `unable to find version v10`，连 checkout 都跑不到。

最终写法：`actions/checkout@v7`（大版本） + `astral-sh/setup-uv@v10.3.0`（精确版本），
`uv sync --all-extras --frozen`；2026-10-11 那次绿跑是 `517 passed / 3 skipped`。

**追问与陷阱**：

- 「为什么 `--frozen`？」——锁文件漂移是那种「本机永远是好的」的问题；`--frozen`
  让它在装依赖这一步就红。
- 「为什么 `--all-extras`？」——`ui` / `api` 的测试靠 `importorskip` 决定跳不跳；
  少装一个 extra 不会报错，只会静悄悄少跑一批。

### Q63. 可观测你怎么做的？最重要的指标是什么？

**面试官在考什么**：你是否能从一堆指标里挑出真正有信息量的那个。

**参考答案**：

三个观测面：

1. **日志**（`logs/<date>.log`）：给人扫的；
2. **trace**（`logs/requests.jsonl`）：一行一条请求，机器可读。记录的是**事实**
   （路由来源、每个 worker 的 ok / 耗时 / token、最终决策），不是结论；
3. **`GET /trace`**：把最近若干条请求的决策链摊出来。

最重要的指标是 **`router_source` 的分布**（llm / rule / fallback）。
**rule / fallback 的比例一涨，说明 LLM 那层在坏**——这是整套系统里唯一一个能在用户
投诉之前发现路由退化的信号。

往后才是：每请求 token 成本、每 worker 的 p95 耗时、`insufficient` 比例。

**追问与陷阱**：

- 「为什么不是 CPU / 内存？」——那些和业务质量无关。LLM 系统的两个独有信号是
  **成本漂移**和**质量漂移**，router_source 属于后者。
- 「为什么 trace 记事实不记结论？」——口径变一次不用重跑历史数据；「这次成功了吗」
  由查询方判断。

### Q64. 讲一个你印象最深的 bug。

**面试官在考什么**：排障方法论，以及你能否把「症状和原因隔得很远」讲清楚。

**参考答案**（挑一个讲，推荐「重试放大」或「reducer 跨轮累加」）：

**重试放大**：

- 症状：路由正常是零点几秒，某次网络不通时拖了 25 秒才落到规则兜底。
- 原因：openai 客户端默认 2 次重试 + 外面 3 次重试，两层是乘法；
  单次 8 秒 × 3 = 24 秒，外面的 20 秒总预算失效。
- 修法：`max_retries=0`，重试权收回代码；加总预算。
- 教训：**重试只能有一层**，而且这一层要知道「这次调用值不值得重试」。

**或者 reducer 跨轮累加**：

- 症状：第二轮汇总把第一轮结论又汇总一遍，同一段话说两遍，只在第二轮出现。
- 原因：`results: Annotated[list, operator.add]` 跨轮只增不减，写 `[]` 等于没写。
- 修法：`stamp_round` + `round_results`。
- 教训：**理解 reducer 在做什么，不能靠「赋值清空」绕开。**

**追问与陷阱**：

- 「怎么定位的？」——先看 trace 的耗时分布，发现路由环节异常；再看 SDK 文档确认
  默认重试；最后用假 LLM 复现。
- 「怎么防回归？」——加测试 + 把「总预算」写进配置注释。

### Q65. 这个项目里「单一真相源」体现在哪些地方？

**面试官在考什么**：你是否理解「两处各写一份、分叉不报错」这类问题。

**参考答案**：

四个例子：

1. **`ecom/settings.py`**：全项目唯一读 `.env`、唯一算项目根。三个子系统原来各算一次
   路径，搬进子目录后全都还能算出结果、只是算错——不抛异常。
2. **`utils/ids.py`**：订单号形状只有一份，router 和 order worker 都 import。
3. **`utils/entities.py`**：跨轮指代判定只有一份，router 规则层和 order worker 共用。
4. **`NOTES.md`**：数据集口径一份文件、一次读取、三处注入（analyst / self_corrector /
   reviewer）。

共同点：**能靠「只有一份」消掉的分叉，就不该指望靠注释去对齐。** 注释不会在你改
另一边的时候变红。

**追问与陷阱**：

- 「为什么不用 lint 规则禁止重复？」——lint 只能查语法模式，查不了「两个常量含义
  相同但名字不同」。单一真相源是设计问题。
- 「路径只算一次怎么测？」——`tests/test_package_layout.py` 里有一条断言把三个
  settings 模块的根路径钉死一致。

### Q66. 和 Dify / FastGPT / RAGFlow / Coze 比，你的项目有什么优势？

**面试官在考什么**：你是否了解市场，以及能否诚实定位。

**参考答案**：

先给结论：**它们解决的是「快速搭一个 AI 应用」，我解决的是「把多源答案的编排、
失败语义和可评测性做透」。** 不是同一个赛道。

| 平台 | 强项 | 我这个项目的差异 |
|---|---|---|
| **Dify** | 全栈 LLM 应用平台，可视化工作流、多模型、LLMOps、企业权限 | 我没有平台化能力；但我把「路由三层兜底、`ok` vs `insufficient`、有界回环、汇总不引入新事实」这些**失败语义**写成了代码和测试，平台里通常是黑盒 |
| **FastGPT** | 轻量知识库问答，中文 RAG 好，OpenAI 兼容 API | 我的 RAG 链路（混合检索 + RRF + rerank + 评测）是可拆开讲清的；但我没有它的产品化程度和多租户 |
| **RAGFlow** | DeepDOC 复杂文档解析（PDF/表格/扫描件）业界强，引用溯源 | 我的语料是法规纯文本，解析不是重点；复杂文档场景我不会硬碰 |
| **Coze** | 零代码、插件生态、一键发布 | 我是代码级可控，能讲清每一层为什么；但 Coze 的上手速度和渠道能力我完全没有 |
| **商用客服**（Zendesk / 阿里云智能客服等） | 全渠道、工单、CRM、人工坐席、SLA | 我是架构原型；没有身份、工单、支付、坐席这些产品能力 |

我的真实优势是三条：

1. **可解释**：每个决策都有 trace（router_source、每个 worker 的 ok / 耗时 / token）；
2. **可评测**：检索 Recall@5 / MRR、答案忠实性、拒答率，指标和语料都在仓库里；
3. **边界清晰**：哪些不做、为什么不做、什么条件下会改，写在文档里而不是藏着。

**追问与陷阱**：

- 「那企业为什么不直接用 Dify？」——大多数场景应该用。我的项目不是要替代它，
  而是证明我能理解并实现平台背后的那些机制。
- 「你这些能力平台不能配吗？」——部分能（比如工作流、知识库），但「失败语义、
  有界回环、单一真相源、评测驱动」通常要改平台源码或写插件；我的价值是能讲清
  为什么这么设计。

### Q67. 和「直接调大模型 API + 写好 prompt」比，你这个项目是不是过度设计？

**面试官在考什么**：你能否为一个复杂架构辩护，同时也承认它可能过度。

**参考答案**：

不是所有客服都需要这套架构。判据是**答案来源的数量和失败代价**：

- 如果只有 FAQ，一个 RAG + 一个 prompt 就够了；
- 如果答案跨文档、数据库、实时计算三类来源，而且写操作有真实后果（退货、退款），
  就需要路由、契约、失败语义、人工审核。

这个项目的复杂度是跟着**失败模式的数量**走的：

- 检索失败 → `insufficient`；
- 查库失败 → `ok=False`；
- 代码执行失败 → 重试 / 纠错；
- 写操作 → 幂等 + 人工拍板；
- 模型整个挂掉 → 三层路由兜底。

如果把这些都塞进一个大 prompt，系统在正常情况下能跑，但**出问题时你不知道该信谁**。

**追问与陷阱**：

- 「那你怎么证明复杂度是必要的？」——用真实故障路径证明：dashscope 不通时，
  路由 8 秒退规则、知识库超时、订单照常答、总耗时 17.6 秒而不是 180 秒。
  单体方案在这种情况会整体失败。
- 「哪些复杂度可以砍？」——如果只做只读 FAQ，数据分析 worker、人工审核、双后端
  都可以砍；但身份和可观测不能砍。

### Q68. 你的项目有什么明显劣势？什么场景不适合用？

**面试官在考什么**：自我认知。只会说优势的人不可信。

**参考答案**：

**劣势**：

1. **没有身份主体**：客户号是猜的，`session_id` 是 bearer token，admin 是单口令。
2. **没有多租户**：`tenant_id` 不贯穿检索 / 数据库 / 工具层，不能给多家企业共用。
3. **沙箱不是强隔离**：挡模型写错，挡不住故意攻击。
4. **SQLite 单写者**：不能横向扩副本。
5. **没有限流 / 预算 / 熔断**：突发流量会打空额度。
6. **没有工单 / CRM / 支付 / 全渠道**：它不是完整客服产品。
7. **记忆不是实时的**：要跑 distill。
8. **RAG 指标一般**：Recall@5 78.3%，改写型只有 68.6%。

**不适合的场景**：

- 需要合规审计、真实资金操作的生产客服；
- 复杂 PDF / 扫描件为主的文档问答（RAGFlow 更合适）；
- 需要零代码配置、快速上线的业务团队（Dify / Coze 更合适）；
- 高并发、多租户 SaaS。

**追问与陷阱**：

- 「那你的项目还有什么价值？」——它证明我能把多 Agent 编排、RAG、评测、失败语义、
  上线差距讲清楚；这些能力换个业务也能用。
- 「你会先补哪个？」——身份。它是上线清单的第一条，也是唯一一个「做了要改架构」的。

## 十、全面铺开上线要改什么（重点）

> 这题是「你的项目离生产还有多远」的变体。**不要答成「加个登录、加个限流」**。
> 正确答法是：先指出根问题，再按依赖顺序给路线图，最后说清哪些是故意不做的。

### 10.1 一句话结论

**这套系统最缺的不是某个加固，是「谁」这个概念。** 没有身份主体，后面的鉴权、审计、
多租户、限流、画像都只能做成局部补丁——补上了也说不清它挡的是谁。

### 10.2 按依赖顺序的改造清单

#### 第一层：身份与入口（P0，必须先做）

| 改什么 | 现在 | 上线要改成 |
|---|---|---|
| 客户身份 | `_guess_customer` 从话里猜，兜底 `C9995` | 登录态 / SSO / OAuth，服务端从 token 推 `customer_id`；**删掉 `_guess_customer`** |
| 会话归属 | `session_id` 是 bearer token | `session_id` 绑定登录态；cookie `HttpOnly + Secure + SameSite`；不放进 URL |
| 后台 | 单个 `ADMIN_PASSWORD` | 用户表 + 角色（审核员 / 管理员）+ 审计日志（谁、何时、对哪一笔） |
| API | 一个共享 `API_KEY`，不配就放行 | 每个调用方一个凭据，可单独吊销；默认拒绝；mTLS 或 OAuth2 |
| 入口边界 | app / admin 都绑 `127.0.0.1`，但 app 无鉴权 | 反向代理 + TLS；app 也要登录；按端口做网络策略 |

具体代码落点：

- `ecom/orchestrator/workers/order.py::_guess_customer` 删除或退化为「在已认证客户
  名下做消歧」；
- `ecom/orchestrator/session.py`：`sessions` 表加 `principal_id` / `tenant_id`；
- `admin.py::check_password` 换成真正的登录 + RBAC；
- `api.py::require_api_key` 换成按调用方的凭据校验 + 吊销列表。

#### 第二层：执行安全（P0/P1）

| 改什么 | 现在 | 上线要改成 |
|---|---|---|
| 沙箱隔离 | AST 白名单 + 受限 builtins，同容器同用户 | 独立容器 / gVisor / Firecracker；只读文件系统；无网络；独立低权用户 |
| 资源上限 | 无 rlimits | `mem_limit` / `cpus` / `pids_limit` + `resource.setrlimit` |
| 超时 | 父进程 `subprocess.run(timeout=)` | 保留，再加子进程内部 watchdog |
| 提示词注入 | 用户问题原样进代码生成 prompt | 输入过滤 + 指令/数据分隔 + 生成后静态校验 + 最小权限执行 |
| 数据访问 | 沙箱能读到 `.env`、`orders.sqlite` | 只挂载必要的数据集，且只读；密钥不进沙箱容器 |

这一层的顺序很重要：**先把入口关起来（第一层），再加厚沙箱（第二层）**。在一扇
没锁的门上装防盗链，收益很低。

#### 第三层：数据与一致性（P1）

| 改什么 | 现在 | 上线要改成 |
|---|---|---|
| 订单库 | SQLite 单文件 | MySQL / Postgres；连接池；读写分离（按需） |
| 会话库 | SQLite 单文件 | Redis / Postgres；支持多副本 |
| Schema 演进 | `CREATE TABLE IF NOT EXISTS`，只建不改 | 引入迁移工具（Alembic / Flyway）；先迁移后发版 |
| 备份 | 无 | 在线备份 / PITR；定期恢复演练（没演练过的备份不算备份） |
| 多租户 | 无 `tenant_id` | `tenant_id` 贯穿入口 / 检索 / 工具 / 数据库；仓储层强制过滤；向量库按租户隔离 |
| 数据保留 | 会话 30 天；日志只增不减 | 日志轮转 + 保留期 ≤ 会话保留期；trace 原文单独短保留；提供按用户删除 |

关键判据：**当 `return_reviews` 里出现第一个「人下的结论」时，就必须有迁移机制。**
那之前「删库重灌」是免费的，那之后重灌就是抹掉人的决定。

#### 第四层：可靠性与成本（P1）

| 改什么 | 现在 | 上线要改成 |
|---|---|---|
| 限流 | 无 | 按 key / IP / 租户的 RPS + 并发 + TPM 多维限流 |
| 预算 | 无 | per-tenant 日/月 token 预算；超阈值熔断 / 降级 |
| 重试 | 路由有界；写操作不重试 | 指数退避 + jitter；错误码分类；只对幂等调用重试 |
| 熔断 | 无 | 模型供应商 / 向量库 / 数据库各自熔断 + 降级 |
| 队列 / 背压 | 无 | 慢请求（analytics）走队列；在线/离线分优先级 |
| 优雅停机 | 无 | 处理完在途请求再退出；健康检查分 liveness / readiness |
| 多副本 | SQLite 堵死 | 外部化状态后水平扩展 |

#### 第五层：可观测与质量（P1/P2）

| 改什么 | 现在 | 上线要改成 |
|---|---|---|
| 指标 | 本地 JSONL trace | OpenTelemetry + Prometheus / 云监控；`router_source` 比例、p95 耗时、token 成本、错误率、`insufficient` 比例 |
| 告警 | 无 | 路由退化、错误率、预算、延迟、依赖不可用 |
| 日志 | 明文、无轮转 | 结构化日志 + 脱敏 + 轮转 + 保留期 |
| 追踪 | request_id | 全链路 trace_id，跨 worker / 子进程 / 模型调用 |
| 质量门禁 | 离线评测 | 评测进 CI；每次 prompt / 模型 / 检索改动跑回归；线上抽样 + 人工复核 |
| 灰度 | 无 | 按租户 / 流量 hash 切流；shadow → canary → 全量；可回滚 |

#### 第六层：交付与合规（P2）

| 改什么 | 现在 | 上线要改成 |
|---|---|---|
| 镜像 | 固定 `ecom-cs:local` | 版本化 tag（语义版本 / git sha）；回滚演练 |
| CI/CD | ruff + pytest | 加镜像构建 + compose 冒烟 + 安全扫描（依赖 / 镜像） |
| 密钥 | `.env` 明文 | KMS / Vault / Docker secret；轮换；不进镜像 |
| 合规 | 无 | 用户同意、隐私政策、数据删除、模型供应商 DPA、内容安全审核 |
| 审计 | 审核备注是手填字符串 | 不可篡改的审计日志（谁、何时、对哪一笔、改了什么） |
| SLO | 无 | 定义可用性 / 延迟 / 质量目标；错误预算 |

### 10.3 分阶段路线图

**阶段 0：内部演示（现在）**

- 单机、SQLite、无身份、无 SLA；
- 目标：证明架构和链路。

**阶段 1：内测（2~4 周）**

- 身份 + 登录 + 网络收口（P0）；
- 容器资源上限；
- 基础限流 + 预算；
- 日志轮转；
- 一批真实问题做评测基线。

**阶段 2：小流量生产（1~2 个月）**

- 订单库 / 会话库换外部存储；
- 迁移机制；
- 指标 + 告警；
- 灰度 / 回滚；
- 沙箱独立容器；
- 人工审核 + 审计。

**阶段 3：规模化（3~6 个月）**

- 多租户隔离；
- 多副本 + 队列 + 背压；
- 模型网关（多供应商降级、成本归因）；
- 质量门禁 + 在线实验；
- 合规与数据保留体系。

### 10.4 最小可用上线（如果只有两周）

按投入产出排：

1. **所有入口套登录**（app / admin / api）；
2. **只绑内网 / 反代 + TLS**；
3. **客户身份从登录态推，删掉 `_guess_customer`**；
4. **容器加 `mem_limit / cpus / pids_limit`**；
5. **按 key 限流 + 日预算**；
6. **日志轮转 + 保留期**；
7. **`router_source` 接一个计数器 + 告警**；
8. **镜像版本化 + 回滚演练**。

这八条加起来的工作量，远小于「把沙箱做成强隔离」，但挡住的风险更大。

### 10.5 面试怎么答这题（模板）

> 先说结论：这套系统离生产最缺的不是某个技术点，是身份主体。没有「谁」，
> 后面的鉴权、审计、多租户都是局部补丁。
>
> 然后按依赖顺序说：第一层身份与入口，第二层执行安全，第三层数据与一致性，
> 第四层可靠性与成本，第五层可观测与质量，第六层交付与合规。
>
> 再说最小可用：两周内做身份、登录、网络收口、资源上限、限流预算、日志轮转、
> router_source 告警、镜像版本化。
>
> 最后说清哪些是故意不做的：强隔离沙箱、完整多租户、用户画像——不是不会，
> 是在当前定位下做了会掩盖更根本的问题。

### 10.6 明确不做，以及为什么

- **不把沙箱做成强隔离**：它挡的是「模型写错」，不是「有人故意攻击」；先关入口，
  再加厚沙箱。
- **不在没有真实流量时拍限流阈值**：猜出来的配置比没有配置更危险，因为它看起来像
  有依据。先记录用量，观察两周再切强制。
- **不做用户画像**：先有身份，才谈得上画像。
- **不执行退款**：没有支付网关，假装退款比不做更坏。
- **不合成数据里没有的字段**：会让下游的事实检查一起失效。

## 十一、高频追问与压力面

> 这一节是短答，适合面试前快速过一遍。每题 2~4 句。

1. **「你这个不就是 prompt 工程吗？」**
   不是。prompt 只管单个模型的输入输出；这个项目的核心是控制流、失败语义、状态契约
   和可观测。模型挂了系统仍然能路由、能答订单、能如实说哪块没拿到。

2. **「为什么不用 Function Calling 一把梭？」**
   订单号用正则更准（100% vs 95%，而且不会把「2025 年」当订单号）；操作类型用 LLM
   更稳。所以规则先认、LLM 兜底。写操作还要 worker 层再校验一次。

3. **「多 Agent 是不是过度设计？」**
   对纯 FAQ 是；对「文档 + 数据库 + 实时计算 + 写操作」不是。复杂度跟着失败模式的
   数量走，不是为了用框架而用框架。

4. **「你的 RAG 效果怎么证明？」**
   152 题 Recall@5 78.3%、MRR 0.533；40 条答案忠实性 83.0%；10 条不可答题弃答 9/10。
   指标一般，但可复现，而且拆分看了改写型 / 术语型。

5. **「78.3% 算好吗？」**
   不算高。大约每 5 个问题有 1 个正确答案没进 Top-5；短板在改写型（68.6%）。
   术语型已经 98%。下一步是 query rewrite 和更好的 chunk 策略，而不是调阈值。

6. **「模型胡说怎么办？」**
   三层：检索层阈值 + 生成层「资料里没有就说没有」+ 评测层不可答题。汇总层禁止
   引入新事实；只有一个结论时不调模型。仍然会胡说，所以要有人审和评测。

7. **「用户注入 prompt 让你执行代码怎么办？」**
   这是真实风险。链路是用户问题 → 代码生成 prompt → 沙箱执行。当前沙箱挡模型写错，
   不挡故意攻击；上线要先关入口、再独立容器隔离、只读挂载、无网络。

8. **「能扛多少 QPS？」**
   当前单进程 + SQLite，不能给生产数字。瓶颈依次是：SQLite 单写者、线程池并发、
   没有限流。要先用真实流量测，再谈容量。

9. **「怎么知道上线后变差了？」**
   `router_source` 的 rule/fallback 比例、每 worker 的 p95、insufficient 比例、
   token 成本、错误率。评测集进 CI，prompt / 模型 / 检索改动跑回归。

10. **「如果重做，你会砍掉什么？」**
    如果只做只读 FAQ：砍数据分析 worker、人工审核、双后端。如果做生产客服：砍
    「猜客户身份」和「自由文本审核备注」，换成登录态和结构化审计。

11. **「为什么不用向量数据库自带的 BM25？」**
    两个后端能力不对等；用了会让「换后端只改配置」的契约变成半真半假。应用层 BM25
    只依赖 `all_chunks()`，184 个 chunk 完全够用。

12. **「RRF 的 K 和权重有什么区别？」**
    K 压平靠前名次的差距，但动不了两路话语权（任一路第 1 名恒为 `w/(K+1)`）；
    要改相对强弱只能调权重。默认不加权，因为留出集上没调出稳定收益。

13. **「为什么只有一个结论时不调模型？」**
    没有东西可合并时调模型，只会把忠实的话改写成可能不忠实的话——多一次幻觉机会，
    零信息增益。

14. **「`ok=False` 为什么不重路由？」**
    多半是同一个网络 / 同一台机器的问题，再试一次大概率还是坏。那是「服务一抖动就
    换个 worker 再抖一次」。`insufficient` 才是有信息量的失败。

15. **「为什么全挂了要转人工？」**
    系统性的坏，换人不解决。全挂时 `alive=False`，不重路由，说明情况并转人工。

16. **「SQLite 怎么支撑生产？」**
    支撑不了多副本。单机小流量可以，但横向扩展直接堵死。上线换 MySQL / Postgres；
    会话换 Redis / Postgres。

17. **「为什么退货审核用新表？」**
    不引入第一个 schema 迁移机制；而且`return_reviews` 一旦有人下的结论，重灌库就是
    抹掉人的决定。新表 `CREATE TABLE IF NOT EXISTS` 天然兼容老库。

18. **「两个人同时审同一笔怎么办？」**
    两道闸：状态不是待审核直接返回 `already=True`；UPDATE 带 `AND status = 待审核`，
    `counts[0]==0` 抛 `_LostRace` 回滚整笔事务。必须抛，不能 return。

19. **「为什么写退货不能重试？」**
    写操作可能产生重复申请。读可以重试；写要靠幂等键 + 唯一约束，不能盲目重试。

20. **「会话为什么不用 checkpointer？」**
    `chat_history` 是节点输入不是图状态；让 checkpointer 接管要改图语义，还会撞上
    `operator.add` 重复累积。两个图共用一张表也会混 `thread_id`。

21. **「记忆为什么不在请求路径上蒸馏？」**
    会让用户每问一句都可能多一次模型调用，且不可控（第一次问触发全量蒸馏）。
    收成 CLI 后，模型调用只在有人敲它的时候发生；代价是记忆不实时。

22. **「记忆的幂等怎么保证？」**
    `UNIQUE(session_id, through_message_id)` + `INSERT OR IGNORE`。锁是进程内的，
    蒸馏是独立进程，所以幂等必须由数据库保证。

23. **「为什么不做用户画像？」**
    客户身份是猜的，没有登录态；画像会挂在错误的人上。先有身份，才谈得上画像。

24. **「Chroma 和 Milvus 怎么切换？」**
    `VECTOR_BACKEND` 环境变量；两个后端实现同一套 `VectorStore` 契约；混合检索在
    应用层，避免能力不对称。

25. **「Milvus 版本错位有影响吗？」**
    服务端 v2.5.5，客户端 pin `>=2.6,<3`，实测接口可用但没有保证。长期用要对齐。

26. **「流式输出怎么做的？」**
    另开 `/chat/stream`（SSE），不改 `/chat` 的 JSON 契约；`answer_stream()` 用
    LangGraph 的 `stream_mode=["custom","values"]`，只有汇总模型逐 token 流，
    worker 的中间答案不送。`final.answer` 是权威版本，中途失败以它为准。

27. **「测试为什么不用真实模型？」**
    结果会随模型版本、网络、负载浮动，无法规格回归。用 FakeLLM / ExplodingLLM 测
    控制流和失败语义；质量用离线评测。

28. **「CI 上为什么记的是 517 条，本机是 715 条？」**
    517 是 2026-10-11 那次绿跑的数字；之后仓库又加了会话记忆、图片、流式、L1 演示、
    沙箱加固、MCP 和 React 等测试，本机现在是 717 条 / 715 passed / 2 skipped。
    **新增的这批还没跑过 CI**，所以 CI 数字仍是旧的。skip 的原因也不同：干净 checkout 上没有 `orders.sqlite`、
    向量库和 Milvus，相关用例会跳过。数字必须带环境和日期，不能直接横比。

29. **「你项目里最危险的代码是哪一段？」**
    沙箱执行 + 无鉴权的数据分析入口 + 用户问题原样进代码生成 prompt。这三者连起来
    是「提示词注入 → 代码执行」的完整链路。现在已经按名字禁掉 pandas/numpy/
    matplotlib 的读写入口、并允许 `savefig` 只写 `CHART_PATH`，但仍是黑名单；
    真正的边界要靠独立容器、只读挂载、无网络、低权用户。

30. **「如果给你一个月，你先做什么？」**
    身份 + 登录 + 网络收口 + 资源上限 + 限流预算 + 日志轮转 + router_source 告警 +
    镜像版本化。先让系统「能安全地给别人用」，再谈功能和规模。

31. **「MCP 为什么默认只开三个工具？」**
    工具列表就是能力发现。默认关掉 PII 和写操作，模型第一步就知道能力不存在；
    注册了再拒绝会让它白调一轮。写操作还要 `confirm=true` 和服务端开关两把钥匙。

32. **「前端为什么不用 WebSocket？」**
    这里只有「问一句、服务器流回一段」，单向 SSE 足够；WebSocket 的双向和长连接
    状态换不来收益。浏览器端用 `fetch` 是因为要 POST + 自定义鉴权头，`EventSource`
    做不到。

## 十二、多模态：图片输入

> 这部分对应 `ecom/orchestrator/tools/image_understander.py` 和
> `ecom/orchestrator/utils/image_intent.py`。一句话：**图片只做一次提取，主链路
> 仍然只读文本。**

### Q69. 图片为什么不直接进对话主链路？

**面试官在考什么**：你是否分得清「加一个能力」和「改一条契约」的成本。

**参考答案**：

当前链路是：

```
上传图片
  → understand_image()      一次视觉模型调用，输出 JSON
  → ImageIntent             结构化契约（订单号 / 金额 / 商品 / 诉求 / 置信度）
  → augment_question_with_image()   拼成带标记的文本块
  → supervisor.answer()     主链路完全不知道图片存在
```

三个理由，按重要性排：

1. **写操作的闸会被绕开。** 主链路判断「这个订单号是不是用户当轮打的」，靠的是
   `order_id_source`。图片里的号是模型从像素里认出来的，如果直接把图塞进主链路，
   它会被当成 `question`，从而有资格触发退货申请。这比「多调一次模型」严重得多。
2. **每个 worker 都要会看图。** 路由、订单、知识库、汇总四个节点都得处理图片格式，
   都得为视觉模型的输出稳定性负责。实际只有「提取订单号/诉求」这一件事需要视觉。
3. **失败面会扩散。** 视觉模型超时、吐非 JSON、图太大，是**可选功能**的失败；
   让它发生在主链路里，等于让一次图片识别失败拖垮整次问答。

**追问与陷阱**：

- 「为什么不把 base64 直接放进 `HumanMessage`？」——那等于让每个节点都变成多模态
  节点；而且模型仍要自己从图里再识别一次订单号，结果不可控。
- 「图片理解为什么不进 supervisor 的 token 账？」——它发生在主链路之前，
  `answer()` 的 token 汇总看不到它。所以 `ImageIntent` 单独带 `tokens`，
  由界面/接口单独记进演示预算。

### Q70. 图片里的订单号为什么「能查不能写」？代码怎么保证？

**面试官在考什么**：提示词/多模态引入的信任边界，以及你有没有把它写成代码而不是注释。

**参考答案**：

订单号来源只有四种：

```python
order_id_source ∈ {"question", "context", "image", ""}
```

- `question`：用户**在当前这条消息里手打**的号；
- `context`：从上一轮对话里带过来的号；
- `image`：视觉模型从图里认出来的号；
- `""`：没有号。

写操作（`create_return`）只认 `question`。`workers/order.py` 里：

```python
guessed = intent.get("order_id_source") in {"context", "image"}
```

`guessed=True` 时，查单可以，提交退货会被挡下来并要求用户手动输入订单号。

还有两处容易被忽略的细节：

1. **拼进正文前先洗号。** 视觉模型可能在 `request` 字段里复述
   「我要退货，订单号 52644」。`sanitize_image_text()` 会把这个号替换成
   `[订单号]`，真正的号只留在带标记的图片块里，由 `image_order_id()` 按
   `source="image"` 取。否则规则层会把它标成 `question`，闸就形同虚设。
2. **规则/模型提取前先摘块。** `strip_image_block()` 把整块摘掉再做意图提取，
   避免图片块里的文字被当成用户输入。图片块只用于补字段，不参与「用户说了什么」
   的判断。

**追问与陷阱**：

- 「用户自己打字补充订单号不就行了？」——对，这就是设计：**要写，就请当轮打出来。**
  多打一次字的成本，远小于替用户提交一个他没提的申请。
- 「为什么 `context` 也不能写？」——上一轮的号可能是从更早的图片或猜测里带过来的，
  来源已经不可靠；写操作只认当前消息，规则简单到不会有人理解错。

### Q71. 视觉调用失败怎么处理？为什么失败是返回值，不是异常？

**面试官在考什么**：可选功能的错误契约，以及敏感错误信息怎么不泄露到界面。

**参考答案**：

`understand_image()` 把所有失败都收敛成 `ImageIntent(ok=False, error=...)`：

| 失败 | 处理 |
|---|---|
| 没配 `VISION_API_KEY` | 构造客户端时抛，函数内接住，返回 `ok=False` |
| 图片为空 / 超 `VISION_MAX_IMAGE_MB`（默认 5MB） | 直接返回 `ok=False` |
| MIME 不在 png / jpeg / webp | 返回 `ok=False`；`image/jpg` 归一成 `image/jpeg` |
| 网络超时（默认 30s）/ 模型吐非 JSON | `loads_or_none()` 判失败，返回 `ok=False` |
| 模型给的订单号形状不对 | 用 `ORDER_ID_RE.search()` 再校验一次，不合格就留空 |

`ok=True` 但 `order_id==""` **不是故障**：图里没有订单号是正常情况，界面提示
「要查订单请手动补号」即可。这个区分和 worker 的 `ok=False` vs
`insufficient=True` 是同一种思路：**坏了**和**看过了没有**必须分开。

为什么不让它抛异常：图片是可选输入，主链路不该为了一个可选功能到处写
`try/except`。异常只留在一处（`get_vision_llm()` 构造失败），由
`understand_image()` 统一接住。

错误原文只写日志，界面只显示「识别失败，请手动输入」——视觉 API 的报错里可能带
请求细节，不适合摆在公网页面上。

**追问与陷阱**：

- 「为什么 `temperature=0`、`max_retries=0`？」——提取任务要稳定，不要创意；
  重试只能有一层，那一层是调用方，SDK 内部再重试会让超时预算失控。
- 「模型把运单号当订单号怎么办？」——形状校验会挡掉大部分；仍认错时，最坏结果是
  「查不到这笔订单」，不会变成「写错一笔订单」。

## 十三、流式输出：SSE 与「真的流」

> 对应 `supervisor.answer_stream()` 和 `api.py` 的 `/chat/stream`。核心不是
> 「用了 SSE」，而是**哪些字是真的流出来的、哪些不是、失败时以谁为准**。

### Q72. 流式怎么做？为什么另开 `/chat/stream`，不改 `/chat`？

**面试官在考什么**：接口契约的兼容性，以及你是否理解「流式」在架构里的位置。

**参考答案**：

```
POST /chat/stream
  → answer_stream()  (生成器)
      → build_graph(stream=True)
      → LangGraph app.stream(stream_mode=["custom", "values"])
      → aggregate 节点把汇总模型的增量推到 custom 通道
  → SSE 帧：start / delta / final / error
```

`answer_stream()` 的事件契约只有三种：

```python
{"type": "start", "request_id": "..."}
{"type": "delta", "text": "..."}
{"type": "final", "state": {...}, "elapsed_ms": 123}
```

`/chat/stream` 是同步生成器，`StreamingResponse` 会把它放进线程池迭代——和
`/chat` 写成 `def` 是同一个理由：模型调用和 sqlite 都是阻塞的，不能塞进事件循环。

为什么另开端点：

- `/chat` 的契约是「一次返回完整 JSON」，几十个调用方（包括测试）按它写；
- 让同一路径按 `Accept` 头切换 body 类型，是那种「curl 看起来正常、客户端里悄悄
  坏掉」的改法；
- 两条路共享同一份 `_finalize()`：trace 只写一条、token 只汇总一次、会话只落一次。
  加流式没有变成「两份成本账」。

**追问与陷阱**：

- 「为什么不直接改 `/chat` 返回流？」——现有调用方要的是 JSON；新增能力不应该
  破坏旧契约。多一个端点比多一个模式开关更容易测。
- 「SSE 的代理坑是什么？」——nginx/Caddy 默认缓冲响应，症状是「服务端流完了，
  浏览器一次性显示」。所以响应头带 `X-Accel-Buffering: no` 和 `Cache-Control: no-cache`。

---

### Q73. 哪些内容是「真流」？只有一个结论时为什么不切碎？

**面试官在考什么**：你会不会为了演示效果伪造流式，以及你对一致性的处理。

**参考答案**：

**只有汇总模型那次调用逐 token 流。** worker 的答案不送出去，原因有两个：

1. 多路结果会被汇总改写，先送出去再收回只会让界面闪一下；
2. worker 的答案不是最终答复，提前展示会让用户以为已经定稿。

没有汇总可做时（只有一个结论 / 直接转人工），最终答复作为**一个** `delta` 整段
交出去，**不把一整段字符串切成小块假装在流**。那是在演延迟，不是在降延迟。

一致性上有一条硬规矩：**`final.answer` 是权威版本。** 汇总流到一半失败时，服务端
会退回拼接，前面收到的 delta 拼起来可能和它不一致——这是流式天生的窗口，不是 bug。
消费方必须以 `final` 为准。

会话落盘也在 `final` 之后：中途断开的请求不写会话。半句话接进下一轮，比没答更坏。

**追问与陷阱**：

- 「能不能 worker 也流？」——可以，但那是另一种产品形态（展示思考过程）。当前
  刻意不展示中间结论，因为中间结论可能被 aggregate 否定。
- 「流式失败怎么告诉用户？」——`error` 事件带一句人话和 `request_id`，异常原文
  只进日志。HTTP 状态码在开始发 SSE 时已经是 200，不能事后改成 500。

### Q74. 为什么用 SSE，不用 WebSocket？前端为什么用 fetch，不用 EventSource？

**面试官在考什么**：协议选型的实际约束，而不是「SSE 更轻」这种口号。

**参考答案**：

- **SSE**：单向、服务器 → 客户端，正好是「问一句、流回一段」；基于普通 HTTP，
  代理、鉴权、日志都沿用现有设施。
- **WebSocket**：双向、长连接，适合多人协作/实时推送；这里没有客户端中途发消息的
  需求，引入连接状态和心跳只会增加运维面。

浏览器端用 `fetch` + `ReadableStream`，不用 `EventSource`：

- `EventSource` 只能发 GET，不能带请求体；
- `/chat/stream` 是 POST，还要带 `X-API-Key` / `X-Invite-Code` 自定义头；
- `fetch` 还能用 `AbortController` 实现「停止生成」。

解析上要处理两件小事：CRLF 归一化、按 `\n\n` 切帧。SSE 的帧边界是空行，不是
「一次网络 chunk」——一个 chunk 可能包含半帧，也可能包含多帧。

**追问与陷阱**：

- 「为什么不用轮询？」——每个 token 一次请求，延迟和成本都更差；而且服务端没有
  「这次回答的进度」这种可查询状态。
- 「SSE 断线重连呢？」——当前不做自动重放：一次问答不是可恢复的订阅，重连应该
  重新提问。`Last-Event-ID` 这套机制在这里没有语义。

## 十四、MCP 工具层

> 对应 `ecom/mcp/`。一句话：**给「已经知道要干什么」的 Agent 一条结构化出口，
> 不经过 Supervisor。**

### Q75. MCP 是什么？你为什么做它？它和对话链路是什么关系？

**面试官在考什么**：你是否理解 MCP 的定位，而不是把它当成「又一个 API」。

**参考答案**：

MCP（Model Context Protocol）是一套让模型/Agent 发现并调用外部工具的协议。
这个项目原来只有自然语言入口：用户不知道自己的问题该找谁，所以需要路由。
MCP 解决的是相反的问题：

> 另一个 Agent 已经知道「我要查订单 52644」，它不该为了这件事再调一次大模型
> 做意图识别，再等一段自然语言回答。

所以两条路**共用业务函数，但不互相调用**：

```
对话链路   app.py / api.py → supervisor → workers → tools/order_tools.py
                                                    ↖
MCP 客户端  ──stdio──→ ecom/mcp/server.py → ecom/mcp/tools.py ─┘
```

- MCP 不经过 Supervisor：少一次模型调用、少一层可能挂的地方；
- 对话链路不经过 MCP：中间多一个进程和一轮协议，换不来任何隔离收益；
- 两边都调 `order_tools.py` 和知识库检索函数，**规则只有一份**。复制一份到 MCP，
  两份迟早会对同一笔订单给出不同结论。

**追问与陷阱**：

- 「为什么不给 MCP 也加路由？」——调用方已经给出了结构化参数；再路由一次等于
  不信任调用方，还多一次模型调用。
- 「为什么不复用 FastAPI 的 `/chat`？」——`/chat` 的输入是自然语言，输出是一段话；
  MCP 要的是结构化参数和结构化结果，两者契约不同。

### Q76. MCP 暴露了哪些工具？写工具和 PII 工具为什么默认关闭？

**面试官在考什么**：能力发现的设计，以及「默认安全」是否落到了注册层面。

**参考答案**：

| 工具 | 默认 | 作用 | 写库 |
|---|---|---|---|
| `get_order` | ✅ | 订单状态、金额、区域、时间 + 物流 | 否 |
| `get_order_returns` | ✅ | 某订单已有的退货申请 | 否 |
| `search_knowledge` | ✅ | 混合检索 + rerank，只返回原文和出处 | 否 |
| `list_customer_orders` | ❌ | 按客户号查名下订单（PII） | 否 |
| `create_return` | ❌ | 提交一笔「待审核」退货申请 | **是** |

默认关闭的两个工具由服务端开关决定**注不注册**：

```bash
MCP_ENABLE_PII=1      # 注册 list_customer_orders
MCP_ENABLE_WRITES=1   # 注册 create_return
```

为什么是「不注册」而不是「注册了再拒绝」：工具列表是调用方唯一的发现机制。
一个永远返回 `not_allowed` 的工具，模型会先调一次、被拒、再放弃——白跑一轮；
列表里没有它，模型第一步就知道这个能力不存在。**能力发现要说真话。**

写操作即使开关打开，也还要求调用方传 `confirm=true`；演示模式下无论开关如何
都拒绝落库。三道闸防的不是同一种误操作：

| 闸 | 谁决定 | 挡住什么 |
|---|---|---|
| `MCP_ENABLE_WRITES` | 服务端 | 这个能力根本不对机器开放 |
| `confirm=true` | 调用方 | 模型把「能退吗」直接执行成申请 |
| `DEMO_MODE` | 部署方 | 公网演示环境被写脏 |

**追问与陷阱**：

- 「为什么 PII 工具也默认关？」——按客户号查单会返回一批订单，泄露面比单号查单大；
  默认关掉，要用的人明确打开并承担审计责任。
- 「为什么没有 `analyze_sales`？」——它会执行模型生成的代码。对话链路里这条已经
  是最需要隔离的一环，再开一个没有对话上下文的入口只会扩大攻击面。

### Q77. MCP 的返回契约、错误码和传输边界是什么？

**面试官在考什么**：协议层的错误处理，以及你对 stdio 安全模型的理解。

**参考答案**：

所有工具返回同一个信封，**失败不抛异常**：

```json
{"ok": true, "data": {...}, "meta": {"elapsed_ms": 3.2}}
{"ok": false, "error": {"code": "not_found", "message": "查不到订单号 99999。"},
 "meta": {"elapsed_ms": 1.1}}
```

错误码只有五个：`invalid_input` / `not_found` / `not_allowed` / `unavailable` /
`internal`。为什么不抛异常：MCP 里异常会变成一次协议错误，模型通常只看到
"tool failed"；而 `invalid_input` 的 message 是它能据此自我纠正的话。内部异常的
原文（可能带 DSN、路径）只写日志，不出现在 message 里。

字段裁剪：按单号查单**不返回** `customer_name` / `customer_id`。对话链路需要它们
判断是不是本人，MCP 调用方不需要——返回客户姓名只是顺手把一份 PII 交给了一个
我们不知道会不会转存的客户端。字段清单是白名单，以后表里加一列不会自动泄露。

传输：**只支持 stdio**。安全性来自「谁能拉起这个进程」，不是来自协议；没有鉴权、
没有限流、没有远程调用。v1 刻意不做 HTTP 传输——那要先回答「谁能调、算谁的、
怎么限流」，没想清楚不开。

还有一个具体坑：**stdout 是 JSON-RPC 的通道**。任何 `print()` 都会打断协议，
症状是「服务起来了，但一个响应都收不到」，而不是报错。所以两个 logger 的 handler
都挂在 stderr；`--list-tools` / `--check` 是例外，它们不跑协议。

**追问与陷阱**：

- 「为什么 MCP 不上公网演示？」——L1 的只读承诺不依赖它；多一个入口就多一份
  需要证明的东西。它没有端口，也不在镜像的启动命令里。
- 「知识库检索会写库吗？」——不会。它只读，也不把问题塞进人审队列（不调
  `record_question`）；但首次调用会加载 embedding / rerank，可能几秒。

## 十五、React 前端与双入口

> 对应 `frontend/` 和 `api.py::mount_frontend()`。核心取舍：**第二个视图，
> 不是第二套实现。**

### Q78. 为什么又做一套 React 前端？和 Streamlit 是什么关系？

**面试官在考什么**：你是否能说清「多入口」的边界，而不是堆技术栈。

**参考答案**：

Streamlit 那版是「演示 + 侧边栏直连视图」：有图片输入、数据分析看板、人审队列，
适合自己跑、自己看。React 这版只做一件事：**一个干净的流式对话界面**，顺带显示
`/health`、路由结果、来源和 token 用量。

两者是同一套编排逻辑的两个视图：

```
Streamlit  app.py  ─┐
FastAPI    api.py  ─┼→ supervisor.answer() / answer_stream()
React      /ui     ─┘
```

React 版**刻意不重复**图片输入和数据分析看板：那些能力在 Streamlit 版里有，
重复实现只会产生两套会分叉的行为。它也不替代 `app.py`——`main.py` 仍然是第一入口。

构建与挂载：

```bash
cd frontend && npm run build        # tsc --noEmit + vite build → dist/
uv run uvicorn api:app --port 8000  # 启动时检查 dist，有就挂到 /ui
```

`vite.config.ts` 的 `base: "/ui/"` 必须和 `mount_frontend()` 的挂载路径一致。
不一致的症状是**页面能打开、但白屏**——资源请求的是 `/assets/...`，实际在
`/ui/assets/...`，只有浏览器控制台能看到 404。

**追问与陷阱**：

- 「为什么不把 Streamlit 也换成 React？」——Streamlit 版的侧边栏、看板、人审队列
  是内部工具形态，React 重写一遍成本高、收益低；这次要补的是「对外演示的流式界面」。
- 「前端构建失败会让 API 起不来吗？」——不会。`mount_frontend()` 检查
  `dist/index.html`，不存在就跳过并打一条 info。前端是可选层，不能把「可选」
  变成「必需」。

### Q79. 前端怎么处理鉴权、会话和 XSS？为什么不加 CORS？

**面试官在考什么**：前端安全常识，以及你是否会把开发便利带进生产。

**参考答案**：

- **API Key / 邀请码 / 会话号只放 `sessionStorage`**：关掉标签页就没；不进 URL、
  不写 `localStorage`。会话号是 bearer token，不是账号——进 URL 就会被浏览器历史、
  代理日志、Referer 头带走。
- **回答按纯文本渲染**（`white-space: pre-wrap`），不解析 Markdown / HTML。
  模型输出直接进 `innerHTML` 是这类界面最常见的一个洞；这里连 Markdown 都不解析，
  因为演示场景不需要，而解析器本身就是攻击面。
- **不展示 `/trace`**：它会返回所有人问过的话和内部耗时，是排障窗口，不是给演示
  观众看的。演示模式下服务端也会返回 404（而不是 403——403 等于告诉对方
  「这里有东西，只是不给你」）。
- **不加 CORS**：开发时 Vite 把 `/health` `/chat` `/trace` 代理到 `127.0.0.1:8000`，
  浏览器始终看到同一个 origin；生产时 FastAPI 直接托管 `/ui`，也是同源。为了开发
  环境去放宽生产接口的 CORS，方向反了。
- **构建产物里没有密钥**：`VITE_*` 变量会被打进 bundle；本项目只用
  `VITE_API_TARGET`，而且只在开发服务器里生效。

**追问与陷阱**：

- 「sessionStorage 也会被 XSS 读走。」——对，所以第一道是「不引入 XSS」：纯文本
  渲染、不解析模型输出。真正的高安全场景应该用 HttpOnly cookie + CSRF 防护，
  那需要后端有真正的登录态，不在当前演示范围。
- 「为什么 `EventSource` 不行？」——见 Q74：它只能 GET、不能带自定义头，而
  `/chat/stream` 是 POST + 两个鉴权头。

## 十六、L1 公网演示与沙箱加固

> 对应 `ecom/demo.py`、`api.py` 的演示闸和 `ecom/analytics/core/sandbox.py`。
> 这两块要一起讲：一个是「把入口关小」，一个是「把执行面收窄」。

### Q80. 公网演示怎么做成只读？四道闸各挡什么、挡不住什么？

**面试官在考什么**：你是否知道演示环境和生产环境的差别，以及每条防线的边界。

**参考答案**：

`DEMO_MODE=1` 时，四个闸同时生效：

| 闸 | 实现 | 挡住什么 | 挡不住什么 |
|---|---|---|---|
| 邀请码 | `X-Invite-Code` + `compare_digest`，**没配就拒绝**（fail closed） | 随手扫到端口的人 | 把码转发出去的人；没有账号/审计/失效机制 |
| 限流 | 进程内滑动窗口，按客户端 IP | 单个客户端刷屏 | 换 IP、多开会话；跨副本不精确 |
| 每日 token 预算 | sqlite 按天记账，实际用量 | 一天烧掉一大笔钱 | 预算本身设得太大 |
| 只读策略 | `demo.writes_allowed()` / `worker_allowed()` | 退货申请、数据分析代码执行、知识库写入 | 不是权限系统：没有用户、角色、审计 |

几个容易讲错的点：

- **只读不能只靠界面藏按钮。** 闸下在 `workers/order.py` 的写路径上，API、CLI、
  aggregate 重路由都会经过它；路由层和健康检查也会把 `analytics` 摘掉。
- **预算账本落磁盘，不落进程内变量。** Streamlit 每交互一次重跑脚本，API 会被
  丢进线程池/多进程；进程内计数等于「每个进程一份预算」，实际花掉的是 N 倍。
- **账本读不出来时拒绝，不是放行。** 成本闸失效要倒向不花钱那一边；磁盘问题
  会让演示立刻被发现，而「读不出来就继续花」会静默烧穿预算。
- **trace 返回 404，不是 403。** 403 等于告诉对方「这里有东西，只是不给你」。
- **健康检查过滤掉被停用的 worker。** 否则公网上会看到一个「存在但不可用」的
  worker，让人以为只是这一次没路由到它。
- **后台管理端不部署在公网。** `admin.py` 能批准退货，它有自己的密码门禁，但
  不进 L1 的 compose。

一段可以直接背的总结：

> 这是「能安全地挂在公网上给人看」的最低配置，不是一套生产级权限系统。邀请码
> 挡的是路人，限流挡的是刷屏，预算挡的是账单，只读挡的是写库。真要上线到
> 「能替真实用户办事」，得先有身份和审计——那不在这一层解决。

**追问与陷阱**：

- 「邀请码泄露了怎么办？」——换码 + 依赖限流和预算；它本来就不是账号体系，
  没有吊销列表。
- 「为什么限流不做成 Redis？」——单机演示，进程内够用；跨副本仍然有效的闸是
  磁盘上的 token 预算。两者一个有状态、一个无状态，别把功能说反。

### Q81. 沙箱这次补了什么洞？为什么补完还是「黑名单」？

**面试官在考什么**：你是否真的理解「禁了 `open()`」不等于「禁了文件 I/O」。

**参考答案**：

原来的沙箱已经禁了 `open()`、`eval()`、`exec()`、危险 import 和 dunder 属性，
但实际测出来两个洞：

```python
pd.read_csv(r"C:\Windows\win.ini")     # 能读到内容
plt.savefig("任意路径.png")             # 能写文件
```

原因很直接：**pandas / numpy / matplotlib 自己就是文件 API**。不需要逃逸，
用放行的库就够了。所以这次按方法名把常见入口逐个禁掉：

- 写：`to_csv` / `to_excel` / `to_pickle` / `to_parquet` / `to_sql` / `save`
  / `savez` / `savetxt` / `ExcelWriter` / `PdfPages` / `open_memmap` 等；
- 读：`read_*` 前缀 + `load` / `loadtxt` / `genfromtxt` / `imread` / `ExcelFile`
  / `HDFStore` / `get_handle` / `open` 等；
- `from pandas import read_csv` 这种「导入即拿到函数」的写法也要拦，否则
  属性检查被绕过；
- `savefig` 是唯一放行的写文件入口，而且实参必须是 `CHART_PATH`；
  `CHART_PATH` / `output_dir` 不许被赋值或 `match case` 捕获，否则路径检查白做；
- `savefig` 的接收者也要校验：`(open(...) and plt).savefig(...)` 这种写法不能用
  免检区把危险表达式带进来。

但必须说清楚：**这是黑名单，不是边界。** `pd.io.*` 之类的间接入口仍可能绕过。
真正的隔离得靠容器 / 低权用户 / 只读挂载 / 无网络 / rlimit，这些当前都没做。
准确说法是：**它挡得住模型写错，挡不住有人故意攻击。**

**追问与陷阱**：

- 「为什么不直接禁掉整个 pandas？」——数据分析任务就是 pandas；禁掉等于不做。
- 「为什么只允许 `savefig(CHART_PATH)`？」——图表是这个功能唯一需要产出的文件；
  其他任何写文件都不是业务需要。`CHART_PATH` 由服务端生成，不是模型拼的。
- 「为什么不做 AST 白名单之外的正则过滤？」——正则挡不住 AST 层面的别名、间接
  调用和 `match` 捕获；静态校验要看结构，不要看字符串。

### Q82. 如果明天上线，你还差什么？

**面试官在考什么**：你是否知道「演示」和「生产」之间最关键的缺口。

**参考答案**：

按依赖顺序，第一层永远是**身份**：

1. **身份与入口**：登录态 / SSO，服务端从 token 推 `customer_id`；
   `session_id` 绑定登录态，cookie `HttpOnly + Secure + SameSite`；后台加角色和
   审计；API 按调用方发凭据、默认拒绝；反向代理 + TLS。
2. **执行安全**：沙箱独立容器 / gVisor / Firecracker，只读文件系统、无网络、
   低权用户、rlimit；输入过滤 + 指令/数据分隔。
3. **数据与一致性**：订单库换 MySQL/Postgres，会话换 Redis/Postgres；引入迁移
   工具（Alembic/Flyway）。
4. **可靠性与成本**：网关限流、配额、重试预算、模型降级、成本归因。
5. **可观测与质量**：结构化日志、指标、告警、评测集回归、人工复核闭环。
6. **交付与合规**：镜像版本化、密钥管理、备份恢复、数据保留策略。

一句话：**最缺的不是某个加固，是「谁」这个概念。** 没有身份主体，后面的鉴权、
审计、多租户、限流、画像都只能做成局部补丁——补上了也说不清它挡的是谁。
完整路线图见第十节。

## 十七、数字卡片与白板模板

### 17.1 数字卡片（面试前十分钟看这一页）

| 类别 | 数字 |

| 架构 | 1 个 Supervisor、3 个 worker、`MAX_ROUNDS=2`、`recursion_limit=14` |
| 超时 | knowledge 90s / order 20s / analytics 180s；路由 8s、总预算 20s |
| 路由 | 3 层；置信度阈值 0.6；上文 2 轮 × 160 字；记忆最多 3 条 |
| RAG | chunk 512 / overlap 50；召回 20 + 20；RRF K=60；融合取 5；rerank 取 3 |
| 评测 | 152 题 Recall@5 78.3%、MRR 0.533；忠实性 83.0%；弃答 9/10 |
| 语料 | 10 篇法规 + 7 篇示例；184 个 chunk |
| 订单 | 65,752 笔订单；62,897 条物流；查询毫秒级 |
| 分析 | 20,242 行、3.6MB；一笔订单平均 2.8 行 |
| 实测 | 一次请求 16.3s / 839+320 token；知识库 8.1s vs 订单 12ms |
| 降级 | dashscope 不通：8s 退规则，总耗时 17.6s 而非 180s |
| 会话 | `HISTORY_TURNS=6`；TTL 30 天；`MEMORY_TOP_K=3`；蒸馏上限 40 条 |

### 17.2 白板画图顺序（5 分钟）

1. **画 5 个框**：START、router、aggregate、END、三个 worker（可以画成一列）。
2. **连三条并行边**：router → 三个 worker；三个 worker → aggregate。
3. **连回环**：aggregate → router，标注 `decision == "re_route"`。
4. **写四个条件**：`plan 非空 & untried 非空 & round < MAX_ROUNDS & alive`。
5. **写失败语义**：`ok=False` 不重路由；`insufficient=True` 重路由。
6. **写三个接入边界**：知识库进程内 / 订单 SQLite / 数据分析子进程。
7. **写一个数字**：知识库 8.1s vs 订单 12ms，解释超时为什么分开配。
8. **补入口与出口**：四个入口共用 `answer_stream()`；MCP 走 stdio、不经过 Supervisor。
9. **最后补一句**：模型能判定不能拍板；写操作人工审核；公网演示只读。

### 17.3 一句话记忆锚点

- **路由三层**：LLM 聪明、规则不坏、知识库兜底。
- **失败两种**：坏了不换人，没有才换人。
- **回环四门**：有计划、有新人、没到顶、还活着。
- **汇总两条**：不加新事实；只有一个结论不调模型。
- **图片一条**：图里认的号能查不能写；要写就请当轮打出来。
- **流式两条**：只有汇总真流；`final.answer` 永远权威。
- **MCP 两条**：能力发现说真话（默认不注册）；stdio 的安全来自谁能拉起进程。
- **演示一句**：四道闸是最低配置，不是权限系统。
- **边界一条**：模型能判定，不能拍板。
- **上线一句**：最缺的不是加固，是「谁」。

## 十八、反问面试官

面试最后通常会给你提问机会。问这四类，比问「公司福利」加分：

1. **团队现在最大的技术债是什么？**
   看他们是坦诚还是回避。
2. **这个岗位前三个月最想解决的问题是什么？**
   判断你进来是救火还是建设。
3. **线上质量怎么衡量？有评测集 / 人工复核 / 用户反馈闭环吗？**
   直接对应你项目里的评测经验。
4. **模型 / 供应商选型是集中管理还是各团队自选？**
   对应你对模型网关、成本归因的理解。
