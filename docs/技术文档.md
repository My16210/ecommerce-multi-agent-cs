## 一、系统概览

```
                        ┌──────────────────────────────┐
                        │        decision == re_route  │
                        ▼                              │
 START ──► router ──┬──► worker_knowledge ──┐          │
                    ├──► worker_order     ──┼──► aggregate ──┬──► END（answer）
                    └──► worker_analytics ──┘               └──► END（human）
```

三个 worker 各对应一种"答案在哪里"：

| 问题类型 | worker | 答案在哪 |
|---|---|---|
| 退货政策 / 保修 | knowledge | 文档里，要检索（向量 + BM25 + rerank） |
| 订单到哪了 / 我要退货 | order | 数据库里，要查（SQLite / MySQL 双后端） |
| 哪个大区卖得最好 | analytics | 要算（模型写 pandas 代码 → 子进程执行 → 自查） |

### 八条设计原则

后面每一节都是其中一条展开。先摆在这里，是因为它们决定了后面所有的"为什么"：

1. Agent 还是 Tool，判据只有一条：有没有"看一眼结果再决定下一步"的循环。订单查询没有，所以是纯函数；数据分析有，所以是图。
2. worker 之间不传自然语言，只传结构化契约。
3. `ok=False`（坏了）和 `insufficient=True`（看过了没有）必须分开。只有后者触发重路由。
4. 回环有界，而且由代码保证，不靠提示词里写"不要重复路由"。
5. 汇总不引入新事实；只有一个结论时连模型都不调。
6. 模型能判定，不能拍板。所有会产生后果的动作（写知识库、批准退货）都要人过一道。
7. 能用设计绕开的并发问题，就不该用锁去救（`tried` 由 router 一次写入，而不是上 reducer）。
8. 能不引入机制就不引入机制（审核痕迹用新表，不引入 schema 迁移）。

## 二、编排层：四个契约

### 2.1 `CSState`：哪些字段是状态，哪些只是输入

[ecom/orchestrator/core/state.py](../ecom/orchestrator/core/state.py)

```python
class CSState(TypedDict, total=False):
    question: str
    chat_history: list  # 节点输入，不是图状态：图从不往回写；router 和各 worker 读它，汇总节点刻意不读

    plan: list              # 本轮要调用哪些 worker
    plan_reason: str
    plan_confidence: float
    router_source: str      # "llm" / "rule" / "fallback"——路由结论是谁给的
    router_tokens: dict
    tried: list             # 跨轮累积，防止原地打转
    round: int

    # Annotated + operator.add：并行 worker 各自 append，最终合起来。
    results: Annotated[list, operator.add]

    decision: str           # "answer" / "re_route" / "human"
    answer: str
    sources: list
    synth_source: str       # "llm" / "concat"
    pending_note: str
    request_id: str
```

`results` 是唯一带 reducer 的通道，这一条决定三件事：

- 并行 worker 各自 `append`，谁也不覆盖谁。reducer 就是为这个存在的。
- 代价是它跨轮只增不减。往一个 add 型通道写 `[]` 等于没写。所以每条结果都由 [workers/base.py](../ecom/orchestrator/workers/base.py) 的 `stamp_round` 盖上 `round`，汇总时用 `round_results(results, n)` 挑出本轮的。这是全项目最容易写错的一处，回归测试是 `test_results_do_not_leak_from_one_round_into_the_next`。
- `chat_history` 不是图状态，是节点输入。它只由 `make_initial_state` 塞进去，图从不往里写（没有 reducer、没有累积节点）。读它的是 router（指代消解）、order worker（抽实体）和 knowledge worker（生成答案）；汇总节点刻意不读，因为它那一步只做"各说各的、不替谁判对错"。§六 会说明，正是"它是输入而不是状态"这一条，决定了会话持久化不能复用 `SqliteSaver`。

一个反直觉的地方：`tried` 也是"多个节点想写同一个键"的场合，但这里没上 reducer，改成由 router 一次性写入。计划本来就是 router 定的，它顺手记下来最自然；这么一来也从构造上避开了并发写，不需要锁，也不需要 reducer。

### 2.2 router：三层优先级

[ecom/orchestrator/core/router.py](../ecom/orchestrator/core/router.py)

```
route(question, tried, chat_history)
  ├─ ① LLM 分类        ── 成功 → source="llm"
  │     · 提示词带一段有界的「上文」（最近 2 轮），否则「那能退吗」没有主语
  │     · max_retries=0（重试权收回我们手里）
  │     · ROUTER_TIMEOUT=8s 单次，ROUTER_BUDGET=20s 总时长
  │     └─ 失败 → 落 ②
  ├─ ② 关键词规则      ── 命中 → source="rule"
  │     · 指代上一轮的追问（"那能退吗"）：carried_order_id 携带回订单号 → 补 order
  └─ ③ 最小默认计划    ── source="fallback"，plan=["knowledge"]
  最后统一：plan = [n for n in plan if n not in tried]   ← 回环不原地打转
```

`router_source` 必须进 trace。rule / fallback 的比例一涨，说明 LLM 那一层在坏，这是唯一一个能在用户还没抱怨的时候发现路由退化的指标。

低置信度（< 0.6）时往计划里补一个 knowledge。这是故意的不对称：漏调一个 worker 是少答一半，用户看得出来；多调一个只是多花一次调用，用户看不出来。

改路由规则时有个连带面要记住。订单号的形状（`(?<!\w)(\d{5,})(?!\d)`，5 位起步、`(?<!\w)` 挡客户号 `C20755`）只有一份定义，在 [utils/ids.py](../ecom/orchestrator/utils/ids.py)，router 和 [workers/order.py](../ecom/orchestrator/workers/order.py) 都 import 它。

这里曾经是两处各写一份。换真实数据时放宽位数只改了一边，而且分叉不报错——路由认得出的订单号，抽取层认不出。事故经过记在 `utils/ids.py` 的模块 docstring 里。收成一份是那次事故的修复，不是整理。

跨轮指代同理，也只写一份：[utils/entities.py](../ecom/orchestrator/utils/entities.py) 的 `carried_order_id`，router 的规则层和 order worker 共用。理由跟上面一模一样，"接着上一轮说"这条判定要是两处各写一份，也会分叉不报错。

### 2.3 worker 的统一返回契约

```python
{"worker": "order", "ok": True, "answer": "...", "data": {...},
 "sources": [...], "insufficient": False, "error": "",
 "elapsed_ms": 7, "tokens": {"in": 0, "out": 0}}
```

| 字段 | 含义 | 谁读它 |
|---|---|---|
| `ok` | 这次调用本身成功没有 | aggregate 决定要不要说"这块暂时用不了" |
| `insufficient` | 调用成功了，但确实没答上来 | aggregate 决定要不要换人再试一轮 |
| `error` | 失败原因 | trace / 界面 |
| `round` | 第几轮（`stamp_round` 盖的） | `round_results` |

`ok=False` 和 `insufficient=True` 混在一起会发生两件坏事：监控上看不出"业务规则拦了多少"和"系统坏了几次"；行为上变成"服务一抖动就换个 worker 再抖一次"。

同理，"订单号查不到""这个状态不能退货"是业务结论，以 `ok=True` 返回，它们不是故障。例外见 §5.2：退货审核链路上有一个 `ok=False` 是刻意留的，因为那时候用户确实没拿到东西。

### 2.4 aggregate 的决策树

[ecom/orchestrator/core/aggregate.py](../ecom/orchestrator/core/aggregate.py)。短路返回，顺序不能换：

```
aggregate(state)
  ├─ ① usable 非空 ──────────► decision = "answer"
  │      合并 usable；failed 的补"这块暂时用不了"；thin 的澄清话术附在后面
  ├─ ② 想重路由吗？ ─────────► decision = "re_route"
  │      can_retry = plan 非空 & untried 非空 & round < MAX_ROUNDS & alive
  ├─ ③ 手上有话可说吗？ ─────► decision = "answer"
  └─ ④ 什么都说不出来 ───────► decision = "human"
```

四个条件缺一不可，每一个都在堵一种"没出口的回环"：

| 条件 | 缺了会怎样 |
|---|---|
| `plan 非空` | 空计划重来还是空，空转一轮 |
| `untried 非空` | 没有新单元 = 原地打转 |
| `round < MAX_ROUNDS` | 环没有界 |
| `alive` | 全挂了，换人再挂一次 |

`len(usable) == 1` 时不调模型，原样返回。没有东西可合并时还去调一次模型，只会把一段本来忠实的话改写成一段可能不忠实的另一段话，多一次幻觉机会，零信息增益。

`synth_source`（`llm` / `concat`）记进 trace：它决定"这次答案有没有被改写过的可能"，是个该被记录的事实。

## 三、三种接入边界

三个子系统在同一个包里，但接入方式故意不一样。各自算的账不同，不是不一致：

| 子系统 | 接入 | 为什么 |
|---|---|---|
| 知识库 | 进程内 import | 热路径、无副作用的纯库；子进程要多付一次解释器启动 + chromadb 初始化 |
| 订单 | 本进程 + SQLite | 毫秒级、纯函数、不调模型 |
| 数据分析 | 子进程 | 唯一执行模型生成的代码，需要一个能被真杀死的边界 |

### 3.1 数据分析那条边界：理由换过一次，但边界留着

合并前，这里的第一个理由是硬约束：两个仓库都有顶层 `src`，同进程必然有一个静默解析错。合并后那个理由没了。现在留下它的理由有三个，第一个最要紧：

1. 它执行模型生成的代码。沙箱（[core/sandbox.py](../ecom/analytics/core/sandbox.py)，AST 白名单 + 受限 builtins）不做超时，也不做进程隔离，`while True: pass` 拦不住。`subprocess.run(timeout=…)` 到点是真杀，进程内那个"超时"只是不再等它。
2. 它可能跑几分钟（生成 → 执行 → 报错 → 改 → 再执行）。
3. 崩了炸不到 supervisor。

命令是 `python -m ecom.analytics.cli.analyze`，用 `sys.executable`，同一个 venv，所以不再需要"用哪个解释器"这个配置项。子进程 stdout 只吐一行 JSON。

界面（`app.py`）也走这条边界：它调的是同一个 `run_analytics()`，不是直接 import 那个图。为了"少起一个进程"改成进程内调用，等于换了一个没有超时、崩了会带走整个页面的执行环境。`test_the_analytics_worker_still_goes_through_a_process_boundary` 守着这条。

### 3.2 知识库只 import 四个入口

不 import `ecom/knowledge/core/graph.py`：绕开联网搜索那一路依赖，也避开 `answer_node` 里"把问过的题写进待审核队列"的副作用。这个理由和撞名无关，合并前后都成立。

## 四、数据层

### 4.1 `Database`：一个薄适配器

[ecom/orchestrator/db/engine.py](../ecom/orchestrator/db/engine.py)

- SQL 全部用 `?` 占位符写，MySQL 分支在 `_translate` 里统一换成 `%s`。
- DDL 用两边都吃的写法（`VARCHAR` 做主键而不是 `TEXT`，不用 `AUTOINCREMENT`）。
- 默认 SQLite 的理由不是"SQLite 更好"，而是默认路径必须零外部依赖，否则"别人拿到能跑"就是空话。

`transaction(statements) -> list[int]` 是这个类上唯一一个"多条语句一个连接"的方法，退货审核用它。两个必须知道的点：

```python
def transaction(self, statements: list) -> list:
    """一个连接里跑多条写语句，一起提交；返回每条语句的行数。"""
    # sqlite: with self.connect() as conn: ...  cursor.rowcount
    # mysql:  conn = self._open_mysql(autocommit=False)   ← 必须显式关
```

- MySQL 分支必须开 `autocommit=False`。默认连接是 `autocommit=True`，那样"事务"是假的：每条语句各自提交，中途失败留下半截。而且它不报错。
- 返回行数是必需的，不是好看。退货审核要靠 `counts[0] == 0` 发现"状态已经被别人改掉了"（见 §5.3）。

### 4.2 真实数据暴露的三个问题

原来是手写数据，换成 DataCo 之后才暴露出来。它们不是新功能，是手写数据藏住的问题：

1. 一行不等于一笔订单。DataCo 一行是一个商品项，一笔订单平均 2.8 行，`len(df)` 当订单数会多算近三倍，且不报任何错。口径写在 `dataco/NOTES.md`，一次读取、三处注入（analyst / self_corrector / reviewer）——因为原来两处各写了一遍，没有任何机制保证一致。
2. 公开数据里没有承运商、没有运单号，`Order City` 是目的地不是发货地。这三列一律留空。有意不合成假值：补一个假值会让下游"不许引用不存在的事实"那道检查一起失效。
3. 订单号是 1~5 位。`\b\d{6,}\b` 对真实订单号一笔都命中不了，却会把 6 位以上的发票号路由成"查订单"。门槛定在 5 位是因为放宽到 4 位会让「2025 年买的」里的 2025 被判成订单号——认错一个订单号比认不出更糟。这个形状现在只有一份定义，在 [utils/ids.py](../ecom/orchestrator/utils/ids.py)；router 和 order 都 import 它。这里原来也是两处各写一份，换数据时只改了一边，分叉不报错——那段经过 §2.2 讲过，不重复。

### 4.3 状态词表：数据源原值 vs 我们自己造的状态

| | `orders.status` | `return_requests.status` |
|---|---|---|
| 值 | 9 个英文原值（`COMPLETE` / `CLOSED` / …） | 3 个中文值（待审核 / 已通过 / 已拒绝） |
| 读者 | 代码和模型 | 人（后台界面、给用户的话术） |
| 来源 | 数据源原值，改一个就多一个没有依据的映射 | 我们自己造的 |

一句话规则：数据源给的字段保留原值，我们自己造的状态用中文。中文注释只用在给人看的报错和回答里，不参与任何判断——判断一律比英文集合。注释一旦参与判断，就变成了第二个真相来源。

## 五、人工审核这一环

贯穿全项目的一条：模型能判定，不能拍板。两处落点，形状一模一样：

| | 知识库队列 | 退货审核 |
|---|---|---|
| 模型能做的 | 判定"这个问题值得沉淀" | 登记一笔退货申请 |
| 人才能做的 | 批准 → 才渲染成 md、才进向量库 | 批准 / 拒绝 → 才产生结论 |
| 代码 | [knowledge/review/queue.py](../ecom/knowledge/review/queue.py) + [cli/review.py](../ecom/knowledge/cli/review.py) | [orchestrator/admin/returns.py](../ecom/orchestrator/admin/returns.py) + [cli/returns.py](../ecom/orchestrator/cli/returns.py) |

中间为什么必须隔一层：模型生成的答案一旦直接进向量库，下一轮检索就会把它当成"权威资料"捞出来喂给模型，错误会被放大并固化成看起来不容置疑的知识。这个叫知识库自污染。

### 5.1 `admin/` 和 `tools/` 是两个目录

```
ecom/orchestrator/tools/    模型能调到的（order_tools.py 的纯函数）
ecom/orchestrator/admin/    只有人能下的结论（returns.py）
```

为什么不把 `review_return` 放进 `order_tools.py`：那个模块的 docstring 第一句就是「为什么这些是"工具"而不是"Agent"」，它是模型能调到的工具层。把"批准退货"放进同一个模块，等于把"模型可以拍板"写进架构里，哪怕现在没有任何工具去调它。这条边界该用目录结构守，而不是用代码评审守。

### 5.2 退货的重复申请：拦截条件写错一格，两个方向各错一次

```python
OPEN_RETURN_STATUS     = "待审核"
APPROVED_RETURN_STATUS = "已通过"
REJECTED_RETURN_STATUS = "已拒绝"
RETURN_STATUSES = (OPEN_RETURN_STATUS, APPROVED_RETURN_STATUS, REJECTED_RETURN_STATUS)

# 挡住重复申请的两种状态
BLOCKING_RETURN_STATUSES = {OPEN_RETURN_STATUS, APPROVED_RETURN_STATUS}
```

- `已通过` 必须在里面，而且它是最要紧的一个。审完之后这笔申请已经不是待审核了，只比 `待审核` 的话重复拦截会静默失效，同一笔订单能再申请一次，结果是两笔退款——而且是在"看起来一切正常"的情况下发生的。
- `已拒绝` 刻意不在里面。被拒绝之后应当允许重新申请（补了理由、时间过了、换了客服）。少了这一条，用户会撞上一个"你被拒绝过，所以永远不能再申请"的系统，而界面上没有任何一句话说明这件事。

两个方向相反，所以 `tests/orchestrator/test_return_review.py` 里必须各写一条：只写其中一条的话，另一种写法照样全绿。

### 5.3 幂等 + 竞态：一段代码里有两道闸

```python
if current["status"] != OPEN_RETURN_STATUS:
    return {"ok": True, "already": True, ...}   # 不覆盖，一个字段都不动

try:
    counts = db.transaction([
        ("UPDATE return_requests SET status = ? WHERE return_id = ? AND status = ?",
         (decision, current["return_id"], OPEN_RETURN_STATUS)),   # ← 第二道闸
        ("INSERT INTO return_reviews (...) VALUES (?, ?, ?, ?, ?)", (...)),
    ])
    if counts[0] == 0:
        raise _LostRace     # 必须抛出去，不能在这里 return
except _LostRace:
    return {"ok": True, "already": True, "message": "就在你确认的这一刻……"}
```

三个要点：

1. 幂等：审过的再审一次返回 `already=True`，note / reviewer 一个字段都不动。人的结论是证据，不是可以被后一次点击改写的草稿。这条语义和 `knowledge/review/queue.py` 的「人工定了就不再回退」是同一个。
2. `AND status = ?` 是第二道闸，堵的是 check-then-act 的竞态：`get_return` 读到"待审核"之后、这条 UPDATE 执行之前，另一个审核人（后台界面和 CLI 完全可能同时在跑）先把结论下了。少了它，后手会把人已经下的结论覆盖掉——按幂等规则那本来是不允许的，只是因为读了旧值才绕了过去。
3. `raise` 而不是 `return`：`return` 会正常提交，那条 review 痕迹就落下了，变成"有痕迹、但状态没被这次改动"——正是这个事务要防的东西。

"批准"到底做了什么，边界写死：

- 改 `return_requests.status`；插入 `return_reviews` 一行；两步在一个事务里。
- 不执行退款（没有支付网关可调，假装退款比不做更坏）。
- 不改 `orders.status`（退货通过 ≠ 订单状态变化；而且那个字段是数据源原值，改它就是在编造数据）。

### 5.4 审核痕迹放新表，不加列

`Database.init_schema()` 只做 `CREATE TABLE IF NOT EXISTS`，已经存在的库不会自动多出新列。所以给 `return_requests` 加三个列就得写迁移（SQLite `PRAGMA table_info` + MySQL `information_schema`），那会是这个仓库的第一个 schema 演进机制。

选新表的理由两条，都站得住：

1. 能不引入机制就不引入机制。这个项目里"删库重灌"一直是免费的（全是派生数据），所以从不需要迁移。为了加三列而引入第一个迁移机制，收益和分量不匹配。和 FLOWCHART 里「能用设计绕开的并发问题，就不该用锁去救」是同一条。
2. 这个理由今天不成立，但下个月就成立。一旦这套被演示过，`return_requests` 里就会有人下的结论。到那时再想加列，重灌库就等于抹掉人的决定。在一个只有派生数据的库上引入"删除即无损失"的隐含假设，是最容易留下的技术债。

`return_requests.status` 依然是唯一真相；`return_reviews` 只放审核痕迹（谁、什么时候、写了什么备注），一行都没有就代表还没审。

## 六、会话持久化

### 6.1 为什么不复用 `ask.py` 的 `SqliteSaver`

`ecom/knowledge/cli/ask.py` 已经有一套跑通的落盘会话（`SqliteSaver` + `thread_id`）。看着应该直接搬过来统一，但不该搬，三条理由：

1. `chat_history` 在 supervisor 里是"节点输入"，不是"图状态"。`answer()` 把它塞进 `make_initial_state`，`CSState.chat_history` 上没有 reducer。要让 checkpointer 接管，就得往图里加"累积历史"的逻辑。
2. 那样做会撞上 `state.py` 已经写明的陷阱：给 `chat_history` 加 `operator.add` 之后，每次 `invoke` 传入的初始值都会被 append 一遍而不是替换，历史里凭空多出重复轮次，而且不报错。
3. 两个图不是同一个图。`ask.py` 存的是知识库图的状态，supervisor 图是另一个对象，共用一张 `checkpoints` 表会让两种图的状态混在一个 `thread_id` 空间里。

对面的好处也要说清，否则这个决定没有分量：统一成一套的好处是"会话"这件事在整个项目里只有一个答案，新人只要学一次。代价是上面三条。

什么条件下该反过来选：如果 supervisor 以后要在图内部做需要记忆的决策（比如记住"这个用户上一轮已经在等人工了"），那就不是"历史作为输入"而是"历史作为状态"，那时候 checkpointer 才是对的。

所以：新建一张 `messages` 表，[ecom/orchestrator/session.py](../ecom/orchestrator/session.py) 自己开 sqlite，不用 `Database` 类。理由和 `review/queue.py` 一样：`Database` 的价值是双后端 + `?`→`%s` 翻译，而会话是纯 SQLite 的演示特性，接 MySQL 是过度设计；更重要的是 `Database.init_schema()` 硬编码了 orders 的 schema 路径，复用它反而要绕。

```sql
sessions(session_id PK, created_at, updated_at)
messages(id INTEGER PK AUTOINCREMENT, session_id, role, content, created_at)
CREATE INDEX idx_messages_session ON messages(session_id, id)
memories(id INTEGER PK AUTOINCREMENT, session_id, summary, keywords,
         embedding BLOB, through_message_id, created_at,
         UNIQUE(session_id, through_message_id))
CREATE INDEX idx_memories_session ON memories(session_id, id)
```

三张表都是 `CREATE TABLE IF NOT EXISTS`，老库天然兼容，这也是选新表策略的延续。

（`messages` 的列清单以前在这里写成还带一个 `request_id`，代码里从来没有这一列——一次请求的 trace 走 `logs/requests.jsonl`，不落到会话行上。顺手改掉。）

### 6.2 会话 id 是凭证，不是账号

这句话必须写在最显眼的地方：

> `_guess_customer`（[workers/order.py](../ecom/orchestrator/workers/order.py)）意味着"客户"是从话里猜出来的、未认证的。所以拿到 `session_id` 就能读到这个会话的全部历史。别把它当账号；要谈归属，前提是先有登录态——那是另一个项目。

推论三个，全都是有意的：

- 默认 30 天过期（`SESSION_TTL_DAYS`）。无主数据不该无限期留着。
- 界面刻意不把会话号放进 URL（不做 `st.query_params`）。它是 bearer token，进了 URL 就会进浏览器历史、代理日志、Referer 头。代价是新开一个标签页 = 新的一段对话。这个边界由 `test_a_new_browser_session_starts_a_new_conversation` 钉着——写成测试，是因为"没做的能力"最容易被下一个人当成 bug 顺手补上，而补法正好是那个不该做的。
- 侧边栏只显示前 12 位。侧边栏是最容易被截图发出去的地方。

### 6.3 三个旋钮不要合并

| 旋钮 | 管什么 | 性质 |
|---|---|---|
| `HISTORY_TURNS = 6` | 喂给模型多少原文 | 成本 |
| `SESSION_TTL_DAYS = 30` | 留多久 | 合规 |
| `MEMORY_TOP_K = 3` | 带几条记忆进 prompt | 成本（另一条通道） |

看起来都可以叫"留多少"，但它们改动的动机完全不同。合并成一个开关，会在有人想省钱的时候顺手把合规期限也改掉。

`HISTORY_TURNS` 和 `MEMORY_TOP_K` 同属成本，但是两条独立通道：前者是"最近几轮的原文"（精确但贵），后者是"更早那一段的摘要"（便宜但有损）。两者不是同一种东西的多少，所以不给它们一个共同的倍率。

`history()` 的实现是 DESC + LIMIT，然后 `reversed`，取的是最近的 N 轮，不是最早的 N 轮。截错方向不会报错，只会让模型拿到一段很旧的上文。这条有专门的测试（`test_history_keeps_the_most_recent_turns`）。

### 6.4 并发与过期

- `connect()` 用模块级缓存 + `check_same_thread=False` + 一个 `threading.Lock` 保护写，照 `trace.py` 的先例。（顺带修掉一个真缺陷：`api.py` 原来那个 `_SESSIONS` 字典连把锁都没有。）
- 过期只在两处触发：进程启动时调一次 `purge()`，以及 CLI 显式调用。不做懒加载式的"读的时候顺手删"，那会让读操作产生写副作用，出问题时极难定位。代价是长驻进程不会自我清理，得外挂一行 cron：

```bash
# 建议的 cron（长驻进程不会自己清）
17 4 * * * cd /path/to/ecom_cs && uv run python -m ecom.orchestrator.cli.session purge
```

### 6.5 会话内长期记忆：蒸馏 + 按需召回

`history()` 只带最近 `HISTORY_TURNS` 轮，所以聊到第 20 轮时，第 3 轮说过的订单号、诉求、结论都已经滑出窗口。这一层把滑出窗口的那一段压成一条摘要存进 `memories` 表，需要时按语义召回，拼在真实历史前面。实现在 [`ecom/orchestrator/memory.py`](../ecom/orchestrator/memory.py)，和 `session.py` 平级、不进 `core/`：它要联网（模型 + embedding），而 `session.py` 的定位是"只有 SQLite 的笨存储"（§6.1 那条边界），把网络依赖塞进去会让 `session.py` 的测试没法离线跑。

存"可执行的事实"，不是关键词。"超出范围就提炼成关键字另存"这个想法很自然，但它只能告诉你聊过什么话题，不能告诉你结论是什么，而多轮里真正要继承的恰恰是结论（"用户要为订单 52644 退货，但还没确认"）。所以 `summary` 写事实，`keywords` 只当索引：CLI 列表里给人扫一眼，不参与回答。蒸馏 prompt 明确禁止编造没出现过的订单号 / 金额——这条摘要以后会被当成事实喂给模型，编进去的东西没有人会再核一遍。

两个正交的切分。`out_of_window_messages()` 的上下界方向相反，缺一条就出错：

- 下界 `id > 已蒸馏到的最大 id`：蒸馏过的不再重复喂给模型。
- 上界 `id <= 会话最大 id - 窗口宽度`：还在窗口里的不蒸馏。它们下一轮会由 `history()` 原样喂给模型，再压一遍是重复付费，而且模型会读到一段自己有完整原文的删节版。

窗口宽度抽成私有 `_window_size()`（= `HISTORY_TURNS * 2`），不把算式散在 SQL 里。这个算式一处分叉，就会出现"记忆覆盖了窗口内的消息"或"有一批消息永远蒸馏不到"，两种都不报错。它和 `history()` 的 `LIMIT turns*2` 互补且不重叠，中间没有缝。

幂等由数据库保证，不是由锁保证。`session.py` 那把 `_lock` 是进程内的，而蒸馏是独立进程的 CLI：cron 撞上手动执行时，两边读到同一个水位线、蒸馏同一批、各插一条。`UNIQUE(session_id, through_message_id)` + `INSERT OR IGNORE` 让第二次成为 no-op。这就是水位线的用途，记住"已经蒸馏到哪条消息"，而不是"是哪条消息"。同理，模型没给出可用摘要时不写、水位线不推进（写一条空记忆会永远占着水位线，把这段对话彻底吞掉）；embedding 失败抛出去（绝不写一条没有向量的记忆，那条约等于"存在但永远选不上"，`list` 里看得到它，用户会以为它在起作用）。

召回时池子为空就一次 embedding 都不调。这是硬约束，两个理由：老会话（没跑过 distill）每问一句都白花一次调用；离线测试要能在没有记忆的库上跑。不设相似度阈值——池子是这个会话自己的、条数天然少，加一个没实测过的阈值只会静默丢掉记忆。

注入方式：不新增 `CSState` 字段。记忆以 `{"role": "memory", "content": ...}` 的形式由调用方拼在真实历史前面（`memory.augmented_history()`），照旧交给 `answer()`。省下十几个文件的改动不是主要理由，多一条要与 `chat_history` 长期保持同步的平行管道才是（少一个能分叉的地方才挡得住，见 `utils/ids.py` 的教训）。这个取舍靠三件事成立：

1. `answer.py::_format_history` 的 role 判定显式列出三种。原来是 `"用户" if role == "user" else "助手"`，`role="memory"` 会被静默当成"助手说过的话"——等于告诉模型"这是你自己刚说过的话"，它会当成自己的承诺。兜底用"（未知角色）"：认不出来就说认不出来，别替它编一个身份。
2. 每轮现拼、不落盘、不累积。`api.py` / `app.py` 每轮现读 `session.history()`，天然满足；但调用方必须守一条规矩，拿到返回值直接传给 `answer()`，不要再存回去。
3. 记忆不进 `messages` 表（`append_turn` 只写真轮次），所以它不会出现在 `cli.session show` 里，也不会被 `history()` 的 SQL 截断。

蒸馏放 CLI，不放问答路径上。放路径上意味着用户每问一句都可能多一次模型调用，而且是不可控的那种（第一次问就触发全量蒸馏）。收成显式命令之后，模型调用只在有人敲它的时候发生。代价说清：记忆不是实时的，要有人跑 `distill` 才更新。

```bash
uv run python -m ecom.orchestrator.cli.memory distill --session <id>   # 或 --all
uv run python -m ecom.orchestrator.cli.memory list    --session <id>
uv run python -m ecom.orchestrator.cli.memory recall  --session <id> "问题"   # dry-run，只读
```

`recall` 是必须要有的一条：召回是个黑盒，没有它，"线上为什么没带记忆"只能靠猜。这是本仓库「宁可暴露」的一贯做法（`router_source` 进 trace、`synth_source` 进 state 都是同一个理由）。它不并进 `cli/session.py`：那个是"看会话 / 删会话"，这个是"蒸馏 / 召回记忆"，触发者不同（一个运维，一个成本控制），混一个文件 `--help` 会变成一锅粥。

边界三条，都是有意选的：

- 记忆不参与写操作授权，和 §5 的"携带的订单号"同一条底线：摘要里的订单号是模型写的，拿它去提交退货等于替用户对一笔可能错的订单办事。所以一个只提"那笔订单"的追问，在 order worker 那里仍可能落到"请提供订单号"——这条路径宁可多问一次。（router 读得到记忆，所以它至少能被路由对：实测 `plan_reason` 里直接写明了"用户明确指代上文中的订单 52644"。）
- 这张表是会话内的，不是用户画像。按 `session_id` 键，跨会话一条都召不回来——理由和"不做用户画像"完全相同：先有身份，才谈得上画像。它不是"开始做画像"的先例。
- 换 embedding 模型会让已存向量失效。`_cosine` 遇到长度对不上返回 0.0（不抛），让这一条排到最后；没有模型版本号落点，也就没有自动重算。记为已知限制。

不引 numpy。浮点 → BLOB 用标准库 `array("f")`，`_cosine` 纯 Python。全仓库除 analytics 沙箱外没有数值栈（`embedder.py` 也没有），这是依赖边界的决定，不是性能取舍。

隐私：删会话必须连摘要一起删。`delete_session` / `purge` 都级联到 `memories`（不靠外键——SQLite 默认不开 `PRAGMA foreign_keys`，写了 `ON DELETE CASCADE` 也不生效，依赖一个默认关闭的开关是"今天对、换个环境就静默留垃圾"）。`delete_session` 的返回契约仍是消息条数（调用方在用它），`purge` 的返回多了 `memories` 计数——没被报出来的删除，等于没发生。删了会话却留着摘要，是隐私上的假动作。

蒸馏同样要外挂 cron：

```bash
23 4 * * * cd /path/to/ecom_cs && uv run python -m ecom.orchestrator.cli.memory distill --all
```

跑晚了只是记忆旧一点，跑漏了也不会丢消息（水位线没推进，下次接着蒸），所以它不挑时间，但不能指望它自己发生。

## 七、HTTP 接口与两个鉴权方向

[api.py](../api.py)

### 7.1 为什么全是 `def` 不是 `async def`

图里全是阻塞调用：openai SDK 是同步的、chromadb 是同步的、`subprocess.run` 是同步的。写成 `async def` 但里面调阻塞函数，会把事件循环堵死，那比老老实实用 `def` 更坏——FastAPI 会把 `def` 端点丢进线程池，`async def` 不会。

代价是并发上限就是线程池大小。这个项目是演示级的，接受。

### 7.2 错误体：结构化的，而且不泄露内部信息

```json
{"error": "请求格式不对，检查这些字段：question", "request_id": "dba7c82cddaa"}
```

三个处理器：`_on_http_error`（StarletteHTTPException）、`_on_bad_request`（RequestValidationError → 422，列出 `loc[1:]` 的字段名）、`_on_unhandled`（`logger.exception` 记全栈，返回一句人话 + request_id）。

异常原文绝不回给客户端，它可能带内部路径（测试里就用 `orders.sqlite` 这个词钉住了这件事）。`request_id` 是让用户报障时能和日志对上号的唯一线索。

### 7.3 两个鉴权方向故意相反

| | `api.py` 的 `API_KEY` | `admin.py` 的 `ADMIN_PASSWORD` |
|---|---|---|
| 不配时 | 放行，import 时打一条 WARNING | 拒绝启动（`st.error` + `st.stop`） |
| 理由 | 以读为主，面向"clone 下来就能 curl 一下" | 能对花钱的操作下结论 |
| 比较 | `secrets.compare_digest(x.encode("utf-8"), API_KEY.encode("utf-8"))` | 同 |

读可以默认开放，写必须默认关闭。默认值的方向不是风格问题：一个"以为配了其实没配"的后台，比一个明知裸奔的后台危险得多。

两个必须知道的细节：

- `compare_digest` 两侧都要 `.encode()`。它只吃 bytes，碰上非 ASCII 的 str 会直接抛 `TypeError`——而中文口令是很自然会被设出来的东西。
- HTTP 头只能装 ASCII。非 ASCII 的 `API_KEY` 任何客户端都发不出来（httpx 会抛 `UnicodeEncodeError`），结果是"配了等于没配"、每个请求都 401。所以 import 时有一条 WARNING 提醒。这个坑是测试跑出来的，不是想出来的。

`/health` 和 `/docs` 永远放行（健康检查不该需要凭证），而且它们不进依赖注入。别把 README 里"不填 Key 也能跑"理解成这个，那说的是模型的 Key（路由会退回关键词规则），和开不开鉴权是两码事。

## 八、后台管理端

[admin.py](../admin.py)，和 `app.py` 并列而不是嵌进去。

`app.py` 的 docstring 里写着「不做登录 / 权限：这是离线演示，加一套假登录只会让演示多几步点击」。那句话现在依然成立，因为后台不是它。把两者合成一个文件的那一天，那句注释就得划掉，而 `app.py` 的定位（面向客户的演示，clone 下来点开就能用）会被一个密码框毁掉。

### 8.1 门禁逻辑抽成一个不依赖 streamlit 的纯函数

```python
def check_password(entered: str, expected: str) -> bool:
    if not expected:
        return False        # 没配置就是"谁都别进"
    return secrets.compare_digest(entered.encode("utf-8"), expected.encode("utf-8"))
```

为什么必须抽出来：现有的假 streamlit 测试工具不记录关键字参数，`st.error("口令不对。")` 和 `st.error(msg)` 在调用记录里长得一模一样。想用"断言出现了 `st.error`"来证明"错误口令被挡住了"，那个断言证明不了什么。所以判断逻辑单独一个函数，由不依赖 streamlit 的单元测试盯着。

### 8.2 三个页面，只有一个能写

| 页面 | 能写吗 | 复用谁 |
|---|---|---|
| 退货审核 | ✅ | `admin/returns.py`（界面上不重写任何判断） |
| 订单与物流浏览 | ❌ 只读 | `order_tools.query_order` / `list_customer_orders`（不另写一份 SQL） |
| 知识库审核队列 | ✅ | `cli/review.approve_item`（复用那个留了很久没人用的接缝） |

订单页不另写 SQL，否则界面看到的和模型看到的迟早不一样。

### 8.3 端口绑定是密码之外的第二层

`docker-compose.yml` 里那个服务发布的是 `127.0.0.1:${ADMIN_PORT:-8502}:8502`，不是 `8502:8502`。

两层挡的不是同一件事：口令挡"能连到这个端口的人"，绑定挡"根本连不到这个端口的人"（同局域网的另一台机器、宿主上任何程序）。两层都要有。

副作用如实说：这也意味着它不能被反向代理从外面转发。真上线时得把那层代理自己接过来，而不是把这一行改回 `0.0.0.0`。

还有一处必须覆盖：健康检查。镜像里那份 `HEALTHCHECK` 探的是写死的 8501，admin 容器跑的是 8502，不覆盖的话它会永远报不健康，而服务其实是好的。这种"探针指着另一个端口"的错，看日志是看不出来的。

## 九、可观测与测试策略

### 9.1 三个观测面

- 日志（`logs/<date>.log`）：给人扫的。
- trace（`logs/requests.jsonl`）：一行一条请求，机器可读。记的是事实（路由来源、每个 worker 的 ok / 耗时 / token、最终决策），不是结论。"这次成功了吗"由查询方判断，口径变一次不用重跑历史数据。
- `GET /trace`：把最近若干条请求的决策链摊出来。

`main.py -v` 就是 trace 的人类可读版。

### 9.2 一条测试都不联网

不是图快。真调模型意味着测试结果随模型版本、网络、当天负载浮动，那样的测试没法规格回归，它昨天红今天绿，你只会学会忽略它。所有模型调用都用 `FakeLLM` / `ExplodingLLM` 顶掉。

这条规矩的代价要认：交互路径（打字触发一次真实问答）测试覆盖不到。它由另外两种方式补：假模块跑调用链（`test_app_smoke.py` / `test_admin_smoke.py`）、真运行时跑渲染（`test_app_real_streamlit.py`），以及一次性的人工验证（真起 uvicorn、真发请求，见 §10）。

### 9.3 四层测试，越往下越"真"，也越难跑

| 层 | 例子 | 覆盖到什么 |
|---|---|---|
| 单元 | `tests/orchestrator/…` | 纯逻辑，零外部依赖 |
| 假模块 | `test_app_smoke.py` / `test_admin_smoke.py` | 调用写得对不对（参数名、模块路径） |
| 真运行时 | `test_app_real_streamlit.py` | 真 Streamlit 里渲染会不会炸、`st.pills` / `st.status` 这些新调用认不认 |
| 开关式 | `test_milvus_live.py`（`ECOM_LIVE_MILVUS=1`） | 连外部服务时代码路径真的通 |

第四层默认 skip 是有意的：它连的是外部服务，默认跑会让 `pytest` 隐含地要求"先起一个 Milvus"，和"clone 下来就能跑测试"直接冲突。

### 9.4 两条"不用 import 业务代码"的测试

- `test_every_ecom_import_points_at_a_real_module`——只用 AST + 文件系统比对，把每条 `from ecom.x.y import z` 解析回真实文件。合并改了 270 处 import，其中约 55 处在本机跑不起来的子系统里，这条是它们唯一的保护。
- `test_the_analytics_worker_still_goes_through_a_process_boundary`——命令行里必须出现 `subprocess`，且不许直接 `import ecom.analytics`。

### 10.3 已知缺口

- 会话清理要有外挂的 cron，长驻进程不自清（见 §6.4）。这是"读操作不产生写副作用"换来的代价，是取舍不是遗漏。
- 长驻进程只在自己启动时清一次。同一台机器上跑三个副本，它们各自清各自的。
- `_guess_customer` 是从自然语言里猜客户号的 demo 将就。真系统里客户身份来自登录态，绝不从话里猜——那等于让任何人问出别人的订单。
- 进程内 worker 的"超时"只是不再等它。Python 杀不掉正在跑的线程。它保护响应时间，不保护资源占用。
- `KB_MIN_SCORE` 在换语料后基本常开（可答 0.523~0.781、不可答 0.431~0.707 两段糊在一起，没有任何阈值能把它们分开）。原因是语料同质化了。但这不构成调高阈值的理由——调高会一次性误伤那 15 条可答题。取 0.5 依旧是"宁可漏报"。
- 跨轮指代消解只覆盖"订单号"这一种实体，而且只在指代词出现时才触发。原来这条是"路由不解析代词回指"（真跑发现的）：带历史追问「那它的金额是多少」，历史确实进了 prompt（in 从 257 涨到 387），但路由第一层是关键词规则，`plan` 是空的，答了"没听明白"。现在修了：判定集中在 [utils/entities.py](../ecom/orchestrator/utils/entities.py) 的 `carried_order_id`，router 的规则层和 order worker 都用它。注意它是"携带上一轮提到的实体"，不是往关键词表里加几个词——加词会让一个纯政策问题被拉去查订单。边界三条，都是有意的：只有订单号会被携带（金额、商品名没做，那要的是字段级消解）；读操作可以回退到携带来的号，写操作 `create_return` 不可以，猜出来的号退回"请提供订单号"，所以「订单 52644 到哪了」→「那能退吗」会答"如果要为订单 52644 提交退货申请，回一句确认"，而不会自动提交；代价是「那我要退货」这种明确诉求也不用携带来的号，用户得再说一次订单号，拿"少问一次"换"绝不对错误订单办事"。携带窗口 = 最近 `HISTORY_TURNS` 条用户发言。它不解决"聊久了早期信息滑出窗口"——那是另一件事（会话内长期记忆，见 §6.5）。
- 会话内长期记忆不是实时的，也不参与写操作。摘要只在有人跑 `cli.memory distill` 时才长出来（问答路径上刻意不蒸馏，见 §6.5），所以要外挂 cron；不设召回相似度阈值；换 embedding 模型会让已存向量失效（没有版本号落点，也就没有自动重算）；记忆里的订单号不能拿来办写操作。这张表按 `session_id` 键，是会话内的，不是用户画像，它不是"开始做画像"的先例。
- Milvus 客户端与服务端版本错位：本机服务端 v2.5.5，而 `pyproject.toml` 把 pymilvus pin 在 `>=2.6,<3`、compose 里是 `v2.6.24`。实测这几个接口能用，但这条对应关系没有保证。

## 十一、怎么跑

粗略的命令在 [README 的「跑起来」](../README.md#跑起来)。这一节是逐步版：每一步都写清"这一步为什么需要""怎么算成功了""失败了先看哪里"，以及这台机器上特有的前提（最后两个坑）——那两条换个环境就不会遇到，所以只能写在这里，读代码推不出来。

### 本机直接跑（不需要 Docker）

```bash
cp .env.example .env      # 至少填 QWEN_API_KEY 与 SILICONFLOW_API_KEY
uv sync --extra ui        # 界面；--extra api 给 HTTP；--extra milvus/mysql/search 按需
uv run python main.py --init-db                    # 灌 65752 笔订单
uv run python -m ecom.knowledge.cli.ingest         # 建向量库
uv run python main.py "订单 52644 到哪了" -v
```

不填 `QWEN_API_KEY` 也能跑：路由退回关键词规则，订单那一路完全不依赖模型。

> ⚠️ 在开发这台机器上这条走不通——宿主直连 PyPI 不通，`uv sync` 会在解析依赖那一步卡住。所以下面那条 Docker 路径不是"可选"，是这台机器上唯一能用的那条。写在这里是因为这份文档不只给这台机器看，而"哪条路在什么前提下成立"必须说清楚。

### 四个入口

| 入口 | 命令 | 给谁 |
|---|---|---|
| `main.py` | `uv run python main.py "问题" -v` | 排查问题（第一入口） |
| `app.py` | `uv run streamlit run app.py` → 8501 | 演示 |
| `admin.py` | `uv run streamlit run admin.py` → 8502 | 下结论（退货审核） |

### 用 Docker（本机 PyPI 不通时走这条）

下面这七步是在开发这台机器上实测跑过一遍的（2026-10-11），所以每一步都写了"怎么知道它成了"。前两步的顺序不能换，理由见第 1 步。

**第 1 步：先建镜像，再起容器。**

```bash
docker compose build app
```

不要跳过，也别指望 `up -d` 替你建。`docker compose up -d` 只在镜像不存在时才构建；镜像一旦在，它就直接拿来用。这是实际踩到的一条：镜像是 15:41 建的，而修好的代码是 16:54 提交的，`up -d` 会静悄悄起一份没有那些修复的旧代码，而界面上、日志里都看不出任何区别。镜像是 `COPY . /app`，`admin` 服务共用同一个 `ecom-cs:local`。

想确认镜像确实比代码新：

```bash
docker image inspect ecom-cs:local --format '{{.Created}}'   # 这个时间要晚于 git log -1 的时间
```

**第 2 步：起服务。**

```bash
docker compose up -d
# 本机有端口冲突时（见下面「本机特有的两个坑」）加一个变量：
APP_PORT=8600 docker compose up -d
```

怎么算成了：`docker compose ps` 里 app 和 admin 都是 `Up ... (healthy)`。

**第 3 步：灌数据 —— 只有干净 clone 才需要，本机跳过。**

```bash
docker compose run --rm app python main.py --init-db              # 65752 笔订单 + 62897 条物流
docker compose run --rm app python -m ecom.knowledge.cli.ingest   # 建向量库
```

这两步为什么不是可选项：`data/` 不入仓（在 `.gitignore` 里），所以 `git clone` 下来的仓库既没有订单库也没有向量库。界面照样能打开、四个视图照样能切，但每一次提问都会因为查不到数据而答非所问，这是最容易误判成"RAG 写坏了"的一种状态。

⚠️ 本机已经灌过了，不要再跑 `--init-db`。它做的是 `DELETE FROM logistics / orders / return_requests`（`db/seed.py:104-106`）然后再灌一遍，也就是会清掉退货申请。（`return_reviews` 审核痕迹表不在删除列表里，这是一次"审核记录不该被重灌数据抹掉"的选择。）本机现状：`orders` 65752 行、`logistics` 62897 行、`data/knowledge/vector_store/chroma.sqlite3` 约 7MB。

**第 4 步：打开界面。**

```
http://localhost:8501   客户界面（本机改成 APP_PORT=8600 的话就是 8600）
http://127.0.0.1:8502   后台
```

怎么算成了：`curl -s -o /dev/null -w "%{http_code}" http://localhost:8501/` 回 `200`。但 200 只证明 Streamlit 活着，不证明业务是好的，真正的判据是下一步。

**第 5 步：真问一句（这一步才证明整条链路通）。**

```bash
docker compose run --rm --no-deps -T app python main.py "订单 52644 到哪了" -v
```

实测输出（2026-10-11）：

```
路由：订单 52644 到哪了 → ['order']（llm，置信度 0.95）
订单 52644 的物流：目的地 San Salvador，当前「Late delivery」，最近更新 2017-02-12 11:11。
决策：answer（1 个单元给出结论，汇总方式 concat）
耗时 1490 ms　token {'in': 257, 'out': 29}
```

看路由那一行是 `llm` 而不是 `rule`。是 `rule` 只说明它退回了关键词规则，而那条路不需要 key，所以"答出来了"并不等于"模型配好了"。

**第 6 步：后台要先配口令。**

```bash
# .env 里加一行
ADMIN_PASSWORD=你自己的口令
docker compose up -d admin
```

本机这份 `.env` 里目前没有 `ADMIN_PASSWORD`，所以 admin 容器是 healthy 的，但打开 8502 只会看到「没有配置 ADMIN_PASSWORD，后台拒绝启动」。这不是坏了，是刻意的 fail closed（`admin.py:85-93`）。

门禁逻辑被抽成了一个不依赖 streamlit 的纯函数，所以这件事不用开浏览器就能验：

```bash
docker compose run --rm --no-deps -T app python -c "
from admin import check_password
print(check_password('随便什么', ''))   # False —— 没配口令，谁都进不去
print(check_password('abc', 'abc'))     # True
"
```

**第 7 步：停。**

```bash
docker compose logs -f app    # 看日志
docker compose stop           # 停，保留容器
docker compose down           # 停并删容器（data/ 是 bind mount，数据不动）
```

### 本机特有的两个坑

这两条不是这套代码的通用问题，是这台机器上的前提。写下来是因为它们的症状都很像"代码坏了"，但实际都不是，换个环境就不会遇到，所以靠读代码永远推不出来。

**一、8501 被隔壁那个 RAG 项目占着。** 本机常年跑着 `rag_knowledge_base` 的 Streamlit（容器名 `rag-kb-app-1`，绑在 `0.0.0.0:8501`），于是 `docker compose up -d` 会报 `Bind for 0.0.0.0:8501 failed: port is already allocated`。注意它报的是 `0.0.0.0`，看着像 compose 配置写错了，其实是那个老容器的绑定。

```bash
docker ps --filter "publish=8501" --format "{{.Names}} | {{.Ports}}"   # 先看是谁
APP_PORT=8600 docker compose up -d app                                 # 换个口，不动它
```

（`ADMIN_PORT` 同理，后台默认 8502。）

**二、这台机器上走代理的只有 git，curl 不走。** git 的全局配置里有 `http.proxy = https.proxy = http://127.0.0.1:7897`（Windows 系统代理也是它），所以 `git push` / `git ls-remote` 连得上 GitHub；而 `curl https://api.github.com/` 会返回 HTTP 400、`curl https://github.com/` 直接连不上（exit 56）。症状看着像"被墙"，其实是 curl 没读那个代理。要 curl 也走：

```bash
curl -x http://127.0.0.1:7897 https://api.github.com/
```

这条值得单记一笔，因为它会伪装成别的问题：`gh` 也走 `api.github.com`，所以不设代理时 `gh auth login --with-token` 报的是 `error validating token: HTTP 400: 400 Bad Request`，那个报错字面上完全看不出是代理的事，会让人一路去怀疑 token 失效、scope 不够。

### 后台的第一次使用（以及没有界面时的等价物）

配口令那一步见上面第 6 步，这里只讲不开浏览器时怎么办——排障、写脚本、在容器里看一条退货现在卡在哪，都用这一组：

```bash
uv run python -m ecom.orchestrator.cli.returns stats
uv run python -m ecom.orchestrator.cli.returns list --status 待审核
uv run python -m ecom.orchestrator.cli.returns approve R1 --note "客户提供了照片" --reviewer 张三
uv run python -m ecom.orchestrator.cli.session list
uv run python -m ecom.orchestrator.cli.session purge --days 30
uv run python -m ecom.orchestrator.cli.memory  distill --all
uv run python -m ecom.orchestrator.cli.memory  recall --session <id> "问题"   # dry-run，看召回哪几条
```

（在容器里跑就把 `uv run python` 换成 `docker compose run --rm --no-deps -T app python`。）

它和后台界面调的是同一份 `admin.returns` 里的函数，不是两套逻辑。这也是它值得存在的理由：界面那层的门禁、session_state、页面路由都可能出问题，而 CLI 这条路径上它们一个都不在，所以"后台点不动"时，用 CLI 走一遍就能分清是业务逻辑坏了还是界面那层坏了。

### 跑测试

```bash
uv run pytest                 # 555 条，宿主 .venv 实测：553 passed / 2 skipped
uv run ruff check .
# 要连真 Milvus 的那两条（默认 skip）：
```

这个数要在装了全部 extra 的环境里跑才算得准。宿主上少几个包时是 505 条 / 499 passed / 2 failed / 4 skipped（那 2 条红是宿主没装 matplotlib）。
