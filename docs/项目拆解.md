## 一、项目定位与全景

### 1.1 它解决什么问题

电商客服的问题有三类来源：

| 来源 | 例子 | 正确做法 |
|---|---|---|
| 文档 | 「七天无理由怎么算？」 | 检索法规/政策原文，带出处回答 |
| 数据库 | 「订单 52644 到哪了？」 | 查订单 + 物流，毫秒级返回 |
| 实时计算 | 「哪个地区退货率最高？」 | 生成 pandas 代码，执行，出报告 |
| 写操作 | 「我要退订单 52644」 | **只登记待审核，人来做最终决定** |

真实用户不会按这个分类说话：「订单 52644 到哪了，顺便问下退货政策」一句话两个需求。
所以系统的核心不是「让模型会聊天」，而是：

> **判断该找谁办 → 真的去查/去算 → 把结果合成一句诚实的话。**

### 1.2 一句话架构

**LangGraph Supervisor + 三个 Worker + 一个汇总节点**，外面套四个入口和一条 MCP 出口：

```
                    ┌──────────── 入口 ────────────┐
                    │ CLI / Streamlit / FastAPI / React │
                    └──────────────┬───────────────┘
                                   ▼
START → router ─┬→ knowledge ─┐
                ├→ order     ─┼→ aggregate → END（answer / human）
                └→ analytics ─┘       │
                     ▲                │ decision == "re_route"
                     └────────────────┘

MCP 客户端 ──stdio──→ ecom/mcp/server.py → tools.py → order_tools / knowledge
```

两条路**共用业务函数，不互相调用**：自然语言入口需要路由，结构化 MCP 调用不需要。

### 1.3 关键数字

| 类别 | 数字 |
|---|---|
| 编排 | 1 个 router、3 个 worker、1 个 aggregate；`MAX_ROUNDS=2`；`recursion_limit` 默认 14 |
| 超时 | knowledge 90s / order 20s / analytics 180s；路由单次 8s、总预算 20s；汇总 60s |
| 路由 | 3 层（LLM → 规则 → 默认 knowledge）；置信度下限 0.6；上文 2 轮 × 160 字 |
| RAG | chunk 512 / overlap 50；向量 Top-20 + BM25 Top-20 → RRF(K=60) → Top-5 → rerank → Top-3 |
| 评测 | 152 题 Recall@5 = 78.3%、MRR = 0.533；40 条答案忠实性 83.0%；不可答弃答 9/10 |
| 语料 | 10 篇法规 + 7 篇示例；184 个 chunk |
| 订单 | 65,752 笔订单；62,897 条物流 |
| 会话 | `HISTORY_TURNS=6`；TTL 30 天；`MEMORY_TOP_K=3`；蒸馏上限 40 条消息 |
| 测试 | 747 条 / 745 passed / 2 skipped（2026-10-30 宿主 `--all-extras` 实测） |

### 1.4 明确不做的事

这些不是「没来得及」，是当前版本的边界，写在代码和文档里：

- 不做登录 / 多租户 / 用户画像：`_guess_customer` 是从话里猜客户号，不是身份系统。
- 不做自动退款：退货只登记「待审核」，批准是人通过 `admin.py` / CLI 做的。
- 不做强隔离沙箱：AST 白名单 + 受限 builtins + 进程边界，挡模型写错，不挡故意攻击。
- 不做多副本：会话、预算账本、订单库都可以是本地 sqlite；横向扩展要换共享存储。
- 不做知识库自动回写：模型生成的答案进人审队列，人批准后才成为语料。
- MCP 只做 stdio，不做 HTTP 传输 / OAuth / 远程鉴权。

### 2.2 包与职责

| 包 | 职责 | 不负责 |
|---|---|---|
| `ecom.orchestrator` | 路由、worker 调度、汇总、会话、记忆、订单工具、后台审核 | 文档切片、向量检索、数据分析实现 |
| `ecom.knowledge` | 语料 → chunk → 向量库；混合检索、rerank、生成、评测、人审队列 | 多轮客服会话、订单写操作 |
| `ecom.analytics` | 自然语言 → pandas 代码 → 沙箱执行 → 报告、图表 | 客服路由、会话存储 |
| `ecom.mcp` | 把订单/知识库能力按 MCP 协议暴露 | Supervisor、写审核、数据分析 |
| `ecom.demo` | 跨入口的演示策略 | 真正的权限系统 |

### 2.3 依赖方向

```
entrypoints (main/app/api/admin/frontend)
        │
        ▼
ecom.orchestrator.core  ──→  ecom.orchestrator.workers
        │                        │        │
        │                        │        └──→ ecom.analytics（子进程）
        │                        └───────────→ ecom.knowledge（进程内）
        ▼
ecom.orchestrator.db / session / memory / tools
        │
        ▼
ecom.settings（根路径与模型配置）
```

三条约束：

1. **底层不反向 import 入口。** `ecom.*` 不知道 Streamlit / FastAPI 的存在。
2. **知识库与数据分析不 import supervisor。** 它们是库，可以被 CLI、评测、worker 各自调用。
3. **MCP 不 import supervisor。** 它只调业务函数；`tools.py` 甚至不 import MCP SDK
   （SDK 只在 `server.py` 里出现），所以工具测试不需要装 `mcp`。

## 三、四条主链路

### 3.1 CLI：`main.py`

```
argv
 ├─ --init-db        → db.seed.seed() 重建订单库
 ├─ 有位置参数        → 单次问答
 └─ 无位置参数        → 交互循环
        │
        ▼
supervisor.answer() / answer_stream()
        │
        ▼
show()：正文 + 来源 +（--verbose）路由/每个 worker 的耗时与结论 + 决策
```

`--json` 只输出一行 JSON，给脚本用；`--stream` 与 `--json` 互斥，因为流式输出不是
一个完整的 JSON 文档。CLI 是第一入口的原因写在 `main.py` 顶部：**界面会把「哪一层慢、
哪一层挂了」藏起来**，CLI 把决策链摊在眼前。

### 3.2 Streamlit 客户界面：`app.py`

四个视图：

| 视图 | 调什么 | 说明 |
|---|---|---|
| 对话 | `answer_stream()` | 多轮，会话号在 `st.session_state`；图片可选 |
| 订单 | `query_order()` / `list_customer_orders()` | 直接查库，不走 supervisor |
| 数据分析 | `run_analytics()` | 走子进程，和 worker 同一条边界 |
| 知识库 | `retrieve` / `rerank` / `generate_answer` | 直接调用，展示检索与引用 |

对话视图的请求顺序：

```
用户输入（可选图片）
  → understand_image() → ImageIntent → augment_question_with_image()
  → session.ensure_session() / history()
  → memory.augmented_history()（记忆拼在历史前面，不落盘）
  → answer_stream()
  → 逐 delta 渲染；final 到达后用 final.answer 覆盖
  → session.append_turn()（先答完再落盘）
```

### 3.3 HTTP：`api.py`

| 端点 | 方法 | 鉴权 | 说明 |
|---|---|---|---|
| `/health` | GET | 无 | 只报组件在不在，不 ping 模型 |
| `/chat` | POST | `X-API-Key` + 演示邀请码 | 一次返回完整 JSON |
| `/chat/stream` | POST | 同上 | SSE：`start` / `delta` / `final` / `error` |
| `/trace` | GET | `X-API-Key` | 最近请求的决策链；演示模式返回 404 |
| `/ui` | GET | 无 | `frontend/dist` 存在时才挂载 |

两个鉴权方向故意相反：

- `/chat` 的 `API_KEY`：**不配就放行**（读接口，默认开放）；
- `admin.py` 的 `ADMIN_PASSWORD`：**不配就拒绝启动**（写入口，默认关闭）。

`def` 而不是 `async def`：模型调用、sqlite、子进程都是阻塞的；FastAPI 会把同步端点
丢进线程池，不会堵事件循环。

### 3.4 MCP：`python -m ecom.mcp.server`

```
客户端拉起进程
  → server.build_server() 按开关注册工具
  → stdio 上跑 JSON-RPC
  → @server.tool() 工具调用 ecom/mcp/tools.py
  → tools.py 调 order_tools / knowledge 检索
  → 统一信封返回
```

MCP 不经过 Supervisor、不做会话、不跑数据分析。细节见第十二节。

## 四、编排层拆解

### 4.1 `CSState`：哪些是状态，哪些只是输入

`ecom/orchestrator/core/state.py`：

| 字段 | 语义 | 谁写 |
|---|---|---|
| `question` | 当前问题（已截断到 `MAX_QUESTION_CHARS`） | 入口 |
| `chat_history` | 节点输入，不是图状态；图不累加 | 调用方 |
| `plan` / `plan_reason` / `plan_confidence` / `router_source` / `router_tokens` | 本轮路由结论 | router |
| `tried` | 跨轮累积的已试 worker | router |
| `round` | 第几轮，从 1 起 | router |
| `results` | `Annotated[list, operator.add]`，并行 worker 追加 | worker 节点 |
| `decision` / `decision_reason` / `answer` / `sources` | 汇总结论 | aggregate |
| `synth_source` / `synth_tokens` | 汇总是否用了模型、花了多少 | aggregate |
| `pending_note` | 重路由时带走的澄清话术 | aggregate |
| `request_id` | 全链路追踪 id | supervisor |

三个容易踩的点：

1. **`results` 清不掉。** `operator.add` 的语义是追加；往它写 `[]` 等于没写。
   所以每条结果用 `stamp_round()` 盖上轮次，aggregate 用 `round_results()` 挑本轮。
2. **`tried` 只在 router 写。** 三个 worker 并行，让它们各写一次 `tried` 就是三个
   节点同时写同一个无 reducer 的键，LangGraph 会直接报错。
3. **`chat_history` 是输入不是状态。** 不配 reducer、不累积；这样「留最近 N 轮」
   才能由调用方控制。checkpointer 那套（持久化整份 state）不适合这里。

### 4.2 router：三层路由

```
LLM 分类（temperature=0）
   ├─ 超时 8s / 总预算 20s / 最多 3 次解析尝试
   ├─ 解析结果清洗：未知 worker 丢弃、置信度 clamp 到 0~1
   └─ 失败 / 解析不出 → 规则
规则兜底
   ├─ 订单号形状 → order
   ├─ 关键词表 → order / analytics / knowledge
   └─ 上一轮携带的订单号（指代） → order
默认
   └─ knowledge
```

几个设计点：

- **低置信补 knowledge。** 漏调一个 worker = 少答一半；多调一个 = 多花一次调用。
  代价不对称，所以低于 0.6 时宁可多带一个安全的。
- **路由也读上文。** 「那能退吗」光看当轮判断不了主语；LLM 层拿到最近 2 轮 × 160 字，
  规则层走 `carried_order_id()`。这不是往关键词表里加代词。
- **演示模式过滤。** 提示词里不列 analytics，规则层和最终计划还会再过滤一次；
  提示词是建议，不是保证。
- **`router_source` 必须记录。** 规则兜底比例一涨，说明 LLM 那条路在坏。

### 4.3 worker 契约与调度

统一形状（`state.WorkerResult`）：

```python
{
    "worker": "knowledge",
    "ok": True,              # 调用本身成功
    "answer": "...",         # 给人看的结论
    "data": {...},           # 结构化结果
    "sources": [...],        # 出处
    "insufficient": False,   # 成功但没答上来
    "error": "",
    "elapsed_ms": 123,
    "tokens": {"in": 0, "out": 0},
    "round": 1               # stamp_round 加的
}
```

`ecom/orchestrator/workers/base.py::run()` 负责：

1. 从注册表取函数（延迟 import，避免 import supervisor 就拉起 chromadb/matplotlib）；
2. 放进 daemon 线程，`join(timeout)`；
3. 超时 → `ok=False`；异常 → `ok=False`；返回值 → 合并成 `ok=True`。

**超时的真实含义**：analytics 走子进程，超时是真杀；knowledge/order 是进程内，
超时只是「不再等它」，线程会自己跑完。不要把它说成「所有 worker 都能中断」。

### 4.4 aggregate：四步决策树

顺序不能换：

```
① usable 非空                → answer（合并 usable；failed/thin 作为尾注）
② 无结论，但可重试           → re_route
   can_retry = plan 非空 & untried 非空 & round < MAX_ROUNDS & alive
③ 无结论，但手上有话（澄清/故障说明） → answer（必要时补 HANDOFF）
④ 什么都没有                 → human
```

`_split()` 把结果分三堆：

| 桶 | 条件 | 用途 |
|---|---|---|
| `usable` | `ok=True`、`insufficient=False`、正文非空 | 真正要汇总的结论 |
| `thin` | `ok=True`、`insufficient=True` 或正文为空 | 澄清话术/故障说明，不能当正文拼接 |
| `failed` | `ok=False` | 说明这块不可用，不触发重路由 |

两个关键判断：

- **`ok=False` 不重路由，`insufficient=True` 才重路由。** 坏了换人大概率还是坏；
  看过了没有，换一个单元才有依据。
- **只有一个结论不调 LLM。** 没有东西可合并时调模型，只会多一次幻觉机会。

### 4.5 图的结构与有界回环

`ecom/orchestrator/core/supervisor.py`：

```
START → router → worker_knowledge ┐
              → worker_order     ┼→ aggregate → END
              → worker_analytics ┘        │
                    ▲                     │ re_route
                    └─────────────────────┘
```

- 三条边是静态的；不在计划里的节点执行一次 `if` 就返回 `{}`。并行是 LangGraph
  同一超步白拿的，不需要写并发代码。
- `MAX_ROUNDS=2` = 首轮 + 最多一次重路由；`recursion_limit = MAX_ROUNDS * 4 + 6`，
  默认 14，是编译器层面的兜底。
- aggregate 只在本轮无结论且还有未试单元时才给 `re_route`，所以图上虽然有环，
  实际有界。

### 4.6 收尾：`_finalize()`

流式和非流式共用这一份：

1. **token 汇总所有轮次**：每条 worker 结果 + `router_tokens` + `synth_tokens`。
   只算最后一轮会让成本表偏低。
2. **写一条 trace**：`request_id`、问题前 200 字、plan、轮次、路由来源、置信度、
   决策与理由、汇总方式、来源、每个 worker 的摘要、token。
3. **打一条日志**：轮次、决策、token。

「加了一条流式路径」没有变成「两份成本账」，就是因为收尾只有这一处。

## 五、三个 Worker 逐个拆

### 5.1 knowledge worker：进程内的纯库

`ecom/orchestrator/workers/knowledge.py` 只做四步：

```
retrieve(question, get_vector_store())   # 混合检索，内部含向量 + BM25 + RRF
rerank(question, hits)                   # 三级降级，最差按分数截断
generate_answer(question, top, [], history)
sources = 去重后的 top 来源
```

关键边界：

- **只拿四个入口，不跑知识库的图。** 调用 `retrieve` / `rerank` / `generate_answer` /
  `get_vector_store` 四个函数，不调 `build_graph()`。原因是 `answer_node` 里会
  `record_question()`，把每次客服提问都塞进人审队列——线上每问一句塞一条，队列就废了。
- **最低相似度看 `vector_score` 不看 `score`。** `score` 是 RRF 融合分，量纲约
  0.03；拿它比 `KB_MIN_SCORE=0.5` 永远为假。余弦在 `vector_score` 里。
- **生成侧兜底文案 = 坏了。** `ANSWER_FALLBACK` 出现时抛异常，让 base 记 `ok=False`，
  而不是当成「知识库没答上来」去重路由。
- **进程内而不是子进程。** 它是热路径、纯库、无副作用；子进程要多付解释器启动和
  chromadb 初始化。和 analytics 的接法不同是算账结果，不是不一致。

### 5.2 order worker：规则优先 + 写操作闸门

这是全仓库业务规则最密的一个文件。

**（1）意图提取**

```
strip_image_block(question)          # 先摘掉图片块
image_order_id(question)             # 单独取图片里的号
sanitize_image_text(image_request)   # 图片诉求里的号替换掉
        │
        ▼
_rule_extract()                      # 订单号正则 + 动作词表
        │  action 或参数不全
        ▼
_llm_extract()                       # JSON：action / order_id / reason
        │
        ▼
_apply_carry()                       # 补上一轮携带的号 / 图片里的号，标来源
```

为什么规则优先：认订单号是「5 位以上数字」的形状问题，正则 100%，LLM 约 95%，
还会把「2025 年」认成订单号；认操作类型是中文口语问题，LLM 更合适。

**（2）订单号来源**

```python
order_id_source ∈ {"question", "context", "image", ""}
```

- `question`：用户当前消息里手打；
- `context`：从 `chat_history` 携带；
- `image`：视觉模型从图片里认出来。

只有 `question` 能触发写操作。`context` 和 `image` 都只能用于读。

**（3）写操作的几道闸**

| 顺序 | 闸 | 挡什么 |
|---|---|---|
| 1 | 规则层：`CREATE_RETURN_HINT` 且非 `policy_question` | 「退货政策是什么」不被当成「我要退货」 |
| 2 | `guessed`（source ∈ context/image） | 猜来的号/图里认的号不写 |
| 3 | `demo.writes_allowed()` | 公网演示只读 |
| 4 | `policy_question()` 二次确认 | 模型把政策问法听成退货 |
| 5 | `order_tools.create_return()` 的状态/重复校验 | 状态不可退、已有待审核/已通过申请 |

第 4 道会返回一句「确认申请退货」的澄清话术，`insufficient=True`，让 aggregate
有机会交给知识库答；明确要求办理时直接说「只读演示不能办」。

**（4）业务失败 vs 系统失败**

- 订单不存在、状态不可退、重复申请 → `ok=True`，answer 如实说明；
- 查库超时、连不上库 → `ok=False`。

混在一起，监控上就分不清「业务规则拦了多少」和「系统坏了几次」。

**（5）跨轮指代**

`utils/entities.carried_order_id()` 判断「这一轮用了指代词，且上一轮提过订单号」。
判定只写一份；router 和 order worker 都调它。写操作不使用携带号，但澄清问句可以用
——它只问不做，猜错用户当场能纠正。

### 5.3 analytics worker：真的能杀死的子进程

```
sys.executable -m ecom.analytics.cli.analyze "<question>"
  cwd=ROOT
  env: PYTHONIOENCODING=utf-8
  timeout = WORKER_TIMEOUT["analytics"] - 5   # 让子进程先超时，错误信息更明确
```

- **为什么走子进程**：它执行模型生成的代码；沙箱不做超时，`while True` 拦不住；
  子进程 `subprocess.run(timeout=)` 到点是真杀。它还可能跑几分钟，进程内会占着
  supervisor 的线程和内存。
- **stdout 解析**：从后往前找第一行能解析的 JSON，不假定「整个 stdout 就是一行」。
- **错误契约**：子进程返回 `ok=False` 或没有可解析 JSON → 抛 `RuntimeError` →
  base 记成 `ok=False`；报告为空 → `insufficient=True`。
- **审查标记**：`review_passed=False` 时报告仍返回，但日志告警、`data` 里带标记，
  不让它看起来像一次干净的成功。
- **图表路径**：相对路径会按 `ROOT` 解析成绝对路径再返回。

## 六、RAG 子系统

### 6.1 建库链路

```
data/knowledge/documents/*.md
  → document_loader/splitter.py      chunk 512 / overlap 50
  → embedding/embedder.py            BGE-M3，1024 维，批 32
  → vector_store/{chroma,milvus}_store.py
        Chroma：默认，嵌入式，零外部依赖
        Milvus：VECTOR_BACKEND=milvus + docker compose --profile milvus
```

两个后端共用同一份契约（`vector_store/base.py`）：`add` / `search` / `all_chunks` /
`delete` / `close`。契约测试对两个后端跑同一组用例（Milvus 那组默认 skip）。

### 6.2 检索链路

```
             ┌─ 向量召回 Top-20（余弦） ─┐
question ────┤                            ├─ RRF(K=60) ─→ Top-5 ─→ rerank ─→ Top-3
             └─ BM25 召回 Top-20 ────────┘                 BGE-reranker-v2-m3
```

- **BM25 在应用层实现**，不依赖向量库：Milvus 2.5+ 有内置 BM25，Chroma 本地版没有；
  自己实现才能让两个后端行为一致。
- **RRF 只用名次**，避免「余弦 0.3~0.7」和「BM25 0~20+」两个量纲强行归一化。
  两路默认等权；`RRF_WEIGHT_*` 可调，但默认不加权——留出集上没看到稳定收益。
- **rerank 三级降级**：硅基流动 API → 本地 CrossEncoder（可选依赖）→ 按向量分数截断。
  任何一级失败都不会让检索链路断。
- **降级语义**：向量路失败必须抛；BM25 失败只降级。前者是主路，后者是增强。

### 6.3 生成链路

`ecom/knowledge/generator/answer.py`：

- 知识库结果和联网结果分栏拼进 prompt，带 `[1] [2]` 编号；
- 系统提示要求「只依据资料」「资料没有就说没有」「冲突时优先知识库」；
- 历史角色显式列三种：`user` / `assistant` / `memory`；未知角色标「（未知角色）」，
  不静默当成助手——记忆被当成助手承诺是真实踩过的坑；
- 支持流式（`streaming.emit`），拼回的全文才是 `state["answer"]`，流式只改变
  「什么时候看到」，不改变「答案是什么」。

### 6.4 评测与人审

| 工具 | 作用 | 关键点 |
|---|---|---|
| `eval_set.jsonl` | 152 题检索评测 | 真值来自 chunk 级标注，不是模型生成 |
| `gold_set.jsonl` | 人工金标准 | `gold_set.py build/label/report`，分层抽样 |
| `answer_eval.jsonl` | 答案忠实性/相关性 | 40 条，judge 判定 + 人工校准 |
| `unanswerable_questions.jsonl` | 不可答弃答 | 10 条，验证「不知道就说不知道」 |
| `review_queue.db` | 人审队列 | 模型答案不直接回写语料，人批准才落地 |

评测的原则：**真值必须独立计算**。分析侧有一条测试用 AST 守白名单，禁止评测真值
import pandas——拿被考察的实现算真值，就是在自己考自己。

## 七、数据分析子系统

### 7.1 图结构

```
load_data → classify → analyst → execute
                                  │
              ┌───────────────────┼───────────────────┐
              │ 执行报错           │ 成功且 need_review │ 成功且不需审查
              ▼                   ▼                   ▼
        self_correct          reviewer              report
              │                   │
              └──→ execute        ├─ 通过 ─→ report
                                  └─ 不通过 ─→ self_correct → execute
```

- `MAX_EXEC_RETRY=3`：执行报错最多重写 3 次；
- `MAX_REVIEW_ROUNDS=2`：审查最多两轮（首审 + 复审）；
- 重试额度耗尽仍失败 → 进 `report`，给出「诚实失败」，不再无谓消耗；
- 审查不通过且额度用尽 → 带风险标记出报告，不假装成功。

### 7.2 沙箱

`ecom/analytics/core/sandbox.py` 两层：

1. **AST 静态校验**：顶层模块白名单（pandas/numpy/math/matplotlib/datetime/
   statistics/json/re）；禁危险内置名、dunder 属性、危险 import；
2. **受限执行**：只注入白名单 builtins + 自定义 `__import__`，断开 `__class__`
   之类的逃逸链。

文件 I/O 的加固（2026-10-30）：

- `open()` 本来就被禁，但 `pd.read_csv()` / `plt.savefig()` 不经过 `open()`；
- 按方法名禁掉 pandas/numpy/matplotlib 的读写入口，`read_*` 前缀统一拦；
- `from pandas import read_csv` 也要拦（否则属性检查被绕过）；
- `savefig` 只允许写 `CHART_PATH`，且 `CHART_PATH`/`output_dir` 不许被改写或
  `match case` 捕获；
- `savefig` 的接收者也要校验，防止 `(open(...) and plt).savefig(...)`。

**边界**：这是黑名单，不是边界。`pd.io.*` 之类仍可能绕过；真正的隔离要靠容器/
低权用户/只读挂载/无网络/rlimit。准确说法：**挡模型写错，不挡故意攻击。**

### 7.3 数据集口径

`data/analytics/datasets/<name>/NOTES.md` 是口径的唯一来源：

- 字段含义、空值含义、状态取值、已知缺失；
- `dataset_doc.py` 把它注入三处：分类、写代码、报告；
- 换数据集时来源标签也随之变化，不写死「数据分析」四个字。

`derive_dataco.py` 从原始 DataCo 数据派生 `data.csv`，并记录哪些列是**故意留空**的
（承运商、运单号、发货地、支付时间）——空值的含义是「数据集没有」，不是「未支付」。

## 八、数据层与写路径

### 8.1 `Database`：薄的双后端适配

`ecom/orchestrator/db/engine.py`：

- 业务代码只写 `?` 占位符；MySQL 分支统一翻成 `%s`；
- 每次操作开短连接，不引连接池；
- `query` 返回 `list[dict]`，空结果是 `[]` 不是 `None`；
- `executemany` 用于灌种子（12 万行不是 12 万次开库）；
- `transaction([(sql, params), ...])` 让多条写一起提交/回滚；MySQL 分支显式关
  autocommit，否则事务名存实亡。

### 8.2 schema

四张表：

| 表 | 作用 | 关键约束 |
|---|---|---|
| `orders` | 订单 | 主键 `order_id VARCHAR(32)`；状态是 DataCo 原值 |
| `logistics` | 物流 | 主键 `order_id`；carrier/tracking_no/from_city 允许空 |
| `return_requests` | 退货申请 | 状态只有 待审核/已通过/已拒绝 |
| `return_reviews` | 审核痕迹 | 一个申请只审一次，`return_id` 主键 |

为什么不用 `AUTOINCREMENT`、不用 `TEXT PRIMARY KEY`、金额用 `REAL`：
一份 DDL 要同时能跑 SQLite 和 MySQL。真上线金额应换成分（整数）存。

### 8.3 退货写路径

```
create_return(order_id, reason)
  ├─ 订单不存在                 → OrderNotFound
  ├─ status not in {"COMPLETE"} → ReturnNotAllowed
  ├─ 已有 待审核/已通过          → ReturnNotAllowed
  └─ INSERT 一行 待审核          → 返回 return_id
```

- **只有 COMPLETE 可退。** CLOSED 的语义在数据集里没有依据，宁可不放行；被拦下的
  用户还能找人工，错误放行的申请要花钱。
- **已拒绝可以重新申请**，已通过/待审核不能。少了「已拒绝不在阻断集合」这条，
  用户会撞上「被拒绝过就永远不能申请」的系统。
- **批准是人做的**：`ecom/orchestrator/admin/returns.py` 在同一个事务里改状态 +
  写 `return_reviews`；第二次点击返回 `already=True`，不覆盖人的结论。

### 8.4 schema 演进边界

`init_schema()` 只 `CREATE TABLE IF NOT EXISTS`，不迁移。给已有表加列需要
PRAGMA/information_schema，那是本仓库的第一个迁移机制。当前用新表 `return_reviews`
绕开；**当这张表里出现第一个「人下的结论」时，就必须引入迁移机制**，否则重灌库
等于抹掉人的决定。

## 九、会话与长期记忆

### 9.1 会话存储

`ecom/orchestrator/session.py`：单独的 sqlite（`data/orchestrator/sessions.db`），
不走订单库的 `Database`，避免用户对话和订单数据混在一处。

```
sessions(session_id PK, created_at, updated_at)
messages(id, session_id, role, content, created_at)
memories(id, session_id, summary, keywords, embedding BLOB,
         through_message_id, created_at, UNIQUE(session_id, through_message_id))
```

- 进程内复用一个连接，所有读写加锁（连接对象不是并发安全的）；
- WAL 让 purge CLI 和服务同时开着时不互相阻塞；
- `busy_timeout=5000`；
- `append_turn()` 一问一答同一个提交，要么成对写入，要么一行都不写；
- 过期按时间清（`purge`），不能指望「用户走了就可以删」——没有身份，无法按账号响应。

### 9.2 `session_id` 是凭证

拿到 `session_id` 就能读到整段历史，它等价于 bearer token。由此推出：

- 不放 URL、不进浏览器历史/代理日志/Referer；
- 侧边栏只显示前 12 位；
- 默认 30 天过期；
- 删除只能按 session_id 或按时间。

### 9.3 历史窗口

`session.history(session_id)` 取最近 `HISTORY_TURNS=6` 轮，拼成
`[{"role","content"}]`。`answer()` 把它塞进 `make_initial_state`，图不往它里面写。

### 9.4 长期记忆

```
distill（离线 CLI）
  out_of_window_messages(session_id, 40)
  → LLM 压成 {"summary","keywords"}
  → embedding(summary) → BLOB
  → INSERT memories（UNIQUE 水位线幂等）

recall（每轮问答）
  pool 为空 → 直接 []，一次 embedding 都不调
  否则 embedding(question) → 余弦排序 → MEMORY_TOP_K=3
  → 拼在真实历史前面，返回新列表，不落盘
```

- **存摘要不存关键词**：关键词只告诉你聊过什么，不告诉你结论是什么；
- **按需召回不全灌**：全灌 token 随会话线性涨，且大部分无关；
- **不设相似度阈值**：池子小，没实测过的阈值只会静默丢记忆；
- **embedding 失败抛出**：不写 NULL 向量记忆，水位线不推进，下次可重跑。

## 十、多模态图片输入

### 10.1 链路

```
上传图片（png/jpeg/webp，≤ 5MB）
  → understand_image()
       ├─ MIME 归一、大小校验
       ├─ base64 data URL
       ├─ ChatOpenAI（Qwen3-VL-30B-A3B-Instruct，temperature=0，max_retries=0）
       └─ JSON → ImageIntent（订单号/金额/商品/诉求/置信度）
  → augment_question_with_image()
       文本块：【图片识别结果】...【/图片识别结果】
  → answer()
```

**图片不进主链路**的三个理由：写操作闸会被绕过；每个 worker 都要会看图；可选功能
的失败会拖垮整次问答。

### 10.2 契约与失败

`ImageIntent`：

- `ok=False`：没识别成（没 key/网络/非 JSON/图太大/格式不支持）；
- `ok=True, order_id=""`：识别成功，图里没有订单号，正常情况；
- `needs_manual_order_id`：提示用户补号，不是失败；
- `tokens`：单独记账，因为图片理解发生在 supervisor 的 token 汇总之外。

错误原文只进日志，界面只显示「识别失败，请手动输入」。

### 10.3 安全边界

- `sanitize_image_text()` 把模型输出里的订单号替换成 `[订单号]`；
- `strip_image_block()` 在规则/LLM 提取前摘掉整块；
- 块里的号只以 `source="image"` 补回，写操作不认；
- 图片不写入会话，只存提取后的文本块（界面上另存用户原文用于显示）。

## 十一、流式输出

### 11.1 事件契约

| 事件 | 字段 | 说明 |
|---|---|---|
| `start` | `request_id`, `session_id` | 开始 |
| `delta` | `text` | 增量正文 |
| `final` | `answer`, `sources`, `decision`, `plan`, `tokens`, `elapsed_ms`, `request_id`, `session_id` | 权威结果 |
| `error` | `error`, `request_id` | 人话 + request_id |

服务端：`POST /chat/stream` → `StreamingResponse`，`text/event-stream`，
`Cache-Control: no-cache`，`X-Accel-Buffering: no`。

### 11.2 哪些是真流

- 只有 aggregate 的汇总模型调用逐 token 流；
- worker 答案不送：多路会被改写，提前送会让用户以为定稿；
- 单结论/直接转人工：最终答复作为一个 `delta` 整段送出，**不切碎假装流**；
- 汇总中途失败退回 `_concat`：`final.answer` 是权威，delta 拼起来可能不一致；
- 中途断开：不写会话，半句话接进下一轮比没答更坏。

### 11.3 前后端配合

- 前端用 `fetch` + `ReadableStream`，不用 `EventSource`：需要 POST + 自定义头；
- 按 `\n\n` 切帧、CRLF 归一化；
- `AbortController` 实现「停止生成」；
- `final` 到达后用权威 answer 覆盖增量；
- 开发时 Vite 代理，生产同源托管 `/ui`，不加 CORS。

## 十二、MCP 工具层

### 12.1 定位

MCP 是给「已经知道要干什么」的 Agent 的结构化出口。它不经过 Supervisor：

```
对话：入口 → supervisor → workers → order_tools / knowledge
MCP ：客户端 → stdio → ecom/mcp/server.py → tools.py → order_tools / knowledge
```

### 12.2 工具面

| 工具 | 默认 | 读写 | 说明 |
|---|---|---|---|
| `get_order` | 开 | 读 | 订单 + 物流，字段白名单 |
| `get_order_returns` | 开 | 读 | 已有退货申请 |
| `search_knowledge` | 开 | 读 | 混合检索 + rerank，只返回原文/出处 |
| `list_customer_orders` | 关 | 读 PII | 按客户号查，默认不注册 |
| `create_return` | 关 | 写 | 提交待审核，需 `confirm=true` |

默认关闭 = **不注册**，不是注册后拒绝：工具列表是能力发现，模型看到不存在就
不会白调一轮。

### 12.3 返回契约

```json
{"ok": true, "data": {...}, "meta": {"elapsed_ms": 3.2}}
{"ok": false, "error": {"code": "not_found", "message": "..."}, "meta": {...}}
```

五个错误码：`invalid_input` / `not_found` / `not_allowed` / `unavailable` / `internal`。
失败不抛异常；内部错误原文只进日志。字段白名单，表加列不会自动泄露。

### 12.4 传输与安全

- 只支持 stdio：安全性来自「谁能拉起进程」，没有鉴权/限流/远程调用；
- stdout 是 JSON-RPC 通道，任何 `print()` 都会打断协议；日志全在 stderr；
- L1 公网演示不部署 MCP，没有端口；
- `create_return` 三道闸：服务端开关 + `confirm=true` + `DEMO_MODE`。

## 十三、界面层：Streamlit 与 React

### 13.1 Streamlit（`app.py` + `admin.py`）

`app.py` 是「演示 + 侧边栏直连视图」：

- 对话：走 `answer_stream()`，有图片输入；
- 订单：直接查 `order_tools`，不另写 SQL；
- 数据分析：走 `run_analytics()` 子进程；
- 知识库：直接调 `retrieve/rerank/generate_answer`，展示引用。

`admin.py` 是独立的第二个进程，不是 `app.py` 的视图：

| 页面 | 能写 | 复用 |
|---|---|---|
| 退货审核 | ✅ | `admin/returns.py`，界面不重写判断 |
| 订单与物流 | ❌ | `order_tools.query_order` |
| 知识库队列 | ✅ | `knowledge/cli/review.approve_item` |

`AUTH_ENABLED=1` 时用 admin token 登录（审核人取自 principal、写审计）；
默认退回 `ADMIN_PASSWORD`，不配就 `st.stop()`，端口只绑 `127.0.0.1`。

### 13.2 React（`frontend/`）

只做「提问 → 流式回答」一条主线，外加健康状态、路由、来源、token 用量。

```
开发：Vite 5173，base=/ui/，代理 /health /chat /trace → 127.0.0.1:8000
生产：npm run build → frontend/dist → api.py::mount_frontend() 挂到 /ui
```

- **不加 CORS**：开发靠 Vite 代理，生产同源；浏览器始终看到同一个 origin。
- **`base: "/ui/"` 必须和挂载路径一致**：不一致的症状是页面打开但白屏，资源 404
  只在浏览器控制台可见。
- **凭证只放 `sessionStorage`**：API Key / 邀请码 / 会话号；不进 URL、不写
  `localStorage`。
- **纯文本渲染**：回答进 `white-space: pre-wrap` 的文本节点，不解析 Markdown/HTML，
  不碰 `innerHTML`。
- **没有 trace 查看器**：`/trace` 是排障窗口，不是演示内容；演示模式服务端 404。

### 13.3 入口的取舍

四个入口不是四份实现：

| 入口 | 定位 | 特有能力 |
|---|---|---|
| CLI | 排查问题 | 决策链、逐 worker 耗时、`--json` |
| Streamlit | 演示/内部工具 | 图片、订单、分析看板、知识库引用 |
| FastAPI | 被程序调用 | JSON / SSE、鉴权、trace |
| React | 对外流式界面 | 干净的对话页、设置面板、停止生成 |

## 十四、公网只读演示与安全边界

### 14.1 四道闸

`DEMO_MODE=1` 时：

| 闸 | 实现 | 挡什么 | 挡不住什么 |
|---|---|---|---|
| 邀请码 | `X-Invite-Code` + `compare_digest`；没配就拒绝 | 随手扫端口的人 | 转发码的人；无账号/审计/吊销 |
| 限流 | 进程内 60s 滑动窗口，按客户端 IP | 单客户端刷屏 | 换 IP、多开会话；跨副本不精确 |
| 每日预算 | sqlite 按天记账，实际 token | 一天烧掉一大笔钱 | 预算设得太大 |
| 只读 | `demo.writes_allowed()` / `worker_allowed()` | 退货、分析代码执行、知识库写入 | 不是权限系统 |

细节：

- **只读闸下在业务路径上**：`workers/order.py` 的写路径、router 的 worker 列表、
  aggregate 的 untried 集合、健康检查的 workers 列表；不只靠界面藏按钮。
- **预算账本落磁盘**：Streamlit 每交互重跑、API 多线程；进程内计数等于每个进程
  一份预算。账本读不出来时**拒绝**，成本闸失效要倒向不花钱那一边。
- **trace 返回 404 不是 403**：403 等于告诉对方「这里有东西，只是不给你」。
- **analytics 整个摘掉**：它会执行模型生成的代码，是公网演示里风险最高的一块；
  从路由提示词、规则、最终计划三处一起摘。
- **admin 不部署**：prod compose 只有 app + Caddy，app 不发布宿主端口。

### 14.2 沙箱的真实定位

准确说法：

> AST 白名单 + 受限 builtins + 按名字禁掉 pandas/numpy/matplotlib 的读写入口 +
> 只允许 `savefig(CHART_PATH)`，显著收窄了攻击面；但它不做进程内超时、不做文件
> 系统隔离、不做网络隔离、不做 rlimit，是黑名单不是边界。

真正的隔离要靠：独立容器 / gVisor / Firecracker、只读文件系统、无网络、低权用户、
资源上限。这些当前都没做，写在上线清单里。

## 二十、已知限制与路线图

| 限制 | 现状 | 真要上线怎么改 |
|---|---|---|
| 身份 | 客户号从话里猜；`session_id` 是 bearer token | 登录态/SSO；服务端推 `customer_id`；cookie `HttpOnly+Secure+SameSite` |
| 后台权限 | 一个明文口令，无角色/审计 | 用户表 + RBAC + 审计日志 |
| API 鉴权 | 一个共享 key，不配就放行 | 每调用方凭据 + 吊销 + 默认拒绝 + mTLS/OAuth |
| 沙箱 | AST 白名单 + 黑名单，非强隔离 | 独立容器/gVisor；只读挂载；无网络；rlimit |
| 资源上限 | 只有 compose 的 mem/cpus | 进程级 rlimit、pids_limit、超时 |
| 会话 | 单机 sqlite | Redis/Postgres；多副本共享 |
| 订单库 | SQLite 默认；MySQL 可选 | 生产用 MySQL/Postgres + 连接池 + 备份 |
| schema 演进 | 只建表不迁移 | Alembic/Flyway；先迁移后发版 |
| 可观测 | 文件日志 + JSONL trace | 结构化日志、指标、告警、成本归因 |
| 评测 | 离线小样本 | 持续评测集回归 + 线上抽样 + 人工复核闭环 |
| MCP | stdio，无鉴权/限流 | HTTP 传输 + 身份 + 审计 + 配额 |
| 图片 | 单图、单次提取 | 多图、版面理解、原图留存策略 |

**路线图的顺序**：身份 → 执行安全 → 数据一致性 → 可靠性/成本 → 可观测/质量 →
交付/合规。理由：先把入口关起来，再加厚沙箱；在一扇没锁的门上装防盗链，收益很低。

## 二十一、六个可以复述的故障故事

面试里「讲一个你印象最深的 bug」比功能列表更能证明你真的做过。这六个都来自仓库，
每个都有代码落点和回归测试。

### 21.1 「问退货政策，系统真的插了一条退货申请」

- 症状：一句「订单 52644 到哪了，顺便问下退货政策」触发了 `create_return`。
- 根因：动作识别只看「退货」两个字，没区分「我要退」和「能不能退」。
- 修法：`CREATE_RETURN_HINT` 只认第一人称诉求；`policy_question()` 在写操作前
  二次确认；规则层和 worker 层两道闸。
- 测试：`test_asking_about_the_policy_does_not_file_a_return`。
- 教训：**写操作的触发条件要比读操作严一个量级。**

### 21.2 第二轮回答把第一轮又说了一遍

- 症状：只在重路由后的第二轮出现，同一段话说两遍。
- 根因：`results` 是 `operator.add`，跨轮累加；aggregate 把所有轮次都汇总了。
- 修法：每条结果 `stamp_round()`；aggregate 用 `round_results()` 只取本轮。
- 测试：`test_results_do_not_leak_from_one_round_into_the_next`。
- 教训：**reducer 的语义要写进代码，不能靠「我记得它会清空」。**

### 21.3 路由认得出的订单号，抽取层认不出

- 症状：换真实数据放宽订单号位数后，订单号能路由到 order，但 worker 抽不出来。
- 根因：`router.py` 和 `workers/order.py` 各写了一份正则，只改了一边；**分叉不报错**。
- 修法：形状定义收口到 `utils/ids.py::ORDER_ID_RE`，两处只引用。
- 测试：跨模块的订单号形状一致性测试。
- 教训：**同一个事实出现两次，迟早会分叉；分叉不一定报错，只会算错。**

### 21.4 知识库阈值永远不生效

- 症状：`KB_MIN_SCORE=0.5` 看起来在跑，实际从不触发「没答上来」。
- 根因：读的是 RRF 融合分 `score`（量纲约 0.03），不是余弦 `vector_score`。
- 修法：`_top_vector_score()` 只读 `vector_score`；注释写清两者区别。
- 教训：**指标的名字相同不代表量纲相同。**

### 21.5 `open()` 禁了，`pd.read_csv()` 还能读 `win.ini`

- 症状：沙箱静态校验通过，代码却能读本机文件、往任意路径写图。
- 根因：pandas/numpy/matplotlib 自带文件 API，不经过 `open()`。
- 修法：按方法名禁读写入口；`from pandas import read_csv` 也拦；`savefig` 只许
  `CHART_PATH`；保护 `CHART_PATH` 不被改写/捕获；校验 `savefig` 接收者。
- 测试：`test_run_code_blocks_pandas_file_reads` /
  `test_savefig_may_only_write_chart_path` 等 15 条。
- 教训：**禁了一个名字，不等于禁了一类能力。**

### 21.6 进程内会话字典没有锁

- 症状：并发请求下偶发 `ProgrammingError` / 数据竞争；单测看不出来。
- 根因：FastAPI 把 `def` 端点丢线程池，`_SESSIONS` 字典被多线程读写；换成 sqlite
  后共享连接更不允许并发。
- 修法：进程内单连接 + `threading.Lock`；WAL 处理跨进程；`busy_timeout`。
- 教训：**同步端点不是「串行端点」；连接对象不是并发安全的。**
