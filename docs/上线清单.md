# 上线清单

这份文档回答一个问题：**这套东西要真上线，还差什么。**

它和另外三份文档不在一个轴上。README 讲"它是什么"、`项目说明.md` 是给第一次接触的人的导读、`技术文档.md` 是给要改这份代码的人的手册——那三份都在回答**现在有什么**。这一份问的是**在真实环境里会先坏在哪里**。

所以下面的顺序不是按技术分层排的，是按**出事顺序**排的：第一条是"上线第一周就会炸"的，越往后越是"跑起来之后慢慢暴露"的。

写法上，每一条都尽量说清三件事：**现在是什么样**（带 `文件:行号`，可以照着去读）、**真上线会怎么出事**、**要补什么**。最后有一节「明确不做」，讲清楚哪些是**故意留着的**、以及为什么现在补它是错的。

> 一句话结论在最前面：**这套系统最缺的不是某个加固，是"谁"这个概念。** 没有身份主体，第 2 到第 9 条里的加固都只能做成局部补丁——补上了也说不清它挡的是谁。

> **L1 公网只读演示已经落地（代码层，尚未真部署）**：`DEMO_MODE` + 邀请码、按客户端限流、按天落盘的 token 预算、路由层停用数据分析、`create_return` 在落库前拒绝、app/API 入口统一闸、trace 关闭、`docker-compose.prod.yml` + Caddy 自动 HTTPS、RUNBOOK。它把第 2/3/6/7 条在**演示范围内**收口了——但**没有做第一条**，所以它是"能安全地给人看"，不是"能替真实用户办事"。具体见 [DEMO.md](DEMO.md) 和 [RUNBOOK.md](RUNBOOK.md)。

## 一、没有身份主体

**这一条是根，其它都长在它上面。**

### 现在是什么样

四套"凭证"，四套各自的语义，**没有一个背后是"某个人"**：

| 位置 | 它是什么 | 缺什么 |
|---|---|---|
| `workers/order.py:358` `_guess_customer()` | **从自然语言里猜**客户是谁。正则扫一句话里像 `C20755` 的编号，**猜不出就用 `C9995` 兜底**（`:377`） | 客户身份是**猜的**，不是声明的。而且兜底值是一个真实存在的演示账号 |
| `session.py`（模块 docstring 里自认） | `session_id` 是 **bearer token**——拿到它就能读到这个会话的全部历史 | 它不是账号。没有"这个会话属于谁"这回事 |
| `admin.py:86` | 一个 `ADMIN_PASSWORD` 环境变量 | 没有用户表、没有角色、没有"谁批了这笔退货" |
| `api.py:228` `require_api_key()` | 一个共享的 `API_KEY`，**且不配就放行**（`:237`） | 所有调用方是同一个身份 |

### 真上线会怎么出事

具体到能想象的场景：

1. **客户 A 能看到客户 B 的订单。** 用户在聊天框里打「客户C20755的订单」，`_guess_customer` 就信了。这不是"猜测不准"的问题——**这是把客户号当成了一个不需要验证的声明**。而客户号是可以被猜到的（`C` + 数字）。
2. **查不出订单时会答别人的订单。** 兜底是 `C9995`，一个**库里真实存在**的账号。用户问「我的订单到哪了」但没给编号，系统会拿 `C9995` 的订单回他——**答得头头是道，而且答错了人**。
3. **审不出是谁批的。** `return_reviews` 表记了 `created_at`（什么时候），但 `reviewer` 字段的来源是一个没有身份的口令框。真出事的时候，"谁批的"答不出来。
4. **`API_KEY` 一旦泄露就是全部泄露。** 而且因为不配就放行，一个部署忘了配 `.env` 的服务是**完全敞开的**——它只会在启动日志里打一条 WARNING，没人会看到。

### 要补什么

不是"把口令换成哈希"。**先有身份，再谈鉴权**：

- 一个真正的登录态（谁），`session_id` / `customer_id` 都挂在它下面，**由服务端从登录态推出客户 id，而不是从话里猜**。
- `_guess_customer` 这个函数应该**消失**，或退化成"在已认证的客户名下做个消歧"——它现在做的事（把用户的话当身份声明）在**任何**有身份的系统里都是错的。
- `admin.py` 的口令换成有用户/角色的登录，写操作留审计（谁、什么时候、对哪一笔）。
- `API_KEY` 从"一个共享密钥"变成"每个调用方一个凭据"，能单独吊销。

**这一条做不完，下面每一条都只能做成"局部有效"。**

## 二、未鉴权的界面 + 能执行模型生成的代码

### 现在是什么样

把这两件事连起来看，它比单独看任何一件都严重：

```
用户的问题（不可信输入）
    │
    ▼
app.py:337 render_analytics_tab()  ← 这个界面**没有任何鉴权**
    │
    ▼
workers/analytics.py:66  run_analytics()  → 子进程
    │
    ▼
analytics/agents/analyst.py:26  提示词里写着：用户的问题是：{state['question']}
    │                          ← 用户的话**原样**进了"请写一段 pandas 代码"的提示词
    ▼
analytics/core/sandbox.py:179  run_code()  ← 生成的代码在这里执行
```

**准确地说**：用户的提问**原文**会进到那个「请写一段 pandas 代码来回答这个问题」的提示词里（`analyst.py:26`），而生成的代码会被执行。这是"提示词注入 → 代码执行"的完整链路：**一句精心构造的提问，可以改变模型写出什么样的代码。**

要区分清楚的是**另外两个输入不在这条链路上**——这一点容易说错：

- `dataset_rules`（业务口径）来自仓库里的 `data/analytics/datasets/<名字>/NOTES.md`（`prompts.py:6-14`）。它是**文件写入级**的输入，不是远程输入：能改这个文件的人本来就能改代码。
- 联网搜索的结果（`web_contexts`）进的是**知识库那一条**提示词（`knowledge/generator/answer.py:137`），那是**生成文字回答**，不是生成代码。它有自己的注入风险，但**不在代码执行这条链上**。

### 真上线会怎么出事

- **局域网里任何人**都能打开 8501，问一句精心构造的话，让沙箱里跑一段他没写、但由他诱导出来的代码。
- 沙箱本身（见下一条）不是强隔离，所以"跑一段代码"的实际后果要按第三条来估。
- 没有任何速率限制，所以这是**可重复、可自动化**的。

### 要补什么

三层，按性价比排：

1. **别把它暴露出去。**（开发编排里 app 也绑到 `127.0.0.1`；L1 的公网编排更进一步：演示模式下 `analytics` 根本不进路由计划，视图函数也直接挡住。**但这是策略开关，不是沙箱**——真要开放数据分析，仍得先解决第三条。）
2. **界面要登录。** 这是第一条的直接推论。L1 用邀请码挡住了"随手打开的人"，但邀请码不是登录，也没有角色和审计。
3. **执行前的静态校验要面对"提示词注入"这个前提。** 现在的 AST 白名单是按"模型可能写错"设计的，不是按"有人可能故意让模型写出攻击代码"设计的。

## 三、沙箱到底隔离了什么

**这一条最容易说错，所以先把它做对的事说全。**

### 现在是什么样

`analytics/core/sandbox.py` **不是**"裸奔的 exec"。它做了三件事：

- **AST 白名单**（[`core/sandbox.py`](../ecom/analytics/core/sandbox.py)）：只允许 import 少数几个模块，显式禁掉 `_BANNED_NAMES` / `_BANNED_ATTRS`（挡 `__class__` 之类的逃逸链），`validate_code()` 真的会拒绝；文件读写方法（`read_*` / `to_csv` / `savefig` …）也在这一层按名字拦。
- **受限 builtins**（`:116-121`）：exec 时只注入白名单 builtins，不注入完整的那一份。
- **非 root 用户**：镜像里是 `USER app`（`Dockerfile:139`）。

**它没有做的**（同文件里搜不到 `resource` / `setrlimit` / `timeout`，这是查过的）：

- 没有 rlimits（CPU、内存、文件大小、进程数都无限）
- 没有独立的低权用户、没有网络隔离、没有文件系统隔离
- **文件系统黑名单不是边界**：`open()` 被禁了，但 pandas / numpy / matplotlib 自带文件 I/O。2026-10-30 实测 `pd.read_csv(r"C:\Windows\win.ini")` 能读、`plt.savefig` 能写任意路径；现在这些常见入口被禁，但 `pd.io.*` 之类的间接入口仍可能绕过。
- **`run_code()` 自己不设超时**

关于超时要说得准确：真正的超时保护在**父进程**那边——`workers/analytics.py:66` 的 `subprocess.run(timeout=limit)`（`limit` 默认 175s，比 worker 超时短 5s）。它能**真杀掉**一个 `while True`。但这条保护**只在经编排层调用时存在**：直接调 `run_code()`（比如测试里，或将来某个新入口忘了走那条路）就是无限跑。

### 真上线会怎么出事

- **内存**：`pandas` 读一个大 DataFrame，一个不小心就是几个 G。没有 `mem_limit`，宿主会先撑不住。
- **进程数**：fork 炸弹在容器里能把 PID 打满。
- **文件系统**：沙箱进程和主进程**共用同一个容器文件系统**，能读到 `data/orders.sqlite`、能看到 `.env`。AST 白名单挡住了 `open()`，但 pandas / matplotlib 有自己的文件 I/O——**不需要"逃逸"，用放行的库就能读写**（实测见上）。收紧黑名单后常见入口没了，但它仍然是在同一个进程地址空间里做的名字检查，不是隔离。

### 要补什么

- 容器层面先把资源上限加上：`mem_limit` / `cpus` / `pids_limit`。这不需要改代码，`docker-compose.yml` 加几行——**但要注意它只在容器里生效**，直接 `uv run` 时没有。
- 真要强隔离，执行要挪出主进程的地址空间之外：独立容器、单独的低权用户、只读挂载、`resource.setrlimit()`。
- 在补上强隔离之前，**不要把 analytics 暴露给不可信用户**：演示模式默认关掉它；非演示部署至少要和 API 鉴权一起开。
- 这属于"另开一个项目"的量级，见第十一节。

## 四、密钥与留痕

### 现在是什么样

- **`.env` 明文**，装着三家 LLM 的 key（`ecom/settings.py:53-78`：QWEN / DEEPSEEK / SILICONFLOW / TAVILY）。
- **DSN 里的数据库口令会进异常**。（本次已修：`orchestrator/db/engine.py` 原来把整个 `dsn` 原样写进 `ValueError`，而这条异常最常出现在"启动失败"的日志里。）
- **trace 是明文，且不含脱敏**。`orchestrator/utils/trace.py:38` 用普通 `open(..., "a")` 往 `logs/requests.jsonl` 追加，记的是**提问和回答原文**。
- **会话也是明文落盘**，`session.py` 的模块 docstring 里自认："明文落盘，**不做**静态加密和字段级脱敏"。**会话内长期记忆（`memories` 表）同理**——它存的是这段对话的摘要，**里面同样有用户说过的话**，而且更浓缩。

### 真上线会怎么出事

- **`logs/` 没有轮转、没有保留期。** 只有会话有 30 天 TTL（`settings.py:117`，会话内记忆跟着它一起过期）。日志和 trace 是**只增不减**的——一年之后 `requests.jsonl` 里躺着公司一年的客户提问原文，而没有任何机制删它。
- 这意味着**合规上"能删"这件事只做了一半**：按 `session_id` 能删会话（`session.py:243` `delete_session()` + CLI，**消息和记忆一起删**），但同一个问题在 trace 里还有一份拷贝，**不动**。
- key 明文落盘 + 无轮换流程。一个人的开发机被翻，等于三家 API 一起泄露。

### 要补什么

- 日志轮转 + 保留期（`logging.handlers.RotatingFileHandler` 或外挂 logrotate），**并且保留期要短于等于会话的**——否则"删了会话"是个假动作。
- trace 要不要记原文，是个**产品决定**：排障要原文，合规不要。折中是"摘要 + request_id，原文单独存且短保留"。
- key 走密钥管理（哪怕是 Docker secret / 云厂商的 KMS），不复用、能轮换。
- 交接前先确认 `.env` 从来没进过 git 历史（这个仓库里 `.gitignore` 一直是拦着的，但要验证，不是假设）。

## 五、数据与状态

### 现在是什么样

- **SQLite 单文件**：`data/orders.sqlite`（约 11MB，65752 笔订单）+ `data/orchestrator/sessions.db` + `data/knowledge/review_queue.db`。
- **没有备份**，也没有"备份过没有"的记录。
- **没有 schema 迁移机制**：`engine.py` 的 `init_schema()` 逐条执行 `schema.sql`，里面全是 `CREATE TABLE IF NOT EXISTS`。**只建不改**。
- **`knowledge/review/queue.py` 原来有跨线程连接却不配锁**（本次已修，抄的 `session.py`：锁 + WAL + `busy_timeout`）。两个文件同一类存储、原来两种写法——所以这一条的教训不是"忘了加锁"，是**同类东西没有一处对齐的写法**。

### 真上线会怎么出事

- **加一列就得停机 + 手工 ALTER。** 现在这个项目的"改 schema"一直是靠"删库重灌"绕过去的——因为**数据全是派生的**（`orders.sqlite` 从 `data/orchestrator/seed/*.csv` 灌，向量库从 `documents/` 建）。这个前提一旦被打破就立刻出事：`return_reviews` 里一旦有**人下的结论**，重灌就等于抹掉人的决定。
- **SQLite 在同一时刻只有一个写者。** 对这个体量够用（这也是当初选它的理由），但它把"横向扩到两个副本"这条路直接堵死了——两个容器写同一个 `.db` 文件不是"慢一点"，是错。
- 没有备份 = 没有恢复演练 = 出事那天第一次发现备份是坏的。

### 要补什么

- **先有迁移机制**，再谈接真库。顺序反过来会很痛苦：换库和改 schema 同时发生，出问题时分不清是哪一步。
- 订单库换 MySQL（代码里 `ORDER_DB_DSN` 那条路径**已经写好了**，就是本仓库没拿真库跑过——本机 Docker 里的 mysql8 在 3308）。
- 备份用 SQLite 的在线备份 API 或直接上真库，别用 `cp`（WAL 模式下拷文件可能拷到不一致的状态）。
- **部署前置要写进文档**：`data/orders.sqlite` 和向量库**都不入仓**（`.gitignore` 拦着），clone 下来必须 `main.py --init-db` + `python -m ecom.knowledge.cli.ingest` 才能跑通界面。

## 六、网络与传输

### 现在是什么样

- **开发编排**（`docker-compose.yml`）里 app / admin 都是 `streamlit` 直接发布的 HTTP，没有反向代理、没有 TLS；两条都只绑 `127.0.0.1`。这解决的是"谁能连到端口"，**不解决"传输过程是明文"**。
- **L1 公网编排**（`docker-compose.prod.yml`）补上了这一层：只有 app + Caddy，Caddy 自动申请证书并终止 TLS，app 不发布宿主机端口；**admin 不在这个编排里**。
- `api.py`（FastAPI）**根本没有 compose 服务**——`docker compose up` 不会起它，只能手工 `uvicorn`。L1 也没有把它暴露出去（邀请码、限流、预算的代码已经在 API 里，供将来接入）。
- **MCP 工具服务（`ecom/mcp`）只走 stdio**，没有端口、不在任何 compose 编排里，L1 公网演示不部署它。它的安全性来自"谁能拉起那个本地进程"，不是来自协议本身；真要远程调用，得先补 HTTP 传输 + 身份 + 审计。

### 真上线会怎么出事

- `session_id` 是凭证明文放在请求里的。**局域网里抓包就能拿到它**，然后就能读到那个会话的全部历史。
- `X-API-Key` 同理。
- 真上线时那个反向代理（TLS 终止）必须由**部署方**接过来，而不是把 `127.0.0.1` 改回 `0.0.0.0`——compose 里 admin 那一条的注释里写了这句话，别改错了。

### 要补什么

- TLS 终止（反代或直接上 HTTPS），并且 cookie/头要带 `Secure` / `SameSite`。
- 如果要对外提供 API，`api.py` 需要自己的 compose 服务 + 副本数 + 健康检查。
- 明确"哪个入口是给谁的"：现在三个入口（app / admin / api）的边界写在文档里，**上线时要变成网络策略**（哪个端口谁能访问）。

## 七、可靠性与成本

### 现在是什么样

- **L1 演示模式**有了限流（进程内、按会话/IP）和每日 token 预算（`data/orchestrator/demo_usage.sqlite`，按天累计、重启也算数），到额度就拒绝请求。它挡的是**演示环境的成本失控**，不是生产级的配额系统：没有按用户/租户分账，限流也是单进程的。
- 除演示模式外，`api.py` 里**没有中间件、没有信号量、没有限流**（全文搜过——`limit` 只是个分页参数）。
- 单进程 `uvicorn`（`api.py` 的 `def` 不是 `async def`，因为图里全是阻塞调用——这个取舍本身是对的，但它意味着**并发度 = 线程池大小**）。
- 长驻进程**不自清过期会话**。`session.py` 的 docstring 自认要外挂 cron。
- **蒸馏也不自动发生**。会话内长期记忆只在有人跑 `cli.memory distill` 时才长出来（**刻意不放在问答路径上**，免得每问一句都可能多一次模型调用）——所以它同样要外挂 cron。跑漏了不会丢消息（水位线没推进，下次接着蒸），只是记忆旧一点。
- `MAX_ROUNDS=2` 限制了回环（好事），但**没有 per-user 的 token / 费用预算**，也没有熔断。

### 真上线会怎么出事

- 一次突发的重复请求能把三家 LLM 的额度一起打空——**没有任何一处会先喊停**。
- 阻塞调用 + 单进程 = 一个慢请求（知识库那一路实测 8.1 秒）会把线程占住；没有排队和背压，超过线程池之后就是雪崩。
- 会话库一直长，没有人清。

### 要补什么

- 生产级的限流（按身份/租户，而不是按 IP）+ 并发上限（信号量）。**这两个是"让服务活下来"，不是"优化性能"**。L1 演示版只做了"按会话/IP + 全局每日 token"，够挡住公网演示的成本，不够支撑真实流量。
- per-key 的 token / 费用预算 + 超阈值熔断。这个项目的成本**几乎全在 LLM 调用上**，所以它是唯一值得先做的成本控制。L1 的每日预算是它的最小版本（全局，不按 key）。
- 会话清理挂一个 cron / 定时任务（`cli.session purge`），**蒸馏挂另一个**（`cli.memory distill --all`）。**蒸馏那条要按成本排**：它每次都会真调模型和 embedding，会话越多越贵——这是"记忆不是实时的"换来的东西，别当成运维疏忽顺手塞进请求路径。

## 八、可观测

### 现在是什么样

- 有**本地 trace**（`logs/requests.jsonl`），记了 request_id、路由来源、每个 worker 的耗时和成败。这一块做得比多数同类项目细。
- **没有指标、没有告警、没有 dashboard。**

### 要补什么

最值得先暴露的是**一个已有的字段**：`router_source`（`llm` / `rule` / `fallback`）的分布。

理由是 `FLOWCHART.md` 第三节已经写过的那句——**"rule / fallback 的比例一涨，说明 LLM 那边在坏"**。它是整套系统里**唯一一个能提前告诉你"模型侧正在劣化"的信号**，而它现在躺在 JSONL 文件里没人看。把它接成一个计数器，比接十个 CPU 指标有用。

往后才是：每请求的 token 成本、每 worker 的 p95 耗时、`insufficient`（检索没命中）的比例。

## 十、如果真要上，按这个顺序做

上面是九条并列的。真要动手时**不能并列做**，因为它们互相是前提：

```
① 身份体系  ─────────────────────────┐
   先有"谁"，下面五条才有意义          │
                                      ▼
② 界面登录 ─► ③ 网络收口 ─► ④ 资源上限 ─► ⑤ 限流/预算
   （② 是 ① 的直接推论）   （不用改代码）   （让服务活下来）

⑥ 迁移机制 ─► ⑦ 订单库换 MySQL
   （先有迁移，再换库）

⑧ 日志轮转+保留期 ─► ⑨ 指标（先从 router_source 开始）
   （合规与可观测，可以并行）
```

**L1 做到哪一步**：③（网络收口 + TLS）、④（容器资源上限）、⑤（限流 + 每日预算）在**只读演示范围内**落地了；①+②（身份 + 登录）没有做。所以 L1 是"能安全地挂在公网上给人看"，**不是**下面这个"能给别人用"。

**最小的"能给别人用"的样子**是 ①+②+③+④：有身份、界面关起来、只绑本机、容器有资源上限。这四条加起来的工作量**远小于**第 2、3 条里那些"把沙箱做成强隔离"的活，而它们挡住的风险更大。

**反过来，最不该先做的是**：给 `admin.py` 的口令加复杂度校验、把 `API_KEY` 换成长一点的随机串、给沙箱再加几条 AST 规则。这些都在**没有身份**的前提下做——改完之后，"谁"这个问题还在原地，但会给人一种"安全加固做过了"的错觉。**这是这份清单里最容易走错的一步。**

## 十一、明确不做

这一节比上面九条更重要。这个项目的定位是**面试作品**，不是产品——那么"没做什么"就必须是**想清楚了才不做的**，而不是"还没来得及"。

**不做的，以及为什么：**

- **真正的身份体系。** 它是第一节，也是**唯一一个"做了就要改架构"的**：客户 id 从"猜"变成"从登录态推"，`_guess_customer` 要删掉，界面上要加登录。这是另一个项目的量级，而且它会毁掉"clone 下来点开就能用"这个定位（`admin.py` 和 `app.py` 之所以并列而不是合并，就是为了保住它）。**这个项目的正确说法是"我知道这里没有身份，也知道补它要动什么"，不是"我做了鉴权"。**
- **强隔离的沙箱。** 独立的低权用户、`setrlimit`、只读挂载、独立容器——这些每一件单独看都不难，但合起来是**另一个系统**（要处理依赖、文件交换、性能）。现在这套"AST 白名单 + 子进程超时"是**和这个项目的体量匹配**的选择：它挡得住模型写错，挡不住有人故意攻击。**而"挡住故意攻击"的前提是先要有人能攻击到它**——那是第 2 条的事，第 2 条没做之前，把沙箱做厚是在给一扇没锁的门装防盗链。
- **不把 SQLite 换成真数据库、不接指标。** 没有真实流量，现在加进去的每一个阈值都是**猜的**——猜出来的配置比没有配置更危险，因为它看起来像是有依据的。这些的**设计**（什么该限、限到什么程度、哪个指标先看）写在上面了，**实现**要等有真实流量再补。
  （L1 的限流和每日预算是例外：它们不是为了"优化真实流量"，是为了**让公网演示的成本有上限**。默认值（12 次/分钟、20 万 token/天）明确是演示量级，不是容量规划。）
- **不给 `return_requests` 加列 / 不引 schema 迁移机制。** 现在全库都是派生数据，"删库重灌"一直是免费的。**在一个人人都能重灌的库上引入迁移机制，是在为一个还不存在的问题写代码。** 什么时候该做，第五节写了判据：**当 `return_reviews` 里出现第一个"人下的结论"时。**
- **不执行退款、不改 `orders.status`。** 没有支付网关，假装退款比不做更坏；`orders.status` 是数据源原值，改它就是编造数据。（这条 README 里也有，是同一个边界。）
- **不把 MCP 挂到公网、不做 HTTP 传输 / OAuth。** stdio 的前提是"客户端能拉起本地进程"，一旦改成远程 HTTP，就要回答"谁在调、算谁的、怎么限流、出问题查哪条日志"——这四个问题现在一个都没有答案。所以 v1 只做本地 stdio，默认只读；`create_return` 还要服务端开关 + `confirm=true` 两把钥匙。**这不是"没来得及做"，是开了就得连身份体系一起做。**

**已经在做的，但要说清它的分量：**

- `docker-compose.yml` 里 app / admin 绑 `127.0.0.1`、`API_KEY` 的常量时间比较、`ADMIN_PASSWORD` 不配就拒绝启动——这三件事**都不是"安全"**，它们是**"默认值不要是危险的"**。区分清楚：前者需要一个信任模型，后者只需要一个好习惯。
